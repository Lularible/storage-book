# 4.4 CTZ Skhipu-List: The COW Structure for File Data

## Four evolutions of a linked list

You will now design an on-disk structure to store file data. You have these constraints:
- Must support COW (Copy-On-Write) because power-off safety is required
- Append writes must be O(1) since the most common use case for embedded is log append
- Random reads must be faster than O(n) because the user sometimes needs to jump to the middle of the file
- Memory usage must be O(1), and the entire B-tree cannot be built into memory like btrfs.
- The metadata overhead should be small, and each data block cannot be allocated an independent inode.

Let’s take a look at what options you have in turn, and why each one is rejected.

**First generation: One-way linked list. **

```
One-way linked list: data blocks are linked in sequence
=========================================
┌─────────┐ ┌──────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐
│ data 0 │─>│ data 1 │─>│ data 2 │─>│ data 4 │─>│ data 5 │
│ │ │ │ │ │ │ │ │ │
└─────────┘ └──────────┘ └─────────┘ └─────────┘ └──────────┘
```

Append a block → The pointer of the second to last block needs to be updated → COW is triggered → The pointer of the third to last block needs to be updated → Propagate all the way to the first block. This is an O(n) append operation, which is a disaster for log files.

**Second generation: reverse linked list. **

```
Reverse linked list: pointing backward from now
=========================================
┌─────────┐ ┌──────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐
│ data 0 │<─│ data 1 │<─│ data 2 │<─│ data 4 │<─│ data 5 │
│ │ │ │ │ │ │ │ │ │
└─────────┘ └──────────┘ └─────────┘ └─────────┘ └──────────┘
```

To append a block → just create the new block and let the new block point to the old tail block. O(1)! Perfect.

But what about reading? If you want to read data 0, you have to start from data 5 and follow the reverse pointer all the way back to data 0, which is O(n) reading. You can start reading from head, but head only knows the last block, and you need to traverse backward to find the first block. **O(n²) read operations are not acceptable. **

**The third generation: reverse skhipu list (Skhipu-List). **

The classic definition of a skhipu list is to add additional pointers to certain nodes in the linked list and skhipu several intermediate nodes so that the search can "jump forward". LittleFS uses it upside down, the pointers are reversed, but the jumping logic is the same.

```
CTZ reverse jump table
=========================================
┌─────────┐ ┌──────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐
│ data 0 │<─│ data 1 │<─│ data 2 │<─│ data 3 │<─│ data 4 │<─│ data 5 │
│ │<─│ │──│ │<─│ │──│ │ │ │
│ │<─│ │──│ │──│ │──│ │ │ │
└─────────┘ └──────────┘ └─────────┘ └─────────┘ └──────────┘
```

The distance from block 5 to block 1: block 5 → block 4 → block 2 → block 1. The ctz=0 of block 5 only has a pointer to block 4 and cannot jump directly to block 3.

The distance from block 5 to block 0: block 5 → block 4 → block 0. The ctz=2 of block 4 can directly go to block 0 across blocks 3, 2, and 1.

**The key question for this skhipu list is: how many pointers should there be in each block? How far do the pointers jump? **

One solution is "random" (classic skhipu list), but this is not feasible in an environment without dynamic memory allocation. Another solution is "fixed step size", but that will degrade to O(√n) query complexity.

**LittleFS's solution, which is the core innovation of this data structure, is to use the "Count Trailing Zeros (CTZ)" instruction to determine the number of pointers and jump step size for each block. **

## The encounter between CTZ instruction and jump table

Count Trailing Zeros (CTZ) is a CPU instruction whose function is: **Return the number of consecutive 0s at the end of the binary representation of an integer. **

```
CTZ example:
  ctz(1) = ctz(0b0001) = 0
  ctz(2) = ctz(0b0010) = 1
  ctz(3) = ctz(0b0011) = 0
  ctz(4) = ctz(0b0100) = 2
  ctz(5) = ctz(0b0101) = 0
  ctz(6) = ctz(0b0110) = 1
  ctz(7) = ctz(0b0111) = 0
  ctz(8) = ctz(0b1000) = 3
```

The rules of the CTZ jump list are extremely simple: **For the nth data block (n starts from 0), it contains ctz(n) + 1 pointers to the previous block. These ctz(n)+1 pointers skhipu 2^0, 2^1, 2^2, ..., 2^ctz(n) blocks respectively. **

Let's plot it (taking 6 data blocks as an example):

```
n=0: ctz(0)=0 → 1 pointer → no previous block to point to → special case of data block 0
n=1: ctz(1)=0 → 1 pointer → skhipu 2^0=1 blocks → point to block 0 length=1
n=2: ctz(2)=1 → 2 pointers → skhipu 2^0=1 and point to block 1 length=1
                         → Skhipu 2^1=2 and point to block 0 length=2
n=3: ctz(3)=0 → 1 pointer → skhipu 2^0=1 and point to block 2 length=1
n=4: ctz(4)=2 → 3 pointers → skhipu 2^0=1 and point to block 3 length=1
                         → Skhipu 2^1=2 and point to block 2 length=2
                         → Skhipu 2^2=4 and point to block 0 length=4
n=5: ctz(5)=0 → 1 pointer → skhipu 2^0=1 and point to block 4 length=1

Complete structure:
┌────────┬────────┬────────┬────────┬────────┬─────────┐
│ block0 │ block1 │ block2 │ block3 │ block4 │ block5 │
│ │──>b0 1 │──>b1 1 │──>b2 1 │──>b3 1 │──>b4 1 │
│ │ │──>b0 2 │ │──>b2 2 │ │
│ │ │ │ │──>b0 4 │ │
└────────┴────────┴────────┴────────┴────────┴─────────┘

Interpretation: block2 has two pointers - skhipu 1 block to b1, skhipu 2 blocks to b0
      block4 has three pointers - skhipu 1 to b3, skhipu 2 to b2, skhipu 4 to b0
```

The elegance of this structure is that the number of pointers per block is exactly 2 on average. ** Derivation: Among all n blocks, there are n/2 blocks with CTZ value = 0, n/4 blocks with CTZ value = 1, and n/8 blocks with CTZ value = 2... Infinite series summation:

```
Average number of pointers = lim(n→∞) (1/n) × Σ(ctz(i)+1) = Σ(1/2^i) = 2
```

**Each data block only occupies an average of 8 more bytes (2 32-bit pointers) of metadata space. ** For a 4KB block, the overhead is 0.2%, which is almost negligible.

## Reverse position from size: an OEIS coincidence

CTZ jump table also has a hidden killer feature: **Given a file size, you can calculate the index and offset of the last data block in O(1) time. ** This means that when storing a file in a directory, you only need two values: head (the address of the last block) and size (the total size of the file), and there is no need to store the two redundant information "index of the last block" and "intra-block offset".

Derivation process:

The effective data capacity of each data block n is: `block_size - 4×(ctz(n)+1)`, because the ctz(n)+1 pointers in the block occupy the front space.

Then a file of size N occupies blocks from 0 to some n_max:

```
N = Σ(i=0→n) [B - (w/8)×(ctz(i)+1)]

Among them:
  B = block_size (block size, bytes)
  w = word width (32 bits)
```

This accumulation can be calculated in O(n) time. But the author of LittleFS discovered an amazing coincidence on OEIS (Online Encyclopedia of Integer Sequences):

```
Σ(i=0→n) (ctz(i)+1) = 2n - popcount(n)
```

Where `popcount(n)` is the number of 1's in the binary representation of n.

Verify a few values:
- n=0: Σctz+1 = 0, 2×0-popcount(0) = 0-0 = 0 ✓
- n=3: Σctz+1 = 1+2+1 = 4, 2×3-popcount(3=0b11)=6-2=4 ✓
- n=5: Σctz+1 = 1+2+1+3+1 = 8, 2×5-popcount(5=0b101)=10-2=8 ✓

Plug this equation into the file size formula:

```
N = B×n - (w/8)×(2n - popcount(n))
  = B×n - (w/8)×2n + (w/8)×popcount(n)
  = (B - w/4)×n + (w/8)×popcount(n)
```

Solve for n from:

```
i0 = N / (B - w/4); if i0 == 0, n = 0; otherwise n = (N - (w/8)×(popcount(i0-1)+2)) / (B - w/4); offset = N - (B - w/4)×n - (w/8)×popcount(n)
```

This is a pure formula calculation that requires no loops or table lookup. ** In LittleFS's 32-bit environment (w=32), it is very fast.

**This is the implementation of lfs_ctz_index:**

```c
// lfs.c:2873-2884 — Calculate block index from file offset
static int lfs_ctz_index(lfs_t *lfs, lfs_off_t *off) {
    lfs_off_t size = *off;
    lfs_off_t b = lfs->cfg->block_size - 2*4;   // B - w/4 = B - 8
    lfs_off_t i = size / b;                       // approximate index
    if (i == 0) {
        return 0;
    }

    i = (size - 4*(lfs_popc(i-1)+2)) / b;        // Exact index formula
    *off = size - b*i - 4*lfs_popc(i); // Offset within block
    return i;                                     // Return block index
}
```

This function receives a file offset, returns the block index where the offset is located, and modifies `*off` to an intra-block offset. The whole process only requires a few integer operations and takes **O(1) time. **

## lfs_ctz_find: Quickly locate along the jump table

With the `lfs_ctz_index`, reading data from any location in a file is simple. `lfs_ctz_find` starts from head and uses the jumping ability of CTZ jump table to greedily select the pointer that can cover the maximum distance without crossing the target.

```c
// lfs.c:2886-2918 — Find the block where the target offset is located in the CTZ jump table
static int lfs_ctz_find(lfs_t *lfs,
        const lfs_cache_t *pcache, lfs_cache_t *rcache,
        lfs_block_t head, lfs_size_t size,
        lfs_size_t pos, lfs_block_t *block, lfs_off_t *off) {
    if (size == 0) {
        *block = LFS_BLOCK_NULL;
        *off = 0;
        return 0;
    }

    lfs_off_t current = lfs_ctz_index(lfs, &(lfs_off_t){size-1});
    lfs_off_t target = lfs_ctz_index(lfs, &pos);

    while (current > target) {
        lfs_size_t skhipu = lfs_min(
                lfs_npw2(current-target+1) - 1,
                lfs_ctz(current));

        int err = lfs_bd_read(lfs,
                pcache, rcache, sizeof(head),
                head, 4*skhipu, &head, sizeof(head));
        head = lfs_fromle32(head);
        if (err) {
            return err;
        }

        current -= 1 << skhipu;
    }

    *block = head;
    *off = pos;
    return 0;
}
```

Core logic: Starting from the last block, select the maximum number of steps that can be jumped each time (not exceeding the target), read the pointer, and jump to the earlier block. Because each jump at least halve the distance to the target (similar to a binary search), the worst-case number of hops is O(log n). ** Combined with the need to read from Flash for each jump (O(1)), the total read complexity is O(log n).

## lfs_ctz_extend: COW append

Another key operation for file writing is appending. In the CTZ jump table, the process of appending a new block is:

```c
// lfs.c:2921-3017 — lfs_ctz_extend (simplified version)
static int lfs_ctz_extend(lfs_t *lfs,
        lfs_cache_t *pcache, lfs_cache_t *rcache,
        lfs_block_t head, lfs_size_t size,
        lfs_block_t *block, lfs_off_t *off) {
    while (true) {
        // 1. Allocate a new block
        lfs_block_t nblock;
        int err = lfs_alloc(lfs, &nblock);
        if (err) return err;

        // 2. Erase new blocks
        err = lfs_bd_erase(lfs, nblock);
        if (err) {
            if (err == LFS_ERR_CORRUPT) goto relocate;
            return err;
        }

        if (size == 0) {
            // File is empty: the new block is the first block
            *block = nblock;
            *off = 0;
            return 0;
        }

        lfs_size_t noff = size - 1;
        lfs_off_t index = lfs_ctz_index(lfs, &noff);
        noff = noff + 1;

        // 3. If the previous block is not full (not the entire block), copy the data to the new block
        if (noff != lfs->cfg->block_size) {
            for (lfs_off_t i = 0; i < noff; i++) {
                uint8_t data;
                err = lfs_bd_read(lfs, NULL, rcache, noff-i,
                        head, i, &data, 1);
                // Write new block
                err = lfs_bd_prog(lfs, pcache, rcache, true,
                        nblock, i, &data, 1);
            }
            *block = nblock;
            *off = noff;
            return 0;
        }

        // 4. The previous block is full: create a new block and write the jump table pointer
        index += 1;
        lfs_size_t skhipus = lfs_ctz(index) + 1;
        lfs_block_t nhead = head;
        for (lfs_off_t i = 0; i < skhipus; i++) {
            // Write the i-th pointer (pointing to 2^i blocks ago)
            nhead = lfs_tole32(nhead);
            err = lfs_bd_prog(lfs, pcache, rcache, true,
                    nblock, 4*i, &nhead, 4);
            nhead = lfs_fromle32(nhead);

            if (i != skhipus-1) {
                // Read the next pointer value to be written
                err = lfs_bd_read(lfs, NULL, rcache, sizeof(nhead),
                        nhead, 4*i, &nhead, sizeof(nhead));
                nhead = lfs_fromle32(nhead);
            }
        }

        *block = nblock;
        *off = 4*skhipus; // data starts from behind the pointer area
        return 0;

    relocate:
        LFS_DEBUG("Bad block at 0x%"PRIx32, nblock);
        lfs_cache_drop(lfs, pcache);  // Try again
    }
}
```

Key steps:
1. Allocate a new block (via the block allocator)
2. If the previous block is not completely filled (for example, the file ends at a non-block boundary), coalesce (merge) the data from the old block to the new block
3. Write ctz(n)+1 jump table pointers
4. The data area starts after the pointer area

**Append is O(1):** Allocate block, erase block, write pointer, return. Independent of previous blocks, no old data needs to be modified.

## COW write securityCTZ jump table implements true Copy-On-Write file data storage. The process of modifying data in the file is as follows:

```
COW writing process of CTZ jump table
=========================================

Original state:
                                     ┌──────────┐
                                    ┌│metadata │
                                    ││ │
                                    ││ │
                                    │└──────────┘
                                    │ │
                                    │ v
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│ data 0 │<│ data 1 │<│ data 2 │<│data 3 │
│ │<│ │─│ │ │ │
│ │ │ │ │ │ │ │
└────────┘ └────────┘ └────────┘ └────────┘

Write new data to the end of the file:
                                    ┌──────────┐
                                   ┌│metadata │ ← Not updated yet
                                   ││ │
                                   ││ │
                                   │└──────────┘
                                   │ │
                                   │ v
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│ data 0 │<│ data 1 │<│ data 2 │<│data 3 │ ← The old data is still there
│ │<│ │─│ │ │ │
│ │ │ │ │ │ │ │
└────────┘ └────────┘ └────────┘ └────────┘
     ^ ^ ^
     │ │ │ ┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐
     │ │ └────│ new │<│ new │<│ new │<│ new │
     │ └────────────────│data 2 │<│data 3 │─│data 4 │ │data 5 │
     └──────────────────│ │─│ │─│ │ │ │
                        └────────┘ └────────┘ └────────┘ └─────────┘

Submit to metadata pair:
                                                            ┌──────────┐
                                                           ┌│new │
                                                           ││metadata │
                                                           ││ │
                                                           │└──────────┘
                                                           │ │
                                                           │ │
                                                           │ v
                              ┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐
                              │ new │<│ new │<│ new │<│ new │
                              │data 2 │<│data 3 │─│data 4 │ │data 5 │
                              │ │─│ │─│ │ │ │
                              └────────┘ └────────┘ └────────┘ └─────────┘
```

1. Create a new data block chain (COW), leaving the old data blocks intact.
2. Update the file record in the metadata pair to point to the new head block.
3. Old data blocks become garbage and wait for subsequent compaction recycling.

**If power is lost at any step: the old metadata pair (pointing to the old data block chain) is still intact. After mounting, restore to the state before writing. This is the combined power of COW+Metadata Pair. **

## Comparison with KnotFS

The file data management of KnotFS (Chapter 3) adopts a simpler and more direct solution: **Each file's `knode_t` directly embeds the `blocks[8]` array, with up to 8 block addresses, and no separate indirect block. **The maximum file size is 8×4KB = 32KB.

```
KnotFS Indirect Block vs LittleFS CTZ Skhipu-List
=============================================================
Features KnotFS LittleFS
────────────────────────────────────────────────────────
Data block index Direct block address array CTZ jump table
The upper limit of the number of blocks is 8 (fixed) unlimited (theoretical 2^32)
Random access O(1) (direct array index) O(log n)
Append writing O(1) (write new block + update FT) O(1)
Random writing (mid-modification) requires rewriting file entries and rebuilding subsequent chains O(n)
Metadata size: Approximately 72B per file entry. No additional blocks per file.
                    indirect block) (information is stored in directory entries)
────────────────────────────────────────────────────────
```

KnotFS is designed with the assumption that "files are small and limited in number" (8 files × 32KB maximum each = 256KB total data size). Under this constraint, fixed arrays are the best choice, simple, fast, and have a certain memory footprint.

LittleFS is designed with the assumption that "both file and device sizes are undetermined". It needs to support devices from 512KB to GB, and files from a few bytes to hundreds of MB. CTZ jump list is the optimal solution under this scalability requirement.

## Shrinkage and inline optimization of file system

LittleFS's CTZ jump table also has a flexible variant: **Small file inline (inline). ** Small files can be inlined into metadata pairs. The upper limit is `min(cache_size, attr_max, metadata_max, or block_size/8)`; 4KB blocks can be up to 512 bytes, and are also limited by `cache_size` by default.

```
Inline file storage
=========================================
┌──────────────────────┐
│ revision │
│──────────────────────│
│ file.txt name │
│ file.txt data │ ← is directly stored in the metadata pair
│ (≤inline_max, usually ≤512B) │ No CTZ jump table required
│──────────────────────│
│CRC │
└──────────────────────┘
```

```
File storage cost comparison:
  Inline file (≤inline_max): ~16 bytes + file data (name + tag)
  Small files (over inline_max, 1 block): ~4KB (one CTZ block)
  Large file (n blocks): ~n × 4KB (average overhead of 2 pointers per block)
```

The storage overhead of small files may be much greater than the file itself (for example, under the 64-byte inline limit, a 65-byte file will occupy a 4KB block); as the file grows, the overhead ratio gradually decreases.

This is another time LittleFS demonstrates the power of "bounded thinking": **Not only is RAM growth bounded, storage overhead growth is also bounded. **

KnotFS's CoW takes a simpler path: no CTZ jump table, no reverse block number mapping, and up to 8 direct blocks per file, stored directly in the `blocks[8]` array in the file entry. The advantage of this is that the amount of code is extremely low (no CTZ formulas and jump table navigation are required), but the cost is that the maximum file size is only 32KB. LittleFS's CTZ is designed to "support arbitrarily large files without sacrificing read performance"; KnotFS's simplified version CoW is designed to "manage up to 8 files in 64KB total space". Also called CoW, the constraints are different, and the complexity level of the implementation can differ by two orders of magnitude.

## Next episode preview

The CTZ skhipu table allows us to store and read file data efficiently, but every time a data block is allocated, it relies on the block allocator to tell you "where the next free block is." On a small device with 128 blocks, it only takes milliseconds to scan the entire disk. But on devices with 1024 blocks or more, a full scan is unacceptable. LittleFS solves this problem with a fixed-size lookahead buffer, which is like a moving window that slides on the free block space to find a batch, use up a batch, and find another batch. In this seemingly simple allocation process, dynamic wear leveling is quietly achieved.
