# 3.3 FAT: The Simplest Scheme, the Most Fatal Flaw

## You got a formatted SD card

Imagine a scenario: You just bought a 32GB SD card from Electronic City. You plug it into your computer's card reader, and a window pops up: "This disk needs to be formatted." Click OK. After a second, the computer tells you that the format is complete and it is now a clean FAT32 volume.

The FAT (File Allocation Table) file system was born in 1977. It was designed by Marc McDonald, participated/led by Bill Gates, and was first used in Microsoft BASIC-80. It was later used on MS-DOS, Windows, USB flash drives, SD cards, and even some embedded devices. It is the most installed file system on the planet.

**It is also the least suitable file system for bare NOR Flash on the planet. **

Why? Let's take it apart and see.

---

## The Three-Level Structure of FAT: A 1977 Design Film

The disk layout of the FAT file system is extremely simple, so simple that you can draw it on a napkin:

```
FAT32 disk layout
=======================

┌─────────┬──────────┬─────────┬─────────────────────┐
│Boot Sec.│FAT1 │FAT2 │Data Clusters│
│ (1 sector) │ (n sector) │ (n sector) │ (all remaining sectors) │
└─────────┴──────────┴──────────┴──────────────────────┘
  ↑Load into memory ↑The backbone of the file list ↑Real data storage location
  Identify the partition FAT32 root directory is the cluster chain of the Data area, and the starting cluster is specified by BPB_RootClus
```

We dismantle it layer by layer.

**First layer: Boot Sector**

The Boot Sector is the first sector (512 bytes or 4KB) of the FAT volume. It contains a "parameter table":

```c
// Core parameters of FAT32 Boot Sector (BIOS Parameter Block)
struct fat32_bpb {
    uint16 bytes_per_sector;       // Number of bytes per sector, usually 512
    uint8  sectors_per_cluster;    // Number of sectors per cluster, such as 8
    uint16 reserved_sectors;       // Number of reserved sectors (sectors after Boot to FAT)
    uint8  num_fats;               // The number of copies of the FAT table, usually 2
    uint32 total_sectors;          // Volume total number of sectors
    uint32 sectors_per_fat;        // How many sectors does each FAT table occupy?
    uint32 root_cluster;           // The starting cluster number of the root directory
    // ... and many more fields
};
```

Once these parameters are written, the "geometry" of the entire volume is determined. You cannot change the size of the cluster at runtime, and you cannot move the relative positions of the FAT table and Root Directory. It is formatted once and fixed for life.

**The second layer: FAT table, the backbone of the file system**

The FAT table is the heart of the FAT file system. It does one thing at its core: **String the clusters of files into a chain. **

```
"Cluster chain" principle of FAT table
=======================

Suppose a file occupies cluster 3, cluster 5, and cluster 8:

FAT table:
  Cluster 0: [Reserved]
  Cluster 1: [Reserved]
  Cluster 2: [0x00000000] ← Free cluster
  Cluster 3: [0x00000005] ← File 1 → Next cluster is 5
  Cluster 4: [0x00000000] ← Free cluster
  Cluster 5: [0x00000008] ← File 1 → Next cluster is 8
  Cluster 6: [0x00000009] ← File 2 → Next cluster is 9
  Cluster 7: [0x00000000] ← Free cluster
  Cluster 8: [0x0FFFFFFF] ← File 1 → End of chain (EOF)
  Cluster 9: [0x0FFFFFFF] ← File 2 → End of chain (EOF)
  ...

Cluster chain of file 1: 3 → 5 → 8 → EOF
Cluster chain of file 2: 6 → 9 → EOF
```

When reading file 1, the FAT32 driver does this loop:

```c
cluster = file->start_cluster;  // Get the starting cluster number 3 from the directory entry
while (cluster < 0x0FFFFFF8) {
    read_cluster(cluster, buffer);
    cluster = fat[cluster];     // Find the next cluster number from the FAT table
}
```

Simple, intuitive and efficient. On disk, the beauty of this linked list structure is that files do not need to be stored contiguously. You can scatter a large file in every corner of the disk, as long as the chain in the FAT table is continuous.

**Level 3: Directory entries, bridges between names and locations**

A directory is also a "file", a linked list of 32-byte entries:

```c
// FAT32 directory entry (short filename version)
struct fat32_dir_entry {
    uint8  name[11];         // 8.3 Format file name
    uint8  attr;             // Properties: read-only/hidden/system/volume/directory/archive
    uint8  reserved;
    uint8  create_time_tenth;
    uint16 create_time;
    uint16 create_date;
    uint16 access_date;
    uint16 first_cluster_hi; // The high 16 bits of the starting cluster number
    uint16 modify_time;
    uint16 modify_date;
    uint16 first_cluster_lo; // The lower 16 bits of the starting cluster number
    uint32 file_size;        // File size (bytes)
};
```

Each file/subdirectory corresponds to a directory entry. The most critical information in the directory entry is `first_cluster_hi` and `first_cluster_lo`, which together are the starting cluster number of the file. After getting this cluster number, you can go to the FAT table and read down the linked list.

## The elegance of FAT - and its countdown to death

The design of FAT is extremely elegant on the disk. But on Flash, it's a suicide device that targets Flash's weakness precisely.

Let’s take a look at the simplest file modification operation, modifying one byte in the file. What will happen under the combination of FAT+Flash:

```
Modify 1-byte FAT nightmare
=======================

Scenario: File report.txt, size 10KB, stored in cluster 3→5→8 chain (4KB cluster)
Operation: Modify the first byte of the file from 'H' to 'h'

Step 0: The application layer calls write(), offset 0, length 1, data 'h'

Step 1: The file system finds the starting cluster number of the file (cluster 3)
        → Check the chain of cluster 3 from the FAT table: 3→5→8→EOF

Step 2: Read the sectors corresponding to cluster 3
        → Modify the first byte in the buffer 'H'→'h'

Step 3: Write back the sector corresponding to cluster 3 ← Here is the key:
        If the physical block where this sector is located has not been erased:
        A. Erase the physical block (containing the entire 4KB sector of cluster 3)
           ← NOR 4KB sectors typically 50–200ms; NAND blocks ~2–5ms
        B. Program the buffer data back into the physical block
           ← NOR page programming takes about 1.5ms (per page)
        
Step 4: The file size has not changed, but the "last modified time" in the directory entry needs to be updated.
        → The sector where the directory entry is located needs to be modified by 2 bytes (timestamp field)
        
Step 5: Erase the sector where the directory entry is located → Program the new directory entry data
        ← Another wipe!
        
Total cost:
  1 byte modification
  → 2 erases (1 for data sectors + 1 for directory entry sectors)
  → Burn one P/E Cycle for each erase
```

**You modified 1 byte, triggered at least 2 erases, and burned 2 P/E cycles. **

If an application modifies a file once per second (such as syslog writing), there are 86,400 directory entry sector erases per day. The life of a sector of NOR Flash is 100,000 P/E cycles.

```
86,400 times/day ÷ 100,000 times life = 0.864

The directory entry sector was burned in 1.16 days.
```

That's not the worst. There are usually two copies of the FAT table (FAT1 and FAT2), which are identical backups. But the problem is, they are on the same flash bus, usually at adjacent physical addresses. ** When FAT1 is burned to death, FAT2 is often almost there. Your "redundancy" won't save you.

## Heat island effect in FAT area

The FAT table is a "hot area", similar to the heat island effect in a city. Most data writing is scattered (different files, different locations), but the modification of the FAT table is concentrated on several of its sectors. This creates a high concentration of Flash wear:

```
Wear concentration effect in FAT zone
=======================

                    Number of wear
                    ========
Boot Sector: ████ 3500 times
FAT1 Sector 0: █████████████████████████████████████ 98,000 times ← Nearly dead
FAT1 Sector 1: ████████████████ 42,000 times
FAT1 Sector 2: █████ 15,000 times
FAT2 Sector 0: █████████████████████████████████████ 97,500 times ← Nearly dead
Root Dir: ███████████ 30,000 times
Data Cluster 3: ██ 5400 times
Data cluster 5: █ 800 times
Data cluster 8: █ 1200 times
...
Data cluster 999: █ 3 times ← Hardly ever written!

Health disparity: 98,000 ÷ 3 = 32,667 times the imbalance
```

How serious is this imbalance? **On the same Flash chip, the FAT sector may have been erased 98,000 times (nearly dead), while the last data cluster has only been erased 3 times (almost new). **

But the file system doesn't know that. All it knows is "this sector belongs to the FAT table and I need to modify it". It continues to send erase-program instructions to the FAT sector. The driver layer will not prevent it. It does not know "this sector is dying", it only knows "execute user commands".

It wasn't until the 100,001th erase that a certain floating-gate transistor finally became unprogrammable. Data writing failed. The FAT table is damaged. **The entire file system crashes. **

It's not because the data area is full, it's not because there are too many files, it's not because of a power outage. It's just that one sector of the FAT table, that is, the sector that was overused, has expired.

## Lowercase amplification: The mathematical curse of FAT

The problem with FAT is not just "hot area concentration". There is also a more hidden problem, namely **Small-Write Amplification**.

In FAT, any attribute change of a file, even the modification time or the content of one byte, requires updating the FAT entry. The minimum writing unit of the FAT table is the entire sector. If your sector is 4KB (4,096 bytes) and a FAT entry is only 4 bytes (FAT32):

```
Lowercase amplification = sector size ÷ entry size × number of modifications
         = 4,096 ÷ 4 × 1
         = 1,024 times

In order to modify the 4-byte FAT entry,
You need to erase and rewrite the entire 4KB sector.
Physical writes = 1,024 times logical modifications.
```

If you consider that there are two copies of the FAT table (FAT1 and FAT2), and each modification needs to update both at the same time, the write amplification will be doubled:

```
Lowercase enlargement of the double FAT table:
  Modify 1 FAT entry (4 bytes)
  → Erase+Rewrite FAT1 sector (4,096 bytes)
  → Erase+Rewrite FAT2 sector (4,096 bytes)
  Physical write = 8,192 bytes
  Logical modification = 4 bytes
  Write amplification = 8,192 ÷ 4 = 2,048 times
```

**To modify a 4-byte FAT entry, you actually write 8192 bytes to Flash. The write amplification is 2048 times. **

This is not an extreme situation. Consider an embedded ECU scenario: the system has a 100-byte "running status" file that is written once per second. Each write:
- Original data write amplification: 100 bytes of content are modified, but a whole block (4KB) must be erased → write amplification 40 times
- Metadata write amplification: changing a 4-byte field may also trigger the erasure-rewriting of a sector; the multiple depends on the sector size and write path
- **Total write amplification > 2088x**

One write per second, 86,400 seconds a day:
- Effective writes: 100B × 86,400 = 8.64 MB/day
- Physical writes: 8.64 MB × 2,088 ≈ 18 GB/day
- Your 512KB NOR Flash will be completely written more than 35,000 times in one day

**Your Flash will die within a day. **

## If FAT is so bad, why are USB drives still in use?

You may ask: If FAT is so miserable on Flash, why are USB drives, SD cards, and CF cards all over the world formatted as FAT32?

The answer has three words: **FTL (Flash Translation Layer)**.

Consumer-grade Flash storage devices (USB drive, SD card, SSD) have a microcontroller inside that runs FTL firmware. FTL inserts a layer of logical-physical mapping between FAT and physical NAND:

```
FTL isolation layer for consumer flash storage
=======================

Your FAT32 file system:
  "Write these 4 bytes to FAT sector 5"
        ↓
FTL controller (running on the ARM core inside the Flash chip):
  "Received write request for logical sector number 5"
  "Sector 5 is currently mapped to page 3 of physical block A"
  "Allocate a new physical block B"
  "Write new data to page 0 of block B"
  "Copy other valid data in block A to block B"
  "Update mapping table: logical sector 5 → physical block B"
  "Mark block A for recycling"
  "Notify you that writing is complete"
        ↓
Your FAT32 file system:
  "Thank you, I had no idea you were doing this behind your back."
```

**FTL uses Copy-on-Write and wear leveling to shoulder all the original sins of Flash for FAT. **

Your USB flash drive is not what you imagined. Your FAT32 runs directly on NAND. Between FAT32 and NAND, there is a "miniature embedded operating system" that you can't see, desperately doing off-site updates, garbage collection, wear leveling, and bad block management.

This is why you can use FAT32 on a USB flash drive but not on bare NOR Flash, because bare NOR Flash does not have FTL. You must be responsible for everything yourself. **

Naked NOR Flash control in embedded systems, that is, a control method that directly operates physical addresses without going through FTL, is exactly the problem that KnotFS wants to solve.---

## The Fable of FAT: A system designed for one medium, dies on another

The tragedy of FAT is not a design error. Its design in 1977, on an 8-inch floppy disk, was perfect. The media at that time allowed in-place modification, no erasure restrictions, and no concept of wear. The structure of FAT (Boot→FAT→Root→Data) is mapped to the physical layout of the floppy disk (Track 0→FAT Area→Directory Area→Data Area), achieving optimal seek efficiency.

**The problem is that Flash is not a floppy disk. **

Design assumptions from 1977 are no longer valid on 2026 media. This is not a failure of design, this is a fundamental incompatibility of physics.

```
Core assumptions of FAT design vs Flash physical reality
=======================

FAT assumes Flash physical reality
────────────────────────────────────────────────
Can be modified in place → ✗ No, only 1→0
No need to erase before writing → ✗ Must erase before writing
The granularity of reading and writing is the same → ✗ Read = byte, write = block, erase = sector
The media will not wear out → ✗ P/E Cycle 100,000 times
All sectors have the same lifespan → ✗ Concentration of hot areas leads to early death
Can "modify a byte" → ✗ Modify = erase + rewrite the entire sector
Dual copies of the FAT table = high reliability → ✗ If both copies are on the same physical chip, they will both die.
```

Any one of these seven incompatibilities is enough to make FAT perform poorly on Flash. The seven factors working together directly make it a compatibility disaster for Flash.

## What KnotFS learned from the FAT failure

Since FAT cannot survive on bare Flash, KnotFS must take a completely different path. From the failure of FAT, we can conclude three iron rules that must be adhered to:

```
Lessons from FAT → Countermeasures for KnotFS
=======================

Lesson 1: Don’t have concentrated hot spots (FAT table)
  → KnotFS: metadata decentralized storage
    - Superblock uses Log Append instead of in-place update
    - File Table is embedded in Superblock (nodes[8]), and dual copies are guaranteed by SB dual slots
    - No separate "allocation table" - use free_map + SB Log to record mapping

Lesson 2: Don’t modify anything in place
  → KnotFS: System-wide Copy-on-Write
    - Data block: CoW to newly allocated block
    - Metadata: CoW is implemented through Log Append
    - Indirect block: CoW (modified pointer bits are different)
    - There is no "in-place modification" operation in the entire system

Lesson 3: Don’t let small write amplification get out of hand
  → KnotFS: Log-Structured metadata
    - A metadata modification = appending an 8-16 byte log record
    - No need to erase entire metadata sector
    - Write amplification close to 1:1 (metadata level)
    - The data layer depends on the efficiency of GC
```

The cause of FAT's death was "the design of a data structure that heavily relies on in-place modification on a medium that cannot be modified in place." The antidote to KnotFS is: "Completely accept the physical reality that cannot be modified in place, and use log append and Copy-on-Write to adapt to it."

This is a survival necessity, not a design choice.

FAT taught us one thing: on Flash, you can't "modify" anything, you can only "append". This insight leads directly to a landmark paper in 1992, Rosenblum and Ousterhout's "Log Structured File System" (LFS). LFS puts forward a bold idea: **turn the entire file system into an infinite log stream. All writes are appended to the end of the log. Never overwrite old data. **
