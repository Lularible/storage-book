# 4.5 Block Allocator: Lookahead and Wear Leveling

## How do you find an open space on a 4MB Flash?

Imagine you are inside LittleFS. The CTZ jump table has just decided to append a data block. It calls `lfs_alloc(lfs, &new_block)` and says: "Give me a free block."

You now have 1024 4KB blocks. Some of them are already occupied by directories and data, and some are free. You have to work with bounded RAM (can't scan 1024 blocks and build a 1024 bit bitmap, wait, what is 1024 bits? 128 bytes. But what if it's 8192 blocks? 1024 bytes. What if it's 131072 blocks (512MB)? 16KB.) In short, LittleFS can't make assumptions about how small the device is. It must provide an O(1) memory allocation scheme for arbitrarily large devices.

**What are your options?**

Option A: Maintain a free block bitmap on disk. It is read every time it is allocated and updated every time it is released.
→ Problem: Bitmap updates may be interrupted on power loss, resulting in "allocated blocks being recorded as free" (block leak) or "free blocks being recorded as allocated" (permanent loss of space).

Option B: Scan the entire disk once during mount and build an in-memory bitmap.
→ Problem: RAM usage increases linearly with device size, violating the bounded RAM principle. And scanning the entire disk at once may take several seconds on large devices.

Option C: Do not maintain free block information at all. Each time a free block is needed, the entire file system tree is traversed, all referenced blocks are found, and the rest are free. Choose one from scratch each time.
→ Problem: O(n²) allocation time, unacceptable on large devices.

**LittleFS chose option D, the lookahead buffer.**

---

## Lookahead: a window that slides over free blocks

The core idea of Lookahead is: **Use a fixed-size bitmap, such as 16 bytes (128 bits), to cache the free/occupied status of the "current area". When the free blocks in this area are used up, the file system is scanned to find the next area, the bitmap is updated, and allocation continues.**

```
Lookahead Buffer working instructions
=========================================================

Devices (128 blocks, 0 indicates free, 1 indicates occupied):
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│1 │0 │1 │1 │1 │0 │0 │1 │0 │1 │0 │0 │1 │0 │1 │0 │0 │0 │1 │0 │ ...
└──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘
 \____________________/ \____________________________/
   lookahead bitmap The area that has not yet been scanned
   (32 bits = tracking 32 blocks)
```

```c
// lookahead structure in lfs_t
struct lfs_lookahead {
    lfs_block_t start;       // Starting block number of the current window
    lfs_block_t size;        // How many blocks are left in the window to check?
    lfs_block_t next;        // next position within window
    lfs_block_t ckpoint;     // The number of blocks checked since the last checkpoint
    uint8_t *buffer;         // Pointer to bitmap buffer
};
```

Each bit of the lookahead bitmap corresponds to a physical block. "0" means the block is free (not referenced by the file system), "1" means the block is occupied. When you need to allocate a free block, scan the bitmap starting at position `next` and find the first bit with a value of 0.

Example running on a 128-block (512KB) device with a 16-byte (128-bit) lookahead buffer:

```
boot... lookahead:
                fs blocks: fffff9ffffffffffffffffffff0000
scanning... lookahead: fffff9ff ← Scan to find a batch of free blocks
                fs blocks: fffff9ffffffffffffffffffff0000
alloc = 21 lookahead: fffffdff ← allocated block 21
                fs blocks: fffffdffffffffffffffffffff0000
alloc = 22 lookahead: ffffffff ← allocated block 22
                fs blocks: ffffffffffffffffffffffffff0000
scanning... lookahead: fffffffe ← Move the window forward and rescan
                fs blocks: ffffffffffffffffffffffffff0000
alloc = 63 lookahead: ffffffff ← allocated block 63
                fs blocks: ffffffffffffffffffffffffffff0000
scanning... lookahead: ffffffff ← Scanning...
scanning... lookahead: ffffffff ← Continue scanning
scanning... lookahead: ffff0000 ← last paragraph
alloc = 112 lookahead: ffff8000
                fs blocks: ffffffffffffffffffffffffffff8000
```

When the lookahead window runs out of free blocks, `lfs_alloc_scan` is called, and it traverses the entire file system to mark which blocks are occupied in the next scan window. The window continuously slides forward on the device, forming a circular scanning pattern.

## lfs_alloc: The complete process of allocating a block

```c
// lfs.c:666-715 — Complete logic of lfs_alloc
static int lfs_alloc(lfs_t *lfs, lfs_block_t *block) {
    while (true) {
        // 1. Find free blocks in the current lookahead window
        while (lfs->lookahead.next < lfs->lookahead.size) {
            if (!(lfs->lookahead.buffer[lfs->lookahead.next / 8]
                    & (1U << (lfs->lookahead.next % 8)))) {
                // Found it! This block is free
                *block = (lfs->lookahead.start + lfs->lookahead.next)
                        % lfs->block_count;

                // Find the next free block location in advance (optimize subsequent allocations)
                while (true) {
                    lfs->lookahead.next += 1;
                    lfs->lookahead.ckpoint -= 1;

                    if (lfs->lookahead.next >= lfs->lookahead.size
                            || !(lfs->lookahead.buffer[lfs->lookahead.next / 8]
                                & (1U << (lfs->lookahead.next % 8)))) {
                        return 0;
                    }
                }
            }

            lfs->lookahead.next += 1;
            lfs->lookahead.ckpoint -= 1;
        }

        // 2. Check whether the entire device has been scanned
        if (lfs->lookahead.ckpoint <= 0) {
            LFS_ERROR("No more free space 0x%"PRIx32,
                    (lfs->lookahead.start + lfs->lookahead.next)
                        % lfs->block_count);
            return LFS_ERR_NOSPC;
        }

        // 3. The current window is used up and the next window needs to be scanned.
        int err = lfs_alloc_scan(lfs);
        if(err) {
            return err;
        }
    }
}
```

The `lfs_alloc_scan` implementation shows how the lookahead window moves:

```c
// lfs.c:641-662 — lfs_alloc_scan: fill lookahead buffer
static int lfs_alloc_scan(lfs_t *lfs) {
    // Move the lookahead window to the next location
    lfs->lookahead.start = (lfs->lookahead.start + lfs->lookahead.next)
            % lfs->block_count;
    lfs->lookahead.next = 0;
    lfs->lookahead.size = lfs_min(
            8*lfs->cfg->lookahead_size,     // The maximum number of blocks that a bitmap can track
            lfs->lookahead.ckpoint);         // But it cannot exceed the number of remaining blocks

    // Initialize to all 0s (all free), then mark occupied blocks
    memset(lfs->lookahead.buffer, 0, lfs->cfg->lookahead_size);

    // Traverse the entire file system tree and mark occupied blocks
    int err = lfs_fs_traverse_(lfs, lfs_alloc_lookahead, lfs, true);
    if (err) {
        lfs_alloc_drop(lfs);
        return err;
    }

    return 0;
}
```

`lfs_alloc_lookahead` is a callback function that marks "1" in the lookahead bitmap for each block occupied by the file system:

```c
// lfs.c:627-637 — mark occupied blocks
static int lfs_alloc_lookahead(void *p, lfs_block_t block) {
    lfs_t *lfs = (lfs_t*)p;
    lfs_block_t off = ((block - lfs->lookahead.start)
            + lfs->block_count) % lfs->block_count;

    if (off < lfs->lookahead.size) {
        lfs->lookahead.buffer[off / 8] |= 1U << (off % 8);
    }

    return 0;
}
```

**Traversal overhead:** Each time `lfs_alloc_scan` will call `lfs_fs_traverse_` to traverse the entire file system tree, including metadata pairs of all directories and CTZ jump tables of all files. The complexity of this traversal itself is O (number of blocks used). But because the lookahead window is filled with multiple free blocks at once, the amortized cost of each traversal is: O (number of blocks used / number of blocks that the lookahead can track). For a typical configuration (lookahead_size=16 bytes → 128 bits, the device has 1024 blocks), one scan fills 128 blocks of information, requiring only one full scan every 128 allocations.**For daily use on small devices, this usually means only one or two scans are required.**

## checkpoint mechanism: prevent infinite loops

Consider a boundary case: if the file system is almost full and `lfs_alloc_scan` cannot find a free block every time, will `lfs_alloc` keep scanning in circles until the end of time?

The answer is no, because there is a `ckpoint` (checkpoint) counter.

```c
// lfs.c:614-616 — Set checkpoints
static void lfs_alloc_ckpoint(lfs_t *lfs) {
    lfs->lookahead.ckpoint = lfs->block_count;
}
```

`lfs_alloc_ckpoint` is called before a complete, wait-free sequence of allocation operations begins. It sets `ckpoint` to the total number of blocks. Each time a block is scanned, `ckpoint` decreases by 1. If `ckpoint` drops to 0, it means that the lookahead has turned around and there are no free blocks, and `LFS_ERR_NOSPC` (insufficient space) is returned.

This ensures that the allocator does not spin infinitely. Even if the disk is full, it will take at most one scan before explicitly reporting an error.

## Wear Leveling: Hidden Benefits Hidden in the Dispenser

LittleFS's wear leveling is **statistical dynamic wear leveling**. It does not actively track the number of erasures of each block (which requires storing erasure counts by blocks, at the cost of O(n) memory), but uses the natural randomness of the allocation pattern to approximate a uniform distribution.

Specifically:

**1. Linear loop allocation (during device power-up).**

The lookahead window moves in a linear loop across the device. Each time `lfs_alloc_scan` advances the window a certain distance. This means that within a run, blocks are allocated in physical order, block 0, block 1, block 2... until wrapping around. This already provides a layer of wear distribution: hot spots are not concentrated in one area.

**2. Random starting offset (on each mount).**

If allocation starts from block 0 on every power-up, block 0 will experience more erases than block 1023. LittleFS solves this problem by determining a random starting offset at mount time:

```c
// Random seed generation on each mount (from DESIGN.md)
//
//             ┌────────┐ \                         probably random
//            ┌│metadata│ |                                ^
//            ││        │ +→ crc ───────────────────────→ xor
//            ││        │ |                                ^
//            │└────────┘ /                                │
//            └───│──│──┘                                   │
//             ┌─┘    └─────────────────────────┐         │
//            │                                  │         │
//            │        ┌──────────────→ xor ────────────→ xor
//            │        │                 ^       │         ^
//            v       crc               crc      v        crc
//       ┌────────┐ \  ^   ┌────────┐ \  ^   ┌────────┐ \  ^
//      ┌│metadata│─│──│→│metadata│ │  │  ┌│metadata│ │  │
//      ││        │ └──┘  ││        │ └──┘  ││        │ └──┘
//      ││        │ │     ││        │ │     ││        │ │
//      │└────────┘ /     │└────────┘ /     │└────────┘ /
//      └──│──│──┘        └────│───┘        └──│──│──┘
```

**The seed comes from the CRC chain accumulation of valid commit CRCs during the mount process**, which reflects the metadata history.

The `seed` when mounted is set by `lfs_mount_` to the XOR value of the CRC of all traversed metadata blocks. Subsequently, `lfs_alloc` uses this `seed` to determine the starting position of the lookahead when it is first allocated.

**3. Metadata pair relocation based on block_cycles.**

In addition to dynamic allocation, LittleFS also relocates metadata pairs by revision count; it does not use a per-block erase counter, and it is not static wear leveling in the traditional sense.

When the metadata pair's revision count reaches an integer multiple of `block_cycles`, LittleFS will force relocate (relocate) the metadata pair to two brand new blocks. This prevents a frequently updated directory from erasing its metadata block.

```c
// lfs.c:1940-1947 — Check if relocation is required
static bool lfs_dir_needsrelocation(lfs_t *lfs, lfs_mdir_t *dir) {
    // If dir->rev+1 is a multiple of (block_cycles+1)|1, trigger relocation
    return (lfs->cfg->block_cycles > 0
            && ((dir->rev + 1) % ((lfs->cfg->block_cycles+1)|1) == 0));
}
```

`|1` is to ensure the divisor is odd and avoid boundary conditions. If `block_cycles` is set to 100, the divisor is actually 101; relocation occurs approximately every 101 revisions. This mechanism is very important for frequently updated metadata pairs such as the root directory.

## Bad block processing: detection + eviction

LittleFS's bad block handling strategy is "detection and eviction":

**Detect while writing:** When the caller requests verification and the program cache is flushed, `lfs_bd_flush` will read back the data and compare.

```c
// lfs.c:177-208 — validation in lfs_bd_flush
static int lfs_bd_prog(lfs_t *lfs,
        lfs_cache_t *pcache, lfs_cache_t *rcache, bool validate,
        lfs_block_t block, lfs_off_t off,
        const void *buffer, lfs_size_t size) {
    // ...
    if (validate) {
        // Read back for verification immediately after writing
        lfs_cache_drop(lfs, rcache);
        int res = lfs_bd_cmp(lfs, NULL, rcache, diff,
                pcache->block, pcache->off, pcache->buffer, diff);
        if (res != LFS_CMP_EQ) {
            return LFS_ERR_CORRUPT;  // Data mismatch → bad block
        }
    }
    // ...
}
```

**Expulsion:** In the upper code, jump to the `relocate` label after seeing `LFS_ERR_CORRUPT`. In this label, a new block is allocated, data is written to the new block, and the old block is abandoned and no longer referenced by the file system, naturally becoming a free block.

## Comparison with KnotFS block management

```
KnotFS block management vs LittleFS block management
===============================================================
Number of blocks: 16 (fixed) Theoretically unlimited (actually limited by device size)
Free block search Scan free_bitmap (O(n)) lookahead bitmap (O(1) amortized)
                    Only 16 blocks, low overhead necessary for large devices
Wear leveling Explicit wear_count array Statistical dynamic wear leveling
                    1 uint32 per block (64 bytes) No counter per block required
Block recycling is released during compaction. Garbage blocks are not actively recycled.
                    Via free_bitmap tag Via "drop on floor" strategy
Bad block processing not implemented write verification + automatic reallocation
===============================================================
```

KnotFS's block management is very simple as it only has 16 blocks. Maintaining a 16-bit free_bitmap and a 16×4 = 64-byte wear_count array in RAM is trivial. Scan 16 bits for each allocation, find the first free block, and then select the one with the smallest wear_count. This is simplifying the problem to the extreme.

The number of blocks faced by LittleFS may be 100 times or 1000 times that of KnotFS. It must provide acceptable allocation performance while maintaining O(1) memory. The lookahead solution is a subtle compromise, it's not the fastest, but it works on any device size, and the amortized performance is O(1) in most scenarios.

## The philosophy of garbage collection: Drop it on the floor

LittleFS's block recycling strategy can be summarized in one sentence: **Do not actively recycle garbage blocks.**

When a file is deleted, its CTZ jump table blocks and metadata pair blocks are not immediately "marked as free". They are just no longer referenced by any metadata pair, there is no path in the file system tree to reach them. In the normal course of COW operations, compaction naturally excludes blocks that are no longer referenced. The next time `lfs_alloc_scan` scans, these blocks will be considered free blocks because they are not referenced by the file system tree.

This is called the "drop it on the floor" strategy. Its benefits are:
- No need to maintain free list (avoiding power failure safety issues)
- The release operation is O(1) (does nothing)
- Bad blocks are naturally forgotten (as long as no one references it)

The price is: the deleted space will not be available immediately and must wait until the next round of lookahead scan passes through that area.

## A meditation on entropy

The entropy source of LittleFS uses CRC XOR to generate random seeds, which is a design that makes people smile.

Random numbers are a difficult problem in any computer system. This is especially true on embedded systems: there is no hardware RNG, no entropy pool provided by the operating system, no network timestamps. Although the state of the CPU registers after power-on is random, you cannot guarantee that the CRC will not depend on those initialization states after compilation.

LittleFS's solution is to use the file system's own data as an entropy source.  The CRC of each valid commit will be chained and accumulated into the seed. This value depends on the metadata history.

The philosophical implication of this design is: **The file system itself is its most reliable source of randomness because it "remembers" its own history.** The reason why a file system needs wear leveling is precisely because it has been used; and a used file system happens to carry the "usage traces" required to make wear leveling work.

This is a kind of bootstrapping elegance: the question creates its own answer. KnotFS's block allocator is much simpler than lookahead's: only 16 blocks, a `free_map` bitmap is enough, no sliding window required. The wear leveling of KnotFS is also simpler than that of LittleFS. `pick_lowest_wear` directly traverses all free blocks and selects the one with the smallest wear, without the forced relocation mechanism of block_cycles. LittleFS's lookahead is designed for the extreme constraints of "the number of blocks may be thousands, and the RAM is only a few KB"; KnotFS benefits from the small scale of the teaching scenario, the number of blocks is small enough to scan in full, and wear tracking does not require randomized starting offsets. The difference between these two designs once again illustrates: **The same problem, the same theoretical basis, and different constraints will produce completely different implementations.**
