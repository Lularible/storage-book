# 5.8 Copy-on-Write: Don't Retire the Old Book Until the New One Is Confirmed

The principle of Copy-on-Write has been fully discussed in Chapter 3: Never modify in place, write new data first, and then release the old data after confirmation. Here’s a look at the implementation of KnotFS.

## CoW’s two-phase agreement

The write operation of KnotFS is close to two-phase commit, but rollback on failure is not fully implemented and cannot be called a strict transaction. Think of it as a "commit protocol":

```
Phase 1: Data preparation
  ├── 1. Allocate new blocks (pick_lowest_wear, select the empty block with the smallest wear)
  ├── 2. Write new data to new block (fdev_write, simulate Flash programming)
  └── 3. The file entry in the memory points to the new block

Phase 2: Metadata implementation
  ├── 4. Record old block release in SB Log (LT_BITMAP, val=0)
  ├── 5. Record new block occupation in SB Log (LT_BITMAP, val=1)
  ├── 6. Compact: Write new SB content (including new file entry) into Flash
  └── 7. Compact is completed, the old block is returned in the memory bitmap; Flash submission is completed by the new SB
```

The atomicity guarantee of the core lies in the gap between Phase 1 and Phase 2: if power is lost after Phase 1 is completed but before Phase 2 is completed, SB still points to the old data. New blocks are only marked as used in the memory sb; the old SB may still see them as FREE after power loss, so they will be reallocated instead of "keep USED orphan blocks".

compact_write has set the sequence of the new SB to sb.sequence+1 before writing; as long as the new SB is completely written, mount will select it, even if compact_finish has not yet been executed.

Let's look at the initialization code for write operations in KnotFS:

```c
/* knotfs.c: ST_WRT_INIT — starting point for write operations */
case ST_WRT_INIT:
    nd = find_node(cur.name);
    oldcnt = 0;
    if (nd) {
      for (i = 0; i < nd->block_count && i < KNOTFS_DIRECT_BLKS; i++)
        oldb[i] = nd->blocks[i];
      oldcnt = nd->block_count;
      nd->size = 0; /* invalidate old entry so alloc_node won't skip it */
    }
    need = (cur.w_sz + KNOTFS_BLOCK_SIZE - 1) / KNOTFS_BLOCK_SIZE;
    if (need > KNOTFS_DIRECT_BLKS) {
      cur.result = ERR_TOO_MANY;
      cur.st = ST_ERR;
      return;
    }
    nd = alloc_node(cur.name);
    if (!nd) {
      cur.result = ERR_NO_NODE;
      cur.st = ST_ERR;
      return;
    }
    nd->size = cur.w_sz;
    nd->block_count = (uint32_t)need;

    scratch[SCR_OLD_CNT] = oldcnt;
    for (i = 0; i < oldcnt && i < KNOTFS_DIRECT_BLKS; i++)
      scratch[SCR_OLD_BLK(i)] = oldb[i];
    scratch[SCR_NEW_NEED] = need;
    subst = 0;
    cur.st = ST_WRT_ALLOC;
    return;
```

Pay attention to the subtleties in this paragraph: **The old block is recorded first, then the old entry is cleared, and finally the new entry is allocated.** The line `nd->size = 0` prevents `alloc_node` from skipping this slot, because in the implementation of `alloc_node`, the slot of `size == 0` is considered free:

```c
/* knotfs.c: alloc_node — Find the first free file entry */
static knode_t *alloc_node(const char *name) {
  for (uint32_t i = 0; i < KNOTFS_MAX_FILES; i++) {
    if (sb.nodes[i].size == 0) {
      memset(&sb.nodes[i], 0, sizeof(knode_t));
      {
        uint32_t l = 0;
        while (l < KNOTFS_NAME_LEN - 1 && name[l])
          l++;
        memcpy(sb.nodes[i].name, name, l);
        sb.nodes[i].name[l] = '\0';
      }
      return &sb.nodes[i];
    }
  }
  return NULL;
}
```

So the same file name can be kept, but the underlying layer is already a brand new knote_t. The old block number is safely stored in the `scratch[]` array, waiting to be released after the CoW is successful.

## Why is the old block not released immediately?

You may be thinking: When allocating new blocks, can't we just free the old blocks? Why do we have to wait until compact is completed?

The problem is with timing. If the old block is released when a new block is allocated, the old block in free_bitmap becomes FREE. If the power is cut off at this moment, the next time you mount, SB will display: the file entry points to the new block (but the new block data may be incomplete), but the old block has been marked as FREE in free_bitmap. When writing other files next time, pick_lowest_wear may select this "old bookshelf" and overwrite the data that could have been recovered.

The design goal is: the old block will not be released before the new SB is completely written. The current implementation is to mark free in the memory bitmap in advance and rely on compact to write SB to complete the submission on Flash. This is what KnotFS does in the ST_WRT_META phase:

```c
/* knotfs.c: ST_WRT_META — Release old blocks and record new blocks */
case ST_WRT_META: {
    log_reset();
    oldcnt = scratch[SCR_OLD_CNT];
    for (i = 0; i < oldcnt && i < KNOTFS_DIRECT_BLKS; i++) {
      uint32_t blk = scratch[SCR_OLD_BLK(i)];
      if (blk < KNOTFS_BLOCK_COUNT) {
        log_push(LT_BITMAP, (uint8_t)blk, 0);
        mark_free(blk);
      }
    }
    need = scratch[SCR_NEW_NEED];
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_COPY;
      cur.st = ST_ERR;
      return;
    }
    for (i = 0; i < need && i < KNOTFS_DIRECT_BLKS; i++)
      log_push(LT_BITMAP, (uint8_t)nd->blocks[i], 1);

    /* compact SB to persist file entries + log */
    compact_erase();
    comp_wait = true;
    cur.st = ST_WRT_META_FLUSH;
    return;
}
```

Here `log_push(LT_BITMAP, blk, 0)` releases the old block and `log_push(LT_BITMAP, nd->blocks[i], 1)` occupies the new block. Both log records are pushed into the memory buffer `log_buf[]`, and then written to Flash through the compact process.

## Compact: Copy the entire table of contents to new paper

The compact of KnotFS is to rewrite the entire SB rather than to incrementally update it. The current implementation is compact after each metadata operation, and the 50%/214 threshold is not enabled.

```c
static void compact_erase(void) {
  uint32_t tgt = inactive_sb_slot();
  fdev_erase(tgt);
}

static void compact_write(void) {
  memcpy(&compact_buf, &sb, sizeof(knot_sb_t));
  compact_buf.sequence = sb.sequence + 1;
  compact_buf.log_offset = SB_HEADER_SZ;
  compact_buf.log_count = 0;
  compact_buf.crc32 = sb_checksum(&compact_buf);

  uint32_t tgt = inactive_sb_slot();
  fdev_write(tgt, &compact_buf, 0, sizeof(knot_sb_t));
}

static void compact_finish(void) {
  sb.sequence++;
  sb.log_offset = SB_HEADER_SZ;
  sb.log_count = 0;
}
```

The entire compact has three steps: ① Erase the target slot (the inactive one of SB0 or SB1) ② Write the complete SB to that slot ③ `compact_finish` updates the sequence number in the memory to prove "changed to a new directory". The key here: **compact writes to inactive slots. If the power is cut off midway, the old SB in the active slot will not be affected in any way.** The next time you mount, the SB that passes the CRC check and has a larger sequence number will be selected. compact_write sets the sequence of the new SB to `sb.sequence + 1`, so the sequence of the new SB is 1 larger than the old SB. If the power failure occurs after the writing of the new SB is completed but `compact_finish` has not yet been executed, the new SB has been completely written into the Flash and the CRC check can pass (the sequence is larger), the mount will select the new SB. If the power failure occurs during the writing of the new SB and the new SB data is incomplete (CRC check fails), the mount will select the old SB (sequence is smaller but complete and valid). The file entry in the old SB still points to the old data. In either case, at least one complete copy of SB exists, which is the atomicity guarantee of the dual-slot Compact.

If compact is completed successfully, `sb.sequence` in the memory will be +1, and the SB with a larger sequence will win the next time it is mounted. The file entry in the new SB points to the new block, and the old block is marked FREE by Log. The old data is still in Flash, but it is no longer within the scope of any metadata reference. It has become an "empty bookshelf grid" that can be recycled.

At the same time, compact also completed another hidden operation: **Log clearing.** `compact_buf.log_count = 0` and `compact_buf.log_offset = SB_HEADER_SZ` means there is no log record on the new SB. All log changes accumulated before compact (bitmap changes, used_bytes updates) have been "solidified" into the SB field. This is the essence of log-structured metadata: log is the temporary storage area, and compact is persistence.

## The price of CoW: space amplification

CoW is not free. Writing a 1-byte file, KnotFS will also allocate an entire block (4096 bytes). Writing a 4097-byte file requires 2 blocks. The space wastage rate is close to 100% in the worst case (one entire block per file is wasted).

```
Space magnification example:
  File size | Number of allocated blocks | Actual usage | Waste ratio
  ──────────────────────────────────────────
  1 B | 1 block (4K) | 4,096 B | 99.98%
  100 B | 1 block (4K) | 4,096 B | 97.56%
  4,096 B | 1 block (4K) | 4,096 B | 0%
  4,097 B | 2 blocks (8K) | 8,192 B | 49.99%
  8,192 B | 2 blocks (8K) | 8,192 B | 0%
```

This is the natural price of block devices. In the production-level version, "indirect blocks" are used to store block pointers of large files to reduce space waste for small files. KnotFS does not have indirect blocks, but we have a direct block limit of 8 blocks (`KNOTFS_DIRECT_BLKS = 8`), which corresponds to a maximum file of 32KB.

## CoW or write in place? A fight that lasted for 40 years

In the history of file systems, the debate between CoW and in-place updates has lasted for decades:

```
Write in place (In-Place Update):
  Representative: ext2/3, FAT32, NTFS
  Advantages: no waste of space, write amplification = 1
  Disadvantages: metadata may be inconsistent during power outage, requiring fsck
  Classic accident: power outage while writing inode → file lost or directory damaged

Copy-on-Write:
  Representative: ZFS, Btrfs, WAFL, KnotFS
  Advantages: Strong atomicity, natural support for snapshots and version rollback
  Disadvantages: write amplification (modifying 1 byte may cause the entire block to be copied), fragmentation
  Classic scenarios: database, log file system, embedded Flash
```

For embedded NOR Flash, **CoW is the only correct option**. There are two reasons: First, NOR Flash can program 1 to 0, but to change 0 back to 1, it must be erased first; overwriting usually requires a complete block erase, and the bytes cannot be changed in place arbitrarily. Second, embedded devices face frequent power outages (car stalls, equipment loses power), and in-situ coverage is unacceptable in this environment.

KnotFS implements the block-level CoW of the happy path, and the rollback of allocation failure and power-off path have not yet been fully verified.> ⚠️ **Teaching Simplification Tips**: Here KnotFS chooses the simplified version of CoW of "full block copy + two-stage compact". The production-level solution will have more considerations at this point: ① `is_old_block()` protection mechanism, in the log replay stage after mount, marks all files that are blocked by any SB The old block referenced by Log is "to be released" and will not be reallocated by pick_lowest_wear unless confirmed by compact to prevent "orphan block accidental damage"; ② The `s_old_indirect_blocks[]` array tracks indirect blocks. When the file uses indirect blocks, the old indirect blocks also need to be delayed. KnotFS does not have indirect blocks so this simplifies this; ③ Separate file table (FT0/FT1), file for production-level solutions Entries are stored independently in file table blocks instead of SB. CoW metadata updates require compacting both SB and FT log systems.

## If you design

Now you understand the core idea of CoW. Try to answer: If a write operation allocates 2 new blocks, but the power is lost while writing the data of the second new block, what will happen the next time you mount?

Answer: SB points to old data (because compact has not been done yet). Among the two newly allocated blocks, the data of the first block has been written to Flash, and the second block may be partially written. But the problem is not big, because the old SB is still selected during the next mount, the file entry in the old SB still points to the old block, and these two "orphan blocks" are still marked as USED in the free_bitmap of the old SB (because they were marked in the log before compact). So they won't be reallocated, but their space will be wasted until the next write operation to the file frees them.

This waste of space in "orphan blocks" is acceptable. KnotFS's teaching Flash is 64KB; 512KB is the assumption for the production solution. Occasionally a few orphan blocks are acceptable. In contrast, if you choose to overwrite in place and lose a file, the cost will be much higher. The first principle of storage engineering: It is better to waste space than lose data.
