# 3.5 A Map of Embedded Flash File Systems

## There are six black boxes in front of you

Imagine a scenario: You are an embedded engineer and you have a product firmware submission next week. The product uses a 16MB SPI NOR Flash, running FreeRTOS and Cortex-M4. You need a file system.

You open GitHub. You search for "embedded file system flash". You see:

- **LittleFS**: produced by the ARM Mbed team, has been merged into the Linux mainline, and has Python binding
- **SPIFFS**: ESP8266/ESP32’s factory file system, so simple that it’s scary
- **FATFS**: The FAT you're familiar with, but ported to embedded. You know it won't fit bare Flash, but it has "compatibility"
- **YAFFS**: The old NAND file system, which has been running on the Linux kernel for 20 years
- **JFFS2**: The default file system of the Linux MTD subsystem, log-structured, but the mount is as slow as counting sand.
- **F2FS**: produced by Samsung, specially designed for high-capacity Flash, used by Android
- There are also **UBIFS**, **LittleFS-2**, **nx-ffs**...

You stare at the screen. Six black boxes. You don’t know which one to tear down.

This section is designed to help you dismantle it.

## A panoramic map

Let's start with a panoramic view. This table is a place you should not leave without making a decision.
| FS | Target media | Data structure | Wear leveling | Power loss safety | Code size | Minimum RAM |
|---|---|---|---|---|---|---|
| LittleFS | NOR/NAND | metadata pair, CTZ skhipu-list | dynamic | strong | ~14KB | ~1KB |
| SPIFFS | NOR | flat page index (no directories) | static | weak | ~15KB | ~4KB |
| FATFS | Disk/with FTL Flash | FAT table + directory tree | None | Weak | ~8KB | ~1KB |
| YAFFS2 | NAND (OOB area) | T-node tree, chunk-based | dynamic + static | medium | ~30KB | ~2KB |
| JFFS2 | NOR+NAND (MTD) | Pure log structure, jeb-based | Dynamic | Good | ~30KB | ~256B |
| F2FS | NAND SSD, eMMC/UFS | NAT (node address table), multi-segment log | Multiple (dynamic + static) | Strong | ~60KB | ~16KB |
| UBIFS | NAND (MTD UBI) | wandering tree, LEB-based | UBI provided (dynamic + static) | Strong | ~40KB | ~32KB |
| KnotFS | NOR, 64KB-8MB | Log+CoW hybrid, compact metadata | Dynamic | Strong (dual SB slots + Log playback) | ~6KB (ARM) | ~2KB |

Stop and look at this chart carefully. Behind every project choice, there is a story of blood and tears.

## LittleFS: A love letter to microcontrollersLittleFS is a work launched by the ARM Mbed team in 2017. Its design goal is a unique combination: **support NOR and NAND, but the RAM footprint should be reduced to the 1KB level. **

How is it done?

**Metadata Pair (metadata pair), two blocks support a file system. **

```
LittleFS Metadata Pair principle
=======================

┌────────────┐ ┌────────────┐
│ Metadata │ │ Metadata │
│ Block A │ │ Block B │
│ (version 5) │ │ (version 4) │
└────────────┘ └─────────────┘
    Valid old version

Update process:
  1. Read A and B, compare version numbers → A(5) > B(4) → A is a valid version
  2. Modify metadata in memory
  3. Write the modified metadata to B (overwriting the old version of B, and B becomes version 6)
  4. The next time you modify it, write A (A becomes version 7)
  5. Repeatedly

Why only use two blocks?
  - Extremely low RAM usage: only two blocks of metadata need to be cached in memory
  - Automatic distribution of wear: A and B are written alternately
  - Power-down safety: always keep at least one valid version
  - Disadvantage: logical space is limited to the size of two physical blocks
```

The file data of LittleFS uses **CTZ skhipu-list (Counting Trailing Zeros skhipu list)**, which is a chain structure that draws on the idea of B-tree. Its inode adopts a dynamic size design and "grows" layer by layer as the file increases:

```
LittleFS CTZ Skhipu-List structure
=======================

Small files (≤ 1 block):
  inode → [data block]
  Point directly to the data block, level 1

Medium/Large Files:
  inode → last data block
  The header of each data block stores the precursor pointer and CRC determined by ctz
  There is no separate "CTZ block"; pointers are scattered in the data block header
```

**The most exquisite design of LittleFS is its CRC check. **LittleFS's CRC mainly protects metadata commit and CTZ metadata; whether data blocks are verified block by block depends on the version and configuration.

```
LittleFS CRC check chain
=======================

inode:
  [File name│Size│CTZ structure│CRC] ← inode comes with CRC

Data block header:
  [skhipu pointers ... ][User data] ← CTZ pointers are scattered at the header of each data block

metadata commit:
  [tags ...][CRC] ← LittleFS mainly uses CRC to protect metadata commits

Reading path:
  Read inode/metadata → verify metadata CRC
  → Position along the skhipu pointer at the head of the data block
  → Whether data blocks are CRC-by-block depends on version/configuration
```

**LittleFS's CRC design allows it to run on NOR (NOR does not have built-in ECC) and also on low-quality NAND (some pages of NAND may be damaged). **

But LittleFS also has obvious costs:
- A single metadata pair is limited to two blocks; the entire file system can have many pairs, and the directory can also be chain-extended
- CTZ supports O(log n) random access; implementation is more complex than array indexing
- Directories are implemented by entries in metadata pairs

For a Cortex-M0 microcontroller with 4KB RAM, this is an elegant engineering trade-off.

## SPIFFS: rough but effective

SPIFFS (SPI Flash File System) was designed by Peter Andersson, and Espressif is widely used in the ESP8266/ESP32 SDK. It is the simplest and crudest among embedded file systems.

```
The core data structure of SPIFFS
=======================

SPIFFS index table (in RAM):
  File ID │ Start Page │ Size │ Attributes
  ────────────────────────
  0x0001 │ Page 3 │ 1024 │ Readable and writable
  0x0002 │ Page 12 │ 4096 │ Read only
  ...

Per physical page (256B or 4096B, depending on chip):
  ┌────────────────────┐
  │ Header (object ID, span_ix, length) │
  │ Data (remaining space) │
  └─────────────────────┘

Document spans multiple pages:
  File 0x0001:
    Page 3: [header: id=0x0001, span_ix=0] [data: 0~220 bytes] ← 220B
    Page 7: [header: id=0x0001, span_ix=1] [data: 221~440 bytes] ← 220B
    Page 15: [header: id=0x0001, span_ix=2] [data: 441~660 bytes] ← 220B
    Page 21: [header: id=0x0001, span_ix=3] [data: 661~880 bytes] ← 220B
    Page 27: [header: id=0x0001, span_ix=4] [data: 881~1024 bytes] ← End
```

SPIFFS has no directory. It uses 16-bit object IDs and page/object indexes; "finding a file" usually requires scanning/caching object headers.

```
SPIFFS search process:
  lookup("config.txt"):
    1. Locate the object_id corresponding to "config.txt" in the object/page index (indicating 0x003F)
    2. Search object_id=0x003F in the lookup table in RAM → Found: starting page = page 3
    3. Read page 3 → decode header → get data

Advantages:
  Lookup usually requires index table/object header scan + Flash read
  So simple that it couldn’t be simpler

Price:
  The index of all files must be fully loaded into RAM
  For large Flash (e.g. 16MB), the index table may occupy a lot of RAM
  No directory structure → filenames are flat
  Dynamic wear dispersion: via GC/free page allocation; no active cold data relocation
```

SPIFFS proves: **Sometimes the simplest solution is the most suitable solution. ** On a Wi-Fi microcontroller like the ESP8266 (only 160KB RAM, 4-16MB Flash, no MMU), you don't need a complex layered file system. All you need is a simple tool that can find the configuration files after reboot.

## YAFFS and JFFS2: Two Linux veterans

YAFFS (Yet Another Flash File System) and JFFS2 (Journaling Flash File System Version 2) are the oldest Flash file systems on the Linux kernel.

The design philosophy of **JFFS2** is "pure log", everything on disk is an entry appended to the log stream. This brings extremely high power-down safety, but it also brings **mount time nightmare**:

```
JFFS2 mount process
=======================

1. Scan the entire Flash from beginning to end
   → Read the header of each erase block
   → Identify valid data and junk data
   → Build in-memory inode tree

2. Scan time ∝ Total Flash capacity
   
   16MB NOR Flash: ~0.5 seconds (acceptable)
   128MB NAND Flash: ~5-10 seconds (barely)
   1GB NAND Flash: ~30-60 seconds (unacceptable)

3. This is the biggest reputation of JFFS2:
   "When the system starts, JFFS2 slowly counts the sand."
```

Another problem with JFFS2 is that its garbage collection (GC) is unpredictable. GC may be triggered at any time while the system is running, suspending all I/O operations. This is a problem for embedded devices that require deterministic response.

**YAFFS** (especially YAFFS2) is specially designed for NAND Flash and uses the OOB (Out-Of-Band) area of ​​NAND to store verification information. Its data structure is closer to traditional Unix FS (inodes are organized with T-node trees), but all updates are appended through the log.

```
YAFFS2 T-node tree
=======================

inode
  └── T-node (layer 0) → points directly to 16 chunks
       └── T-node (layer 1) → 16 T-nodes each pointing to the next layer
            └── T-node (layer 2) → ...

Each chunk = one NAND page (2KB~16KB)
The maximum file size is determined by the number of layers of the T-node
```

Both YAFFS and JFFS2 face the same embarrassment: **The Linux kernel community has turned its attention to UBIFS and F2FS. ** These two veterans are still in service in their respective areas of expertise (JFFS2 on small NOR, YAFFS on industrial-grade NAND), but the new design has covered all their usage scenarios.

## F2FS: Samsung’s highway for flash memory

F2FS (Flash-Friendly File System) is a log-structured file system designed by Samsung for high-capacity Flash storage (eMMC/UFS/SSD). It runs on Android and is used on hundreds of millions of devices.

The design sense of F2FS is completely different from that of small Flash file systems:

```
F2FS’s grand scale design
=======================

F2FS divides the entire volume into 6 areas:
  ┌──────────┬──────────┬─────────┬──────────┬──────────┬───────────┐
  │Superblock│Checkpoint│SIT │NAT │SSA │Main │
  │(2 copies) │ (CP area) │ Seg.Info │Node Addr │ Summary │Node/Data │
  └──────────┴──────────┴──────────┴───────────┴───────────┴─────────────┘

Core idea: separation of hot and cold
  - Hot data (frequently modified): placed in the log header (CURSEG)
  - Warm data (occasionally modified): assigned to hot/warm/cold log header by access mode
  - Cold data (almost unchanged): long-term stable area
  - The Node area and the Data area are separated → metadata and data with different access modes are scattered in different segments

Multiple log header mechanism:
  ┌─ Node log header (hot)─┐ ┌─ Data log header (hot)─┐
  │ [inode'] [inode'] │ │ [data'] [data'] │
  └───────────────────┘ └───────────────────┘

  GC is based on section/segment, and its scope of influence is not limited to a single log header.
```

F2FS's NAT (Node Address Table) is its most critical data structure. It is similar to LFS's imap and is a huge "inode ID → physical location" mapping table. NAT itself is also segmented and supports incremental updates.

```
F2FS NAT mapping
=======================

NAT: inode_ID │ physical block address │ status
       ──────────────────────────
       0x00001 │ 0x000A3F │ Valid
       0x00002 │ Invalid │ Deleted
       0x00003 │ 0x002B12 │ Valid
       ...

Every inode update:
  1. Write the new inode to the currently active segment of the Node area
  2. Update NAT entry: inode_ID → new physical address
  3. NAT updates are accumulated in batches (to reduce write amplification in the NAT area)
```

The design of F2FS is optimized for tens to hundreds of GB of Flash. It is not suitable for embedded MCUs, and the amount of F2FS code in the kernel state exceeds 60,000 lines.

## KnotFS: where it is on this map

So where is KnotFS on this map?

**It is not on any competitive dimension. **

```
KnotFS’ unique positioning
=======================

LittleFS: The goal is to "run the file system on Cortex-M0" (versatility first)
KnotFS: The goal is to "teach file system design on Cortex-R5" (understandability first)

SPIFFS: The goal is to "store configuration files on ESP8266" (simplicity first)
KnotFS: The goal is to "safely modify calibration data on the ECU" (security first)

FATFS: Targets "PC-compatible file exchange format" (compatibility first)
KnotFS: The goal is to "understand every line of code in the Flash file system" (teaching priority)

YAFFS: The goal is "industrial volume production reliability on NAND" (volume first)
KnotFS: The goal is to "achieve dynamic wear leveling + CoW power-down safety on 64KB Flash" (full functionality first)

JFFS2: Targets "Generic Journaling File System on Linux MTD" (history compatibility first)
KnotFS: The goal is to "disassemble the minimal implementation of log structure for readers" (minimum implementation first)

F2FS: The goal is to "optimize the flash memory performance of hundreds of millions of mobile phones" (scale first)
KnotFS: The goal is "16 blocks × 4KB engineering laboratory" (proof of principle first)
```

**KnotFS does not attempt to compete on performance, features or scale. Its purpose is to let you see every bone of the file system on a bare NOR Flash. **

Its 16 blocks, 4KB block size, compact metadata log, and dynamic wear leveling are all the result of careful consideration. They are designed to allow you to understand the core principles common to all Flash file systems on a system that is simple enough but realistic enough.

These principles are hidden in the flipping logic of metadata pairs in LittleFS, in the batch update of the NAT table in F2FS, and in the randomness of static wear leveling in SPIFFS. However, in KnotFS, they are deliberately exposed, given names, and given state machines.
