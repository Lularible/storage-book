# 5.12 CRC32: Trust, but Verify

## Every bit is a promise, but some promises expire

You write the superblock into Flash. 668 bytes (`sizeof(knot_sb_t)`), each bit is the result of your careful calculation: magic=0x4B4E4653, the sequence number is incremented, free_bitmap accurately marks the status of each block, and the 8 file entries contain the file information that the user spent time writing.

After 1 millisecond, the bit flipped. Maybe it's cosmic rays, maybe it's NOR Flash's read disturb, maybe it's just bad luck. A certain bit in SB changes from 0 to 1. This change is fatal to the file system. It may cause a block that was originally occupied to be suddenly marked as FREE. The next time `pick_lowest_wear` selects it, the user's data will be overwritten.

**What you need is "verify data is OK". **

CRC32 (Cyclic Redundancy Check) is a lightweight error detection code. It is not an encryption algorithm (anyone can forge a CRC), nor is it an error-correcting code (it cannot repair errors), but it can detect accidental corruption of data with a very high probability. For a 32-bit CRC, the probability of random corruption not being detected is 1/2³² ≈ 1/43 billion.


---

## Polynomial 0xEDB88320

The CRC32 polynomial used by KnotFS is exactly the same as the Ethernet, gzip, PKZIP, and PNG file formats:

```
Polynomial: 0xEDB88320 (reflected form)
Primitive polynomial: x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹
           + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1

Bit width: 32 bits
Initialization value: 0xFFFFFFFF
Final XOR value: 0xFFFFFFFF
Reflective I/O: Yes
```

Let’s look at the implementation of KnotFS:

```c
/* knotfs.c: k_crc32 — polynomial 0xEDB88320 */
static uint32_t k_crc32(const void *data, uint32_t len) {
  uint32_t c = 0xFFFFFFFFU;
  const uint8_t *p = (const uint8_t *)data;
  for (uint32_t i = 0; i < len; i++) {
    c ^= p[i];
    for (int j = 0; j < 8; j++)
      c = (c >> 1) ^ ((c & 1U) ? 0xEDB88320U : 0U);
  }
  return c ^ 0xFFFFFFFFU;
}
```

This implementation uses a bit-by-bit calculation method with O(n×8) complexity. For KnotFS, the amount of data to be verified is small (super block 668 bytes, each log record 8 bytes), and the bit-by-bit calculation is fast enough. But if you are doing CRC32 verification on large files in production-level deployment, you should use the lookup table method (256 uint32 lookup tables) to reduce the complexity to O(n).


---

## Two check functions: sb_checksum and log_checksum

KnotFS has two data structures that need to be verified: super block (knot_sb_t) and Log record (knot_log_t). The structures of the two check functions are the same. CRC32 is performed on the entire structure, but the crc32 field itself at the end of the structure is excluded:

```c
/* SB check: CRC32 over the entire SB, excluding the last field (crc32) */
static uint32_t sb_checksum(const knot_sb_t *sb) {
  return k_crc32(sb, sizeof(knot_sb_t) - sizeof(uint32_t));
}

/* Log record verification: CRC32 over the entire log_entry, excluding the last field (crc32) */
static uint32_t log_checksum(const knot_log_t *e) {
  return k_crc32(e, sizeof(knot_log_t) - sizeof(uint32_t));
}
```

Why exclude crc32 field? Because the crc32 field stores "check values ​​of other fields". If you include the crc32 field in the calculation, you will fall into a circular dependency, that is, the check value depends on the check value itself and can never match. This is standard practice in all data structures with checksums.

`sizeof(knot_sb_t) - sizeof(uint32_t)` is equal to 664 bytes (668 - 4). `sizeof(knot_log_t) - sizeof(uint32_t)` is equal to 4 bytes (8 - 4), and only the tag, blk, and val fields of the log record are verified.

## When verification occurs

**Opportunity 1: When mount selects SB. **

```c
/* knotfs.c: ST_MNT_SEL — Verify the CRC of two SBs when mounting */
case ST_MNT_SEL: {
    /* sb0 is the partial copy previously read from block 0 */
    bool ok0 = (sb0.magic == KNOTFS_MAGIC && sb0.crc32 == sb_checksum(&sb0));
    bool ok1 =
        (sb_alt.magic == KNOTFS_MAGIC && sb_alt.crc32 == sb_checksum(&sb_alt));
    if (!ok0 && !ok1) {
      cur.result = ERR_MNT_FAIL;
      cur.st = ST_ERR;
      return;
    }
    if (!ok0 || (ok1 && sb_alt.sequence > sb0.sequence)) {
      memcpy(&sb, &sb_alt, sizeof(sb));
      fdev_read(KNOTFS_SB1_BLK, tmp, KNOTFS_BLOCK_SIZE);
      cur.st = ST_MNT_RD_LOG;
    } else {
      memcpy(&sb, &sb0, sizeof(sb));
      cur.st = ST_MNT_REPLAY;
    }
    return;
}
```

Two checks are done here at the same time: **magic check** and **CRC check**. If both SBs pass magic+CRC, the one with the larger sequence number (updated copy) is selected. If only one passes, use the one that passed. If neither pass, the mount fails and error code -10 is returned. This means that the superblock information on Flash has been irretrievably damaged. For KnotFS's teaching environment, this means "formatting from scratch." For production-grade deployments, this means reporting unrecoverable media errors to the outside world.

**Opportunity 2: During log replay. **

> Note: In the current teaching implementation, `sb.log_count` is usually 0, and the normal life cycle rarely enters playback; the design path is shown below.

```c
/* knotfs.c: replay_log — Verify CRC one by one when replaying Log */
static void replay_log(void) {
  knot_log_t e;
  for (uint32_t i = 0; i < sb.log_count; i++) {
    uint32_t pos = SB_HEADER_SZ + i * LOG_ENTRY_SZ;
    memcpy(&e, tmp + pos, sizeof(e));
    if (e.tag == 0xFF)
      break;
    if (e.crc32 != log_checksum(&e))
      break;
    if (e.tag == LT_BITMAP) {
      if (e.val)
        mark_used(e.blk);
      else
        mark_free(e.blk);
    }
  }
}
```

log_replay reads log records one by one, and performs a CRC check on each record. If a record's CRC does not match, **replay stops immediately** (`break`). This means that all records after the corrupted record are discarded. This is a conservative strategy: rather lose some subsequent metadata updates than risk rewinding a corrupted record (which might incorrectly free or occupy blocks).

Also note `if (e.tag == 0xFF) break`, which is dealing with Flash-specific behavior. NOR Flash is all 1 (0xFF) after erasing. If a log_slot is 0xFF, it means that it has never been written. This is the end of the Log area and playback should be stopped. The order of checks and CRC checks in `tag == 0xFF` guarantees: **We will not try to do a CRC check on a full FF slot (that must be wrong). **

## Why CRC32 instead of a simpler checksum

You may ask: why not use a simple XOR checksum? It is computationally simpler and has a smaller constant factor; how much faster depends on the implementation and platform.

The answer is: **detection capability. **

```
XOR checksum (8 bits):
  Probability of false positive = 1/256 ≈ 0.39%
  For 10,000 operations, it is expected that 39 corruptions will be missed

CRC32 (32 bits):
  Probability of false positive = 1/2³² ≈ 2.33 × 10⁻⁸%
  For 10,000 operations, the expected number of missed detections ≈ 0

CRC16 (16 bits):
  Probability of false positive = 1/65536 ≈ 0.0015%
  Suitable for short data packets within 512 bytes
```

For superblocks (668 bytes), 32-bit CRC is the standard choice. A 16-bit CRC is not enough to cover 1000+ bytes of data, and as the data becomes longer, the probability of collision is not low enough. For 8-byte log records, 16-bit CRC is actually enough, but for code unification and simple implementation, KnotFS uses 32 bits for both SB and log.

## What happens when CRC fails

Let's simulate a specific scenario:

```
Scenario 1: CRC of SB0 fails, SB1 is normal
  →Select SB1 for mount and start normally
  → Users don’t feel any problem

Scenario 2: CRC fails for both SBs
  → mount returns -10
  → File system is unavailable
  → Need to format from scratch

Scenario 3: CRC of record 7 in Log replay fails
  → replay breaks at item 7
  → The bitmap updates of items 1~6 are applied
  → Article 7 and subsequent updates are lost
  → The file system may be in a consistent state but "missing the last few updates"
```

Scene 3 is the most subtle. It will not cause the mount to fail, but may cause **some file updates to be lost**. For example, if the user appends 500 bytes to the file, the corresponding log record is No. 7. If it is damaged during writing, the file will be restored to the size before appending after mounting. The user's data is not lost (the old data is still there), but the results of the most recent operation are lost.

This feature of "losing recent operations without destroying consistency" is exactly the design goal of log-structured file systems. **It is essentially an "append only, not destroy" data structure. In the worst case, only the tail log is lost and the existing metadata will not be destroyed. **

## Limitations of CRC

CRC32 is very capable of detecting random bit flips, but it cannot prevent all types of corruption:

1. **Systematic Damage**: If there is a problem with the Flash controller itself, it may flip all the bits of the data. CRC32 can't do anything about this kind of corruption, it can only detect "accidental" flips.

2. **Malicious Tampering**: CRC32 is not a cryptographic hash. Anyone can recalculate the CRC32 after modifying the data and make the check "pass". If your usage scenario requires tamper resistance, you should use SHA-256 instead of CRC32.

3. **Large-scale bit flipping at the end of silicon life**: When NOR Flash approaches the wear limit, the bit flip rate of a single block will increase sharply. The design assumption of CRC32 is "independent random bit flips", while flips at the end of wear are correlated (concentrated on certain bits).

For the teaching environment of KnotFS, CRC32 is sufficient to detect most random corruption, but it is not integrity proof and cannot cover systematic corruption or malicious tampering.> ⚠️ **Teaching Simplification Tip**: Here KnotFS only uses CRC32 to protect the metadata (SB and Log records). In addition to SB CRC, the production-level solution also has **file content CRC32 verification**. When mounting, the CRC32 is calculated block by block for the verifiable file and recorded in the trust table. If the block CRC of the file is inconsistent with the record during downloading, the file will be marked as `UNTRUSTED` and the download will be refused. In addition, its FT (File Table) block also has independent CRC32 check because FT and SB are separated. KnotFS cuts off file content verification (only retaining metadata CRC), and embeds file entries into SB to avoid the complexity of FT.

## Table lookup optimization of CRC32 (extracurricular reading)

The bit-by-bit CRC32 is processed 1 bit at a time, for a total of 8 inner loops. The standard practice in production-grade versions is to use a 256-entry lookup table, processing 1 byte at a time:

```c
/* CRC32 lookup table (polynomial 0xEDB88320) */
static const uint32_t crc32_table[256] = {
  0x00000000U, 0x77073096U, 0xEE0E612CU, 0x990951BAU, /* ... 256 entries ... */
};

static uint32_t crc32_fast(const uint8_t *data, uint32_t len) {
  uint32_t c = 0xFFFFFFFFU;
  for (uint32_t i = 0; i < len; i++)
    c = crc32_table[(c ^ data[i]) & 0xFF] ^ (c >> 8);
  return c ^ 0xFFFFFFFFU;
}
```

The lookup table occupies 1KB of ROM space. For embedded systems, 1KB is usually acceptable, and table lookup methods can often significantly improve speed, depending on the platform. Cortex-R5 usually uses table lookup software CRC, or uses the SoC's own CRC peripheral.

## If you design

Try to answer: If the CRC check of a log record is correct, but its `blk` field accidentally points to an already occupied block (for example, a bit flip on Flash changes the value of blk, but CRC32 is also "happened" to match at the same time), what will happen?

Answer: The probability of this happening is about 2.33×10⁻⁸%, but it does happen in extreme cases. If this occurs, log_replay will attempt to perform `mark_free` on an already occupied block, which will free up an innocent file's block. This can lead to a "double occupancy" problem, where two file entries point to the same block. Fortunately, since the tag field of the log record will also participate in the CRC check, and the tag has only two legal values ​​(LT_BITMAP=0, LT_USED=1), a flipped tag has a high probability of becoming an illegal tag value (skhipuped by `if (e.tag == LT_BITMAP)` in the replay), thus limiting the impact of the damage.

CRC32 ensures the verifiability of metadata at each mount. However, the daily operation of the file system does not only rely on mount. Every operation (write, append, delete) needs to be queued, scheduled, and executed in order. KnotFS does not have multi-threading or preemption. How does it achieve the non-blocking style of "submitting a request and returning immediately, without blocking, and polling for the results later"? The answer lies in its heartbeat, `knotfs_run()`, an event loop that only advances one state machine at a time, a request queue with only 4 slots, and a pipeline that will never be executed simultaneously. **Cooperative non-blocking scheduling, event loop. **
