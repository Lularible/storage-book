# 5.4 Dual Superblocks: The Catalog in Two Copies

## "Single source of truth" for all metadata

If the file system is compared to a library, Superblock is the **General Catalog of Library Collections**. It records:

-Which bookshelves are filled with books and which ones are still empty (`free_map`)
- Which bookshelf and which shelf each book is placed on (`nodes[]`)
- How many times each bookshelf has been browsed (`wear[]`)
- The current "version number" of the directory (`sequence`)

Without this general catalog, your library is left with rows of bookshelves. You know there are books on them, but you don’t know which one is "The Three-Body Problem", which one is "A Brief History of Time", and which one has been borrowed by readers.

The super block structure of KnotFS is as follows:

```c
// knotfs.c — Complete superblock definition
typedef struct {
  uint32_t magic;
  uint32_t version;
  uint32_t sequence;
  uint32_t log_offset;
  uint32_t log_count;
  uint32_t free_map; /* bitmask: 16 blocks -> fits in 1 uint32 */
  uint32_t wear[KNOTFS_BLOCK_COUNT];
  knode_t nodes[KNOTFS_MAX_FILES];
  uint32_t crc32;
} knot_sb_t; /* superblock (different from SimpleFS's simplefs_superblock_t) */
```

This structure is exactly 668 bytes (`sizeof(knot_sb_t)` is defined as `SB_HEADER_SZ` in the code):

```
knot_sb_t field size calculation
========================

magic 4 bytes (uint32_t)
version 4 bytes (uint32_t)
sequence 4 bytes (uint32_t)
log_offset 4 bytes (uint32_t)
log_count 4 bytes (uint32_t)
free_map 4 bytes (uint32_t)
wear[16] 64 bytes (16 × uint32_t)
nodes[8] 576 bytes (8 × 72-byte node_t)
crc32 4 bytes (uint32_t)
───────────────────────────
Total 668 bytes = SB_HEADER_SZ
```

It happens to be `4+4+4+4+4+4+64+576+4 = 668`. The remaining 3424-byte Log area plus a 4-byte tail (4096 - 668) is the Log append area.

## magic: Is this our library’s catalog or scrap paper?

Magic is how a file system identifies itself. The magic of KnotFS is `0x4B4E4653`; in big-endian byte order it is `K N F S`, and what you see in the memory dump of the little-endian machine is `S F N K`.

Why do you need magic? Imagine you take over a library. You walked into the catalog room and there was an open booklet on the table. How do you know if this volume is a catalog of the library's holdings and not a personal notebook left by a former administrator?

You open the book and look at the first four letters on the first page. If it is `KNFS`, you know that "this is a directory in KnotFS format" and you can continue reading. If the first page says `FAT1`, you know that this may be a FAT format directory used by the previous administrator in other libraries. You cannot understand its encoding and should refuse to mount it.

In the mount process, magic is the first filter:

```c
// knotfs.c — check magic and CRC during mount
bool ok0 = (sb.magic == KNOTFS_MAGIC && sb.crc32 == sb_checksum(&sb));
bool ok1 =
    (sb_alt.magic == KNOTFS_MAGIC && sb_alt.crc32 == sb_checksum(&sb_alt));
if (!ok0 && !ok1) {
  cur.result = ERR_MNT_FAIL;
  cur.st = ST_ERR;
  return;
}
```

If the magic of both catalogs is incorrect, either the library has never been cataloged, or it is not a collection managed by KnotFS at all, the mount will fail and error code -10 will be returned.

## sequence: Which directory is the latest version?

The Sequence is a monotonically increasing `uint32_t`. After each compact (rewriting the directory), the sequence is increased by 1:

```c
// knotfs.c — sequence increments after compaction ends
static void compact_finish(void) {
  sb.sequence++;
  sb.log_offset = SB_HEADER_SZ;
  sb.log_count = 0;
}
```

This serial number solves the core problem of double copies: **Two catalogs, which one is the latest version?**

If you walk into the catalog room and find two identical copies of the General Catalog of Collections on the table: one says "3rd Edition" on the cover, and the other says "7th Edition" on the cover. You don’t need to compare the inner pages, just look at the cover to know that you should trust the 7th edition.

When Mounting, KnotFS reads SB0 and SB1 and compares their sequences:

```c
// knotfs.c — select newer SB based on sequence
if (!ok0)
  memcpy(&sb, &sb_alt, sizeof(sb));
else if (ok1 && sb_alt.sequence > sb.sequence)
  memcpy(&sb, &sb_alt, sizeof(sb));
```

The logic is as follows:
1. If the magic of SB0 does not match or the CRC check fails → `ok0 = false` → use SB1
2. If the magic of SB1 does not match or the CRC check fails → `ok1 = false` → use SB0
3. Both are valid → compare sequences and choose the larger one
4. Both are invalid → mount failed

There is a subtlety: if the sequence of SB0 happens to be equal to SB1 (both are 0 when the format is first completed), the code will select SB0. This is not a bug. When the serial numbers are the same, the contents of the two are indeed the same. Whichever directory you choose will work.

## CRC32: Are there any missing pages in this catalog? CRC32 (Cyclic Redundancy Check) is the last line of defense for KnotFS data integrity. At the end of the super block (the last uint32_t field), the CRC32 value calculated for the other 664 bytes of the super block (`sizeof(knot_sb_t) - sizeof(uint32_t)`) is stored.

```c
// knotfs.c: SB CRC calculation (excluding the crc32 field itself)
static uint32_t sb_checksum(const knot_sb_t *sb) {
  return k_crc32(sb, sizeof(knot_sb_t) - sizeof(uint32_t));
}
```

The CRC32 polynomial is standard `0xEDB88320`:

```c
// knotfs.c — CRC32 calculation core
static uint32_t k_crc32(const void *data, uint32_t len) {
  uint32_t c = 0xFFFFFFFFU;
  const uint8_t *p = (const uint8_t *)data;
  for (uint32_t i = 0; i < len; i++) {
    c ^= p[i];
    for (int j = 0; j < 8; j++)
      c = (c >> 1) ^ ((c & 1U) ? 0xEDB88320U : 0U);
  }
  return c ^ 0xFFFFFFFFU;
}
```

What scenarios does CRC protect? Imagine that the administrator is transcribing a new version of the catalog, and when he reaches the 300th item, there is a sudden power outage. The pen stopped in mid-air, and the ink on the paper was not dry yet. After the call, you pick up this catalog: the first 299 items are the contents of the new version, the 300th item is only half written (maybe garbled), and the following items are still remnants of the old version.

If the administrator takes this "half new but not old" catalog to find books for readers, he may tell readers that "The Three-Body Problem" is on bookshelf No. 7, but in fact bookshelf No. 7 has been emptied long ago, because the administrator did clean bookshelf No. 7 before the power outage, but this cleaning record was not written into the catalog.

CRC will not prevent power outages from happening. But CRC allows you to **detect** that the directory is damaged after a call comes in, and then throw away the damaged one and use the good one.

This is why there are two copies of the directory. One book is half-written, and the other is most likely intact.

## mount process: 4-step state machine

The mounting process of KnotFS is an exquisite 5-step state machine (plus ST_OK, a total of 6 steps):

```
Mount state machine process
===================

┌──────────────────────┐
│ ST_MNT_RD_SB0 │ → fdev_read(SB0) Remove directory A from the bookshelf
│ (status=20) │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│ ST_MNT_RD_SB1 │ → fdev_read(SB1) Remove directory B from the bookshelf
│ (status=21) │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│ ST_MNT_SEL │ → Verify magic+CRC and choose the newer one
│ (status=22) │ → Compare sequence (fail if both copies are damaged)
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│ ST_MNT_RD_LOG │ → Read the Log area of active SB
│ (status=23) │
│ ST_MNT_REPLAY │ → replay_log() Replay the record on the note
│ (status=24) │ → mounted = true Revert changes that were not transcribed to the directory
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│ ST_OK │ Mounting successful, library is open for business
│ (status=90) │
└──────────────────────┘
```

Complete code:

```c
// knotfs.c — mount state machine
static void do_mount(void) {
  knot_sb_t sb0;

  switch (cur.st) {
  case ST_MNT_RD_SB0:
    fdev_read(KNOTFS_SB0_BLK, tmp, KNOTFS_BLOCK_SIZE);
    cur.st = ST_MNT_RD_SB1;
    return;
  case ST_MNT_RD_SB1:
    fdev_read(KNOTFS_SB1_BLK, &sb_alt, sizeof(sb_alt));
    cur.st = ST_MNT_SEL;
    return;
  case ST_MNT_SEL: {
    memcpy(&sb0, tmp, sizeof(knot_sb_t));
    bool ok0 = (sb0.magic == KNOTFS_MAGIC && sb0.crc32 == sb_checksum(&sb0));
    bool ok1 =
        (sb_alt.magic == KNOTFS_MAGIC && sb_alt.crc32 == sb_checksum(&sb_alt));
    if (!ok0 && !ok1) {
      cur.result = ERR_MNT_FAIL;
      cur.st = ST_ERR;
      return;
    }
    if (!ok0) {
      memcpy(&sb, &sb_alt, sizeof(sb));
      fdev_read(KNOTFS_SB1_BLK, tmp, KNOTFS_BLOCK_SIZE);
      cur.st = ST_MNT_RD_LOG;
    } else if (ok1 && sb_alt.sequence > sb0.sequence) {
      memcpy(&sb, &sb_alt, sizeof(sb));
      fdev_read(KNOTFS_SB1_BLK, tmp, KNOTFS_BLOCK_SIZE);
      cur.st = ST_MNT_RD_LOG;
    } else {
      memcpy(&sb, &sb0, sizeof(sb));
      cur.st = ST_MNT_REPLAY;
    }
    return;
  }

  case ST_MNT_RD_LOG:
    cur.st = ST_MNT_REPLAY;
    return;

  case ST_MNT_REPLAY:
    replay_log();
    mounted = true;
    cur.st = ST_OK;
    return;
  default:
    return;
  }
}
```

Note: `ST_MNT_RD_SB0` does not directly enter analysis after reading, it instead initiates `fdev_read(SB1)`. After completing `ST_MNT_RD_SB1`, enter `ST_MNT_SEL` for verification and selection.

Why should I read both books first and then compare them? Because administrators cannot assume which book is good. If you pick up Catalog A, flip through two pages and start using it, and then start using it, and Catalog B is actually a newer version, then you will lose all the bibliographic updates you made before the last closure.

The administrator will not make any decisions until both directories have been retrieved.

## Library metaphor: The catalog is in duplicate and locked in two cabinets.

In a regular library, there will not be only one copy of the general catalog of collections. The administrator will make two copies of the directory: one is locked in the **front desk directory cabinet** for daily reference; the other is locked in the **backstage safe** and is only activated after a fire or theft.

SB0 is the directory in the front cabinet, and SB1 is the backup in the back-end safe. In daily operations, KnotFS uses the currently active share (judged by sequence). When compact (rewriting a new directory) is required, the administrator will:

1. Copy the new directory to the cabinet opposite  (judgment of `inactive_sb_slot()`)
2. After the new directory is transcribed, it becomes the currently active directory.
3. The old one will automatically abdicate as "backup"

This cycle alternates: the front desk changes to the background → the background changes to the front desk → the front desk changes to the background again...

**Worst case scenario: Halfway through transcribing the new directory, the light goes out.**

The new directory in the cabinet at the front desk had just been copied to the 668th byte (the CRC had not yet been calculated), and the desk lamp went out. After the call came in, the administrator got up from the darkness, walked to the backend safe, and took out the backup directory. It was intact. Although the sequence was 1 smaller than the new version that had been transcribed halfway, all the books were correct.

The administrator took this backup directory and wrote a new one. The library remains open.

**This is the essence of double super blocks: not preventing disaster, but ensuring you can get back on your feet after it.**

>  ⚠️ **Teaching Simplification Tip**: The sequence of KnotFS is a simple `uint32_t`, and each compact adds 1. The production-level solution will use stricter comparison logic: when the sequences are equal, the CRC validity will also be compared as a tiebreaker. In addition, in addition to sequence, the super block of the production-level solution also has a `generation` field, which is used to distinguish the situation of "sequence number wraparound" (`uint32_t` wraps to 0 after writing to the maximum value). In the 64KB teaching scenario of KnotFS, the number of compactions is far less than 2³², so these edge cases are omitted.
