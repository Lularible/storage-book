# 2.2 NOR and NAND: Two Roads in the Storage World

## There are two roads in front of you, you must choose one

Imagine you are a storage architect sitting in front of a whiteboard in a conference room. Write your design constraints on the whiteboard: 512KB NOR Flash, 128 4KB blocks, Cortex-R5 MCU, FreeRTOS, AUTOSAR. You need to run a file system on this.

Ignoring the file system, first look at the difference between the NOR Flash in your hand and the NAND Flash used by the department next door.

Your colleague Xiao Li makes memory cards, and he uses 64GB TLC NAND. You ask him: What is the reading and writing speed? He said: sequential reading 500MB/s, sequential writing 200MB/s. You asked again: Have you checked the bad block table? He said: There are 2% bad blocks before leaving the factory, and new ones will be added over time. Anyway, ECC is used to correct errors.

You fell silent. On your Flash, a bad block means that 4KB is missing from the 512KB, 0.8% of the capacity is gone, and your file system was not designed with bad block management in mind.

**This is the fork in the road between NOR and NAND. One takes the reliability route and the other takes the cost route. **

Intel launched EPROM in 1971; Toshiba released NOR Flash in 1984, and NAND Flash at IEDM in 1987. At first, NOR Flash occupied the embedded market because its interface with the CPU was as simple as SRAM. In the late 1990s, Samsung and Toshiba greatly promoted the commercialization of NAND Flash because it was more suitable for large-capacity scenarios such as SSD and memory cards.

Since then, the two roads have gone farther and farther apart. Their differences are even greater than the differences between highways and railways.

## NOR Flash: Each unit has its own house number

The architectural name of NOR Flash comes from the "NOR" gate in Boolean logic. But don't let the name scare you, understanding its architecture requires just a gut feeling: **Each floating-gate transistor hangs directly on a bit line. **

```
NOR Flash cell array - each cell is independently addressable
============================================

                         Bit Line 0 Bit Line 1 Bit Line 2
                            │ │ │
  Word Line 0 ──────────────┼──────┬──────┼─────┬───────┼──────
                            │ ┌─┴─┐ │ ┌─┴─┐ │
                            └────┤FG ├─────┴────┤FG ├──────┘
                                 │ │ │ │
                             ┌───┤ ├────┬─────┤ ├───┐
  Word Line 1 ───────────────┼───┤ │ │ │ │ │
                             │ └─┬─┘ │ └─┬─┘ │
                             │ ┌─┴─┐ │ ┌─┴─┐ │
                             └───┤FG ├────┴─────┤FG ├───┘
                                 │ │ │ │
                             ┌───┤ ├────┬─────┤ ├───┐
  Word Line 2 ───────────────┼───┤ │ │ │ │ │
                             │ └───┘ │ └───┘ │
                             │ │ │ │ │
                             Source Lines (shared by sector block)
  
  Select a unit: WL0 + BL1 → the FG at the intersection is directly turned on/off → readout amplification
  This is random access. No need to read neighbors, no need to turn pages, just locate directly.
```

Key features:

- **The drain of each cell is independently connected to a bit line. **Which unit you want to read, the word line selects that row, the bit line selects that column, and the unit at the intersection outputs the signal directly without passing through any other unit.

- **Each byte has an address. **The interface between NOR Flash and CPU is the address bus and data bus. The CPU puts the address on the bus, and the data comes back tens of nanoseconds later. This is exactly the same interface as SRAM.

- **Using bytes as the minimum access unit. ** You don't need to "turn the page." Do you want to read the 456th byte? The address bus outputs 0x1C8, and the data comes back after 70ns. It's that simple.

This is why NOR Flash can do XIP (eXecute In Place). The CPU directly fetches instructions from Flash and executes them without copying the code to RAM first. In embedded systems, this means you can save valuable SRAM (Cortex-R5 usually only has a few hundred KB to a few MB of SRAM).

```
Connection between NOR Flash and CPU (simplified)
=============================

  CPU NOR Flash
 ┌──────────┐ ┌───────────┐
 │ │─── Address[18:0]──→│Address decoder │→ Select word line/bit line
 │ │ │ │
 │ │←── Data[15:0] ────│Sense amplifier │← Selected unit output
 │ │ │ │
 │ │─── /CE (Clip Selection) ────→│ │
 │ │─── /OE (output enable) ─→│ │
 │ │─── /WE (write enable) ──→│ │
 └──────────┘ └────────────┘
 
  The interface is like SRAM, not like a disk.
  CPU sends address → Flash returns data. No "read page" command is required.
```

This is the memory access pattern. The random read latency of NOR Flash is about 70–100ns; SRAM is about 1–10ns, which is about an order of magnitude difference. The CPU puts the address on the bus, and the instruction comes back dozens of nanoseconds later and is sent directly to the pipeline for execution.

This is why NOR Flash can do **XIP (eXecute In Place, in-place execution)**, the CPU directly fetches instructions from Flash and executes them without first copying the code to SRAM. In embedded systems, this means you can save valuable SRAM (Cortex-R5 is usually only a few hundred KB to a few MB), and the firmware image can run directly on Flash. Your car ECU, WiFi router, smart watch, their codes all run like this.Precisely because each byte is independently addressable, early microcontroller programmers could execute code in-place (XIP) on NOR Flash and erase sectors, reprogram and then jump to execution when updates were needed. This was completely unimaginable on NAND.

## NAND Flash: hawthorn on a bunch of candied haws

The architecture of NAND Flash is completely different. The name NAND comes from the way the cells are connected. The cells in each column are connected in series, like a string of candied haws.

```
NAND Flash cell array - a string of series structures
=========================================

                   Bit Line 0 Bit Line 1 Bit Line 2
                       │ │ │
     String Select ────┼──────┬─────────┼─────┬──────────┼──────
     (SST) │ ┌─┴─┐ │ ┌─┴─┐ │
                        └────┤FG ├────────┴────┤FG ├─────────┘
                             │ │ │ │
     Word Line 0 ────────────┤FG ├────────────┤FG ├────────────
                             │ │ │ │
     Word Line 1 ────────────┤FG ├────────────┤FG ├────────────
                             │ │ │ │
     Word Line 2 ────────────┤FG ├────────────┤FG ├────────────
                             │ │ │ │
     ... (a series of 32-128 units connected in series)
                             │ │ │ │
     Word Line 31 ───────────┤FG ├────────────┤FG ├────────────
                             │ │ │ │
     Ground Select ─────┼───┤ ├────┼────────┤ ├───┼────
     (GST) │ └───┘ │ └───┘ │
                        │ │ │ │ │
                        └─────┘ └──────────┘ └─────
                                Source Line (common ground)
  
  There are 32-128 units in a "string". To read one of them, all other units must be forced on.
  The sense amplifier then senses whether the selected cell is on or off.
```

The storage units of NAND Flash are not independent. A column of 32 to 128 floating-gate transistors is connected in series into a "String", which greatly saves the number of bit line contact holes and reduces the area of ​​each cell from NOR's ~10F² to ~4F² (F is the feature size). This is the physical reason why NAND is cheaper than NOR.

**But cheap has a cheap price. **

To read the value of a certain cell in a string, you must force all other cells to turn on and apply a high enough voltage (called Vpass, usually 6-8V) to their control gates so that the channels are all turned on regardless of whether there are electrons in their floating gates. Then, add Vread only to the control gate of the selected unit to see whether it is conducting or not.

```
NAND read operations
==============

  Selected unit: CG plus Vread (~3V) for this unit
  Other units: CG plus Vpass (~7V) → regardless of their floating gate status, all are forced on
  Sense amplifier: Sensitive total current → Determine whether the selected unit is on (1) or off (0)
  
  It's not "read one", it's "read a whole string" and only care about one of them.
```

**So you can't do random byte access on NAND. ** You have to read a whole page (usually 4KB to 32KB), and then pick the byte you need from the page. NAND addressing is based on **page (Page)**.

This is why NAND cannot be used for XIP. Are you going to execute code on NAND? First, the entire page of data is read into a SRAM buffer, and then the CPU gets instructions from the buffer. This can only be done by "loading first and then executing".

## NOR vs NAND: A Fateful Comparison Chart

| Features | NOR Flash | NAND Flash |
|------|-----------|------------|
| **Read Latency** | ~70ns (byte random access) | ~25µs (page read, first byte latency) |
| **Read Granularity** | 1 Byte | 1 Page (4KB-32KB) |
| **Max read bandwidth** | ~100-200MB/s (burst mode) | ~500MB/s-4GB/s (sequential read) |
| **Write Granularity** | 1 byte (the entire sector needs to be erased first) | 1 page (the entire block needs to be erased first) |
| **Programming Time (Single Unit)** | ~10µs/byte | ~200-500µs/page |
| **Erase Granularity** | Sector (4KB-64KB) | Block (128KB-16MB) |
| **Erase Time** | ~100ms/sector | ~2ms/block |
| **Erase speed (converted)** | ~0.04MB/s | ~64MB/s |
| **Program/erase endurance** | ~100,000 times (SLC) | SLC: 100,000 times, MLC: 3000-10,000, TLC: 500-3000 |
| **Bad block rate (factory)** | Close to 0% | 2%-5% (may be present when leaving the factory) |
| **Bad Block Management** | Not required (embedded scenario) | Required (FTL/ECC/Bad Block Table) |
| **Maximum capacity** | ≤2GB | Single die is about 1Tb (128GB), packaging/stacking can reach TB level |
| **Cost per Bit** | High (~10F²/bit) | Low (~4F²/bit, 3D can be smaller) |
| **Temperature range** | -40°C ~ +125°C | Consumer grade 0–70°C; automotive grade NAND/eMMC needs to be marked separately |
| **Radiation Resistance** | Good | Poor |
| **ECC requirement** | Low (1-bit ECC is enough, not even required) | Required (4-120 bit ECC/per page) |
| **XIP Support** | ✓ Supported | ✗ Not supported (must be loaded into RAM) |
| **Typical Applications** | Automotive ECU, MCU firmware, BIOS/UEFI | SSD, USB drive, mobile phone storage, SD card |

There is a cruel economic truth hidden in this table: **The unit area cost of NOR Flash is 2.5 times that of NAND. To produce the same capacity, NOR requires 2.5 times the silicon area. **

Because the series structure of NAND eliminates a large number of contact holes and isolation areas. A NAND cell occupies an area of ​​~4F² (F is the feature size) on the silicon wafer. And a NOR cell requires ~10F², because the drain of each cell needs a separate contact hole, and each bit line needs to be isolated.

```
Area comparison (simplified diagram)

  NOR cell: approximately 10F² NAND cell: approximately 4F²
  ┌──────────────────┐ ┌───────────────┐
  │ ┌────┐ ┌────┐ │ │ ┌──┐ ┌──┐ ┌──┐│
  │ │ FG │ │ FG │ │ ← Independent contact hole │ │FG│ │FG│ │FG││
  │ │ │ │ │ │ Quarantine Zone │ └──┘ └──┘ └──┘│
  │ └────┘ └────┘ │ │ ← Series connection, save contact holes │
  │ ↑Contact ↑Contact │ └───────────────┘
  │ ↓hole ↓hole │Area = ~4F²
  └──────────────────┘
       Area = ~10F²
```

F² is no joke here on the order of magnitude. For a 16nm process (F=16nm), 10F²=2560 nm², 4F²=1024 nm². About 390,000 NOR cells can be crammed into 1 square millimeter, or about 970,000 NAND cells.

**This means that for the same 300mm wafer, the capacity of NAND is 2.5 times that of NOR. And this multiple has become dozens or even hundreds of times in the world of 3D NAND, because you can stack it up. **

## NOR’s Vertical Dilemma vs NAND’s 3D Takeoff

For a long time, NOR and NAND have been advancing in 2D planar processes, making the size smaller and packing cells denser. But around 16nm, NOR Flash encountered a physical bottleneck:**Floating gate transistors must maintain that 8nm tunnel oxide layer. ** This thickness cannot be any thinner, thinner means greater leakage, shorter retention time, and worse reliability. Moreover, NOR requires independent contact holes and isolation areas. The size of these structures cannot be reduced infinitely, which will increase the contact resistance and cause isolation failure.

Therefore, NOR Flash basically stopped shrinking after the 16nm node. The current mainstream embedded NOR Flash is the 45nm-55nm process, and this process is already "mature" for NOR and cannot be more mature.

What about NAND?

NAND does not require each cell to be independently addressable, so it can be stacked in the Z-axis direction. This is **3D NAND**: multiple layers of memory cells stacked vertically on the same silicon wafer.

```
3D NAND structure (conceptual illustration)
==========================

          Z axis ↑ Number of stacking layers: 24 layers in 2013 → 232 layers+ in 2025
          │
     ┌────┴────┐ ← Nth Floor (Top Floor)
     │ FG FG │
     │ FG FG │ ← Floor N-1
     │ FG FG │
     │ FG FG │ ← Floor N-2
     │ FG FG │
     │ ... │ ← ... 232 layers stacked
     │ FG FG │
     │ FG FG │ ← Level 2
     │ FG FG │
     └────┬────┘ ← Layer 1 (near the substrate)
          │
     Peripheral control circuitry (on the substrate, or placed under the memory array - CMOS Under Array)
```

Each layer is an entire array of memory cells. The layers are stacked on top of each other like a layer cake, and are connected by a vertical channel, a polysilicon pillar that runs from top to bottom. After a Vertical Channel passes through 232 layers, this "string" has 232 units connected in series.

This brings several surprising results:

1. **Improvement of Capacity Density**: 3D stacking significantly increases single die capacity, but it is not a simple "number of layers × 2D capacity"; layer efficiency, peripheral circuits and processes must also be considered. A single die is about 1Tb, and the packaging/stacking can reach the terabyte level.

2. **Regressive process progress**: 3D NAND does not require the most advanced EUV lithography. Because the feature size of each layer can be made relatively large (20-30nm, or even larger), the density is compensated by the number of layers. This in turn reduces photolithography costs.

3. **NOR cannot keep up at all**: Because NOR requires independently addressable bit lines for each unit, if there are 232 layers, how should the bit lines be routed in the vertical direction? In a 3D structure, does each layer need independent bit line contacts? Physically almost impossible. **So NOR Flash has almost no 3D version so far. **

## Why Automotive Electronics Choose NOR

You now know why your car ECU uses NOR Flash instead of NAND.

**First, reliability. ** The car's Flash stores control codes for engine control, braking systems, and airbags. If the stored data is wrong by even one bit, the consequences can be catastrophic. NOR Flash has a low factory bad block rate and a lifespan of 100,000 erasing and writing cycles; however, it does not have zero bad blocks, and ECC is becoming more and more common in NOR. NAND has 2%-5% bad blocks before leaving the factory, which requires powerful ECC (BCH/LDPC) to correct errors. The erase and write life is only a few thousand times on MLC and TLC.

**Second, XIP (execution in place). ** SRAM in automotive ECUs is extremely valuable. The Cortex-R5 may only have 256KB to 1MB of SRAM, while the firmware image may have 2MB to 16MB. NAND cannot be used for XIP and usually requires paged/overwritten loading into SRAM, or a large enough RAM buffer to be reserved. With NOR Flash, the CPU directly fetches instructions from Flash, and SRAM is only used to run the stack and heap, saving a large amount of cost.

**Third, radiation resistance and wide temperature range. ** The operating temperature range of automobile engine compartments ranges from -40°C to +125°C, accompanied by electromagnetic interference and high-energy particle radiation. The data retention capability of NOR Flash in this environment is much better than that of NAND because its cell structure is simpler and the amount of charge is larger (SLC vs MLC/TLC). NAND's charge leakage speed accelerates dramatically under extreme temperatures and radiation.**Fourth, certainty. ** NOR Flash is erased at the sector level. You know that it takes about 100ms to erase a 4KB sector. NAND erasure is at the block level. It may take 3ms to erase a 4MB block, but with bad block management, wear leveling, garbage collection, and write amplification, the actual delay jitter is very large. For real-time systems like cars, determinism is more important than average performance.

```
Typical scenarios of automotive ECU using NOR Flash
==================================

  ECU is powered on → CPU gets Reset Vector from NOR Flash → starts executing firmware
  (No need to copy from Flash to RAM, just fetch and execute directly)

  Firmware storage area (NOR Flash)
  ┌──────────────────────────┐
  │ Bootloader (64KB) │ ← First level boot
  ├──────────────────────────┤
  │ Application (2MB) │ ← Main Application (XIP)
  ├──────────────────────────┤
  │ Calibration (256KB) │ ← Calibration parameters (read and write)
  ├──────────────────────────┤
  │ Log/Data (512KB) │ ← Runtime data logging
  └──────────────────────────┘
  
  All on NOR Flash. No external RAM required to load.
```

## Why choose NAND for mobile phones and USB flash drives?

On the other hand, there are equally good reasons for choosing NAND for your mobile phone, your USB flash drive, and your SSD.

**First, it’s cheap. ** 1GB NOR Flash may cost 2-3 times as much as 1GB NAND. NOR for a 128GB phone? If the cost triples, the phone cannot be sold.

**Second, density. ** 3D NAND can be stacked with 200+ layers, creating hundreds of times the capacity in the same chip area. NOR can't do it.

**Third, write throughput. ** NAND is written in pages (16KB page), and one page only takes 200 microseconds. Although it is slow, the amount of data in one page is large. The overall write bandwidth is much higher than NOR's byte-by-byte programming.

**Fourth, the application scenario does not require random byte access. ** There is never a need to "randomly read the 35467th byte" for photos on the phone and files on the USB flash drive. They always read and write in blocks. NAND's page access model perfectly matches this scenario: read as much as you need, and add another page if not enough.

**Fifth, the software layer masks hardware defects. **NAND's bad blocks, wear and tear, and charge leakage are all covered up by **FTL (Flash Translation Layer)**. FTL is a layer of software/firmware that maintains a mapping table from logical pages to physical pages, tracks bad blocks, does wear leveling, and does garbage collection. What the upper-layer applications and file systems see is a "perfect" block device, but they don't know that underneath it is a "riddled" NAND.

```
NAND software and hardware stack
=================

  Application layer: photos, videos, files
  File system layer: FAT32/exFAT/ext4/f2fs
  FTL layer: Logical block ↔ Physical block mapping ← Cover up bad blocks, wear leveling, GC
  Flash controller layer: ECC error correction, bad block management, command scheduling
  Physical layer: TLC NAND Die × N channel × M chip
```

FTL is the "fig leaf" of NAND. He is also its "translator". Without FTL, NAND is just a rag with bad blocks everywhere. With FTL, it's a perfect block device. The implementation complexity of FTL itself is several times greater than the entire KnotFS file system discussed in this chapter.

## This book only talks about NOR

The book in front of you ultimately only talks about one path: the embedded file system on NOR Flash. **

Because the scenarios we care about are automotive MCUs, real-time embedded systems and Cortex-R5 with extremely limited resources: safety-critical codes mostly use NOR; infotainment, maps, etc. use NAND/eMMC/UFS.

The FTL of a NAND system requires tens or even hundreds of KB of SRAM to maintain the mapping table. But our MCU only has a total of 512KB SRAM, and FTL overhead accounts for 10% or more.

NAND usually requires error correction such as BCH/LDPC; CRC32 can only detect errors and cannot replace ECC. Some MCU/SoC have hardware ECC or Flash controller, please confirm according to the specific model.

The erase block of a NAND system is 128KB to 16MB. Our Flash is only 512KB in total, and one erase block accounts for 25% to 3000%. There is no room for wear leveling, no room for garbage collection.

**So under resource and reliability constraints, NOR is almost the only way. Precisely because it is the only way, there is KnotFS, which we will talk about later, an embedded file system specially designed for NOR Flash. Starting from the teaching scale of 64KB, understand how it can be expanded to complete Flash management in a real vehicle environment. **The 16MB NOR Flash in your hand, based on its process node, capacity and cost, has been marginalized in the consumer electronics world of mobile phones and PCs. But in embedded real-time systems, it is standard. Your car, your router, your smart meter, and your drone flight control all rely on it to store codes and data.

**This is a path most people won’t take. But those who take this path will make the brakes of your car, the flight control of the plane above your head, and the firmware update system of the watch on your wrist. **

This is a narrow road. But every instruction and every bit of it protects your safety.
