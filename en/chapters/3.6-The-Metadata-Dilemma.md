# 3.6 The Metadata Dilemma: Managing the Data About Data

## You have a library, but the general catalog is in the fire

Imagine a scenario: You are a librarian. You built a library in the wilderness. The bookshelves are set up one by one, and the catalogs are compiled one by one. The library is large and well-managed. The reading area faces the mountain to the south, and the borrowing desk faces the road to the east. There are hundreds of book collection areas, each with an index.

Three years later, you retire. Your successor has taken over the library. There was only an envelope in his hand. There are three things in the envelope:

1. **Superblock** (Superblock): The general information of this library, that is, where it is, how big it is, what kind of bookshelf system it uses, and the year it was built.
2. **Borrowing Registration Card** (File Table): Who borrowed which book, for example, "Dream of Red Mansions" is in the third row in the east section, and "The Three-Body Problem" is in the first row in the west section.
3. **Free Bitmap** (Free Bitmap): Which bookshelf areas are empty and can be placed with new books.

Now imagine: someone sets a fire. Only the envelope was burned. The general catalog of the collection, the borrowing registration card, and the shelf map were all burned to ashes. Your successor stands before the library intact and there is nothing he can do.

He didn't know who owned the library. He didn't know which bookshelf row "Dream of Red Mansions" was on. He didn't know which row of bookshelves was empty.

**The general catalog of collections is lost, and the library becomes a deserted place. If the borrowing registration card is lost, the books in it cannot be found. **

This is the dilemma of metadata.

---

## The data is the collection of books, and the metadata is the collection directory.

In the world of file systems, data and metadata are two completely different animals. **

```
Data vs metadata
=======================

Data:
  - Content that users care about: text, pictures, calibration parameters, logs
  - Large size (KB~MB)
  - Missing piece: A few bytes are wrong in the file, usually tolerable
    Or the file is only read once and then thrown away.
    
Metadata:
  - is the data used by the file system to manage data
  - Small size (B~KB)
  - One item is missing: the entire file may not be found
    Or the file system cannot be mounted at all.
```

This asymmetry is the core contradiction in file system design.

Let's take a closer look at what the metadata in KnotFS consists of:

```
KnotFS Metadata Panorama
=======================

1. Superblock (SB0/SB1, block 0/block 1)
   ┌─────────────────────────────┐
    │ magic: 0x4B4E4653 │ ← "KNFS" identifies this as a KnotFS volume
   │ version: 1 │ ← File system version
   │ block_size: 4096 │ ← block size
   │ block_count: 16 │ ← Total number of blocks (teaching version)
   │ free_map: 0x0003 (example) │ ← The lower 16 bits cover 16 blocks; bits 0/1 are already occupied by SB
   │ log_offset/log_count: ... │ ← SB Log read and write pointer
   │ sequence: 0x0042 │ ← Monotonically increasing sequence number
   │ nodes[8]: {file table embedded here} │ ← Up to 8 file entries
   │ wear[16]: ... │ ← Number of erasures per block
   │ crc32: 0x9A3B... │ ← Integrity check
   └─────────────────────────────┘

Note: The file table (nodes[8]) is directly embedded in the SB Header, not an independent block.
      This means that the persistence of the file strip relies on the Compact operation - rewriting the entire SB to the spare slot.

2. SB Log (embedded inside the SB block, after the SB Header)
   ┌─────────────────────────────┐
   │ [tag:USED│blk:4│val:1│crc] │ ← "Block 4 is occupied"
   │ [tag:USED│blk:5│val:1│crc] │ ← "Block 5 is occupied"
   │ [tag:FREE│blk:3│val:0│crc] │ ← "Block 3 is freed"
   │ ... │
   │ About 8 bytes each │
   │ Designed to trigger compact 214 times; currently every operation is compact │
   └─────────────────────────────┘

3. File Table (nodes[8] embedded in SB Header)
   ┌─────────────────────────────┐
   │ entry[0]: "config.txt" │ ← file name (32 bytes)
   │ size: 1024 │ ← file size
   │ blocks[0..7]: [4,0,0...] │ ← Direct block number array
   │ block_count: 1 │ ← Number of occupied blocks
   │ │
   │ entry[1]: "firmware.bin" │
   │ size: 24576 │
   │ blocks[0..7]: [5,6,7...] │
   │ block_count: 6 │
   │ ... │
   │ (8 entries in total, size=0 means free) │
   └─────────────────────────────┘
   The file table modification does not leave the log - it is accumulated in the memory, and the entire file is written to the new SB during Compact.

4. Free Bitmap (free_map embedded in SB Header)
   ┌─────────────────────────────┐
   │ bit[0] = 1 (occupied by SB0) │
   │ bit[1] = 1 (occupied by SB1) │
   │ bit[2] = 0 (idle!) │
   │ bit[3] = 0 (idle!) │
   │ bit[4] = 1 (occupied by file) │
   │ bit[5] = 1 (occupied by file) │
   │ ... 16 bits = 2 bytes; free_map is uint32 low 16 bits │
   └─────────────────────────────┘

5. Wear Count Array (16 × uint32 = 64 bytes, teaching version)
   ┌─────────────────────────────┐
   │ block[0].wear = 35 │
   │ block[1].wear = 42 │
   │ block[2].wear = 28 │
   │ ... │
   │ Wear count, persisted to Flash │
   └─────────────────────────────┘
```

These five types of metadata add up to a total of about 700 bytes (SB Header). But every mistake they make, even if only one bit is wrong, may lead to disaster.

## Three strategies for metadata

In Flash file systems, there are three classic strategies for protecting the reliability and durability of metadata. KnotFS has nothing missing.

**Strategy 1: Dual-Copy, both cannot be bad**

```
Dual copy strategy
=======================

SB0 (block 0): [version=5, data...] ← valid
SB1 (Block 1): [version=4, data...] ← old version

Selection rules:
  if (SB0.sequence_number ≥ SB1.sequence_number)
      Use SB0
  else
      Use SB1

Write rules:
  Always writes "The copy is not currently valid"
  After the write is completed, the sequence_number of the new copy > the old copy
  Atomicly "switch" the active copy

Question:
  If power is lost during writing → the copy being written may be corrupted
  But the old copy is still intact!
  Select the larger sequence_number when restoring (but it must be complete and verified by CRC)
```

The cost of double copies is twice the storage space. For the KnotFS teaching version, the entire SB Header (~700 bytes, including file table + free_map + wear[]) + Log space only requires 2 blocks (SB0 and SB1 each 4KB = 8KB), accounting for 12.5% ​​of the 64KB total space. Although the ratio is not low, for educational-grade file systems, reliability takes precedence over space efficiency.

But dual copies solve the most fatal problem: **If the power is lost during the process of writing metadata, you can always roll back to the last valid version. **

**Strategy 2: Log Append, only add one line, do not rewrite the entire book**

```
Log append strategy
=======================

No logging:
  Modify a field in SB (4 bytes)
  → Erase the block where SB is located (4KB, 200ms)
  → Reprogram the entire SB block to Flash (4KB, ~58ms)
  → Write amplification = 4096 ÷ 4 = 1024 times

Keep a log:
  Modify a field in SB
  → Append an 8-byte log record at the end of the SB block
  → Program 8 bytes (~0.1ms, append directly, no erasing required)
  → There is enough space on the SB block to continue appending (until 50% full)
  → Write amplification ≈ 8 ÷ 4 = 2 times (because the actual log record may be a little larger than the field)

SB block internal layout:
  ┌──────────────────────────┐ ← Start of block
  │ Superblock Header │ ← 668 bytes, only rewritten when compacting
  │ (immutable) │
  ├──────────────────────────┤
  │ SB Log Record 1 │ ← 8 bytes, append writing
  │ SB Log Record 2 │ ← 8 bytes
  │ SB Log Record 3 │ ← 8 bytes
  │ ... │
  │ SB Log Record N │ ← Latest
  ├──────────────────────────┤
  │ Free space (can be added) │
  │ │
  └──────────────────────────┘ ← End of block
```

The subtlety of log appending is: **It turns "modify a fixed field" into "append a row of records at the end". ** Append only needs to change 1 to 0, and there is no need to erase first, because the appended position must be clean (has not been written before). This is a perfect use of the one-way programming feature of Flash.

But the log will be full. For the 4KB SB block, minus the 668-byte header (`sizeof(knot_sb_t)`), there is still a 3424-byte Log area plus a 4-byte tail. Each record is 8 bytes and can hold up to 428 records. By design, 214 items (50%) trigger compact; currently, KnotFS compacts every metadata operation, and this threshold is not enabled.

**Strategy 3: Compact, condense the log into the latest version**

```
Compact process
=======================

Before Compact:
  Within SB0 block:
    ┌─────────────┐
    │ Header v4 │
    │ Log: seq=10 │ ← Old mount record
    │ Log: seq=11 │ ← Old write record
    │ Log: seq=12 │ ← Old write record
    │ Log: seq=13 │ ← Latest: Contains all accumulated changes
    │ [blank] │
    └─────────────┘

Compact process:
  1. Allocate a new SB block (such as block 0 → block 1, or block 1 → block 0)
  2. Replay log: from the first valid log to the latest one
     Accumulate all changes → get the latest complete superblock status
  3. Write the latest superblock header to the header of the new block
  4. The log area of the new block is empty
  5. Erase old blocks

After Compact:
  Inside the new SB1 block:
    ┌─────────────┐
    │ Header v13 │ ← Contains all cumulative changes
    │ [Blank log] │ ← You can continue to add ~428 new records
    │ │
    │ │
    └─────────────┘
```

**These three strategies are all three, not one of the three. **- **Dual copy** provides power loss protection during writing (there is always a valid copy)
- **Log Append** provides efficient metadata updates (no need to erase the entire block each time)
- **Compact** provides recycling of log space (preventing log overflow)

The three form a closed loop:

```
Closed loop of metadata protection
=======================

        Modify metadata
            ↓
    ┌─Append a log record ─→ Is there enough log space?
    │ │
    │ Enough │ Not enough
    │ │
    │ ✓ Complete │
    │ ↓
    │ Trigger Compact
    │ │
    │ ↓
    │Dual copy switching (write to another copy)
    │ │
    │ ↓
    │The log area is cleared and the cycle continues
    │ │
    └────────────────────────┘
```

## "Library" metaphor: general collection catalog, borrowing registration card and shelf map

Let’s go back to that librarian metaphor. In the "library" (Flash) managed by KnotFS:

```
Library metaphor → KnotFS data structure
=======================

Collection General Catalog = Superblock
  Content: How many book collection areas does this library have and what is its structure version?
  Lost: You don’t know who manages this library

Borrowing Registration Card = File Table (embedded in Superblock)
  Content: "A Dream of Red Mansions" is in the book collection area No. 3, "The Three-Body Problem" is in the book collection area No. 5, and "Zi Zhi Tong Jian" is in the book collection area No. 8
  Lost: You know there is "A Dream of Red Mansions", but you don't know which library area it is in

Bitmap = Free Bitmap
  Content: Which library areas are empty and which are occupied?
  Lost: You don’t know which library area to put the newly arrived books in

Bookshelf maintenance record = Wear Count
  Record: The bookshelves in Book Collection Area 3 have been organized 35 times.
  Lost: You don’t know which side of the bookshelf is the most fragile (has the most wear and tear)

Call number check = CRC check
  Each call card is verified: is the call number obtained correct?
  Wrong: The manual has been replaced (data is damaged)
```

**The metaphor of managing a library is powerful because it turns "abstract data structure management" into "concrete physical space management", and the latter is one of the things the human brain is best at. **

In this metaphor, the three strategies for metadata protection become:

- **Double Copies** = Two copies of the general collection catalog, placed in two different safes. Burned one, and another.
- **Log append** = Paste a sticky note behind the general catalog (directly altering the general catalog will damage the paper): "Correction No. 3: "Dream of Red Mansions" has been moved to the 12th library area. Date ×. Signature ×." The more sticky notes are pasted, the more the sticky notes are pasted, but the general catalog itself has not been torn.
- **Compact** = Take out the general catalog with hundreds of sticky notes and re-write it cleanly. All the sticky note information is integrated into the text, and the sticky notes can be thrown away.

## Engineering philosophy of metadata: redundancy is the only way

Back to the core question: Why is metadata the most difficult to manage? **

Because the value density of metadata is extremely high.

1KB of user data was lost, and the user said: "Oh, there is a missing log line."
The 1KB superblock is lost, and the file system says: "I don't know who I am anymore. Mount failed."

Each bit of metadata "manages" data hundreds or thousands of times its own size. This asymmetry means: **Metadata requires a level of reliability that is more than a thousand times greater than that of data. **

In engineering, the only way to improve reliability is through redundancy. Dual copies are spatially redundant (two copies). Log appending is time redundant (modification history is retained). CRC check is check redundancy (redundancy at the information theory level).

KnotFS invests 8KB of physical storage space in ~700 bytes of metadata (SB Header + file table) (SB0 and SB1 each occupy 1 4KB block = 8KB), as well as several array tracking data structures (wear[], free_map).

**Redundancy rate = 8KB ÷ ~700B ≈ 12 times. **

This is not a waste. This is a rational response to the engineering fact that the value density of metadata is a thousand times that of data.
