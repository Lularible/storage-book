# 5.5 SB-Log: The Append-Only Borrowing Ledger

The principles of SB Log (Write-Ahead Log, additional writing, solidification through Compact) have been discussed in Chapter 3. Here we look directly at the data structure of each Log record in KnotFS.

## The anatomy of a Log record: an 8-byte sticky note

```c
// knotfs.c
typedef struct {
  uint8_t tag; /* LT_BITMAP or LT_USED */
  uint8_t blk;
  uint16_t val;
  uint32_t crc32;
} knot_log_t; /* 8-byte log record (different from SimpleFS's
                 simplefs_sb_log_record_t) */
```

Field layout:

```
Log Record (8 bytes)
╔═══════╤═══════╤══════════╤══════════════════╗
║ tag   │ blk   │ val      │ crc32            ║
║ 1B    │ 1B    │ 2B       │ 4B               ║
╚═══════╧═══════╧══════════╧══════════════════╝
```

There are two log types:

```c
// knotfs.c
#define LT_BITMAP (0U) /* log entry type: free_bitmap change */
#define LT_USED   (1U) /* log entry type: block_used_bytes */
```

- **LT_BITMAP**: Modify the allocation status of blocks. `val=1` means marked as used, `val=0` means marked as free. This is the most frequently used Log type in KnotFS: every time a new block is allocated or an old block is released, an LT_BITMAP record is generated.
- **LT_USED**: Record the usage of blocks. Defined in KnotFS but currently almost unused, it is reserved for possible future block content checksum functionality. Production-level scenarios have similar LT_USED records that track the number of bytes of valid data within a block.

Each record carries its own checksum: calculate the CRC32 of the first 4 bytes (tag+blk+val):

```c
// knotfs.c
static uint32_t log_checksum(const knot_log_t *e) {
  return k_crc32(e, sizeof(knot_log_t) - sizeof(uint32_t));
}
```

Why does each record have to have its own CRC? Because a power outage may occur in the middle of writing a Log record. If you only do a CRC for the entire Log area, and a power outage damages one of the records in the middle, you cannot tell which one is damaged, so the entire Log cannot be trusted. Each record is independently verified; the current playback will stop when encountering the first bad record and will not skip it to continue.

## Append Log: Promise to never overwrite

Log writing is completed through the `log_push` function. It appends the new record to a memory buffer `log_buf[32]`:

```c
// knotfs.c — Append a Log to the memory buffer
static int log_push(uint8_t tag, uint8_t blk, uint16_t val) {
  if (log_cnt >= LOG_BUF_CAPACITY)
    return ERR_Q_FULL;
  knot_log_t *e = &log_buf[log_cnt];
  e->tag = tag;
  e->blk = blk;
  e->val = val;
  e->crc32 = log_checksum(e);
  log_cnt++;
  return 0;
}
```

Note the limitations of `log_cnt >= 32`. `log_buf[32]` is a static buffer (`knotfs.c`), which can cache up to 32 Log records at a time. This is a limitation of KnotFS: if more than 32 Logs are generated in one operation (for example, deleting a file that takes up 8 blocks, each block release generates 1 LT_BITMAP + 1 LT_USED, up to 16 logs), the buffer will overflow. In actual use, no more than 10 logs are generated in one operation, and the capacity of 32 logs is sufficient.

When a batch of Log records are written and need to be persisted to Flash, call `log_flush`:

```c
// knotfs.c — Flush the Log in the buffer to Flash
static void log_flush(void) {
  if (log_cnt == 0)
    return;
  uint32_t sz = log_cnt * LOG_ENTRY_SZ;
  fdev_write(active_sb_slot(), log_buf, sb.log_offset, sz);
  sb.log_offset += sz;
}
```

`active_sb_slot()` returns the currently active SB slot according to the parity of `sb.sequence`: even numbers correspond to block 0, and odd numbers correspond to block 1. At the end of each compact, the active slot ping-pongs between block 0 and block 1. Log is always appended to the **currently active** SB, and compact is always appended to the **inactive** slot on the opposite side. The design is completely consistent with the ping-pong logic of dual copies.

There is another detail here: `log_flush` uses `fdev_write` to write Log to Flash. Since `fdev_write` is asynchronous (requires 2 ticks) and `log_buf[32]` is static, this means that you cannot call `log_push` again to modify the contents of `log_buf` before fdev_tick actually performs the write. In the current teaching implementation, `log_flush` is immediately followed by `compact_erase`, and the asynchronous Log writing may be overwritten by subsequent erasure; therefore, the SB Log cannot be regarded as a persistence path that has been placed on the disk. Actual persistence relies on compact rewriting of the SB header.

## Playback Log: "Cash in" the modifications on the sticky note

The last step to mount is `replay_log()`:

```c
// knotfs.c — Play back Log one by one
static void replay_log(void) {
  knot_log_t e;
  for (uint32_t i = 0; i < sb.log_count; i++) {
    uint32_t pos = SB_HEADER_SZ + i * LOG_ENTRY_SZ;
    memcpy(&e, tmp + pos, sizeof(e));
    if (e.tag == 0xFF)
      break;
    if (e.crc32 != log_checksum(&e))
      break;
    if (e.tag == LT_BITMAP) {
      if (e.val)
        mark_used(e.blk);
      else
        mark_free(e.blk);
    }
  }
}
```

The playback logic is very straightforward:
1. Starting from the head of the Log area, read 8-byte records one by one
2. If `tag == 0xFF`, it means that this is an erased area (the default value after Flash erasure is 0xFF), and the following ones are empty data, stop playback
3. If the CRC check fails, it means that the power outage occurred during the writing of this record and the data is unreliable. Stop playback.
4. If tag is LT_BITMAP, update free_map according to val

**A subtle design decision: stop playback on CRC errors instead of continuing past bad ones.**

You may be thinking: "Why not stop this bad one and try the next one? The power failure may only destroy this one, but the subsequent records may be good."

There is a logical reasoning behind this design decision: If a power outage causes the CRC of a Log record to be damaged, then the problem may not be limited to this one. Flash write interruption may cause voltage instability, affecting subsequent writing of several bytes. For safety reasons, it is better to lose a few valid logs than risk using potentially damaged data.

The more fundamental reason is: there may be dependencies in the Log records. Suppose record 5 is "release block 7" and record 6 is "allocate block 7 to file foo". Release and allocation are sequentially dependent and must be released before they can be reallocated. If record 5 is corrupted and skipped, block 7 is still in the "used" state when record 6 is executed, and the allocation will fail (the system will think there is insufficient space). This is an incomplete sequence of operations: you've lost a necessary intermediate step, and the preconditions for subsequent operations are no longer met. Rather than risk performing a potentially wrong operation, it is better to stop playback when a CRC error is encountered for the first time and discard all remaining Logs.

**Stop immediately on CRC failure, this is a conservative but safe choice.**

What will happen to the lost Log? For example: As a design deduction, it is assumed that real Log persistence is implemented in the future: if 3 writes (a total of 30 Logs) are made after the last compact, the power will be lost when the 25th log is written. During mount playback, you can only restore the state of the 24th Log. This means that part of the block allocation from the last write operation may be lost, and the file size will be restored to the value when compacting. The data is lost, but the consistency of the file system is preserved.

**This is the trade-off of Log: it does not guarantee that you will not lose data, but it guarantees that you will not lose consistency.**

## Compact: There are too many sticky notes, so I have to re-copy the entire table of contents.

Log cannot be increased infinitely. Every time a record is appended, `sb.log_offset` moves back 8 bytes. The current implementation adopts an unconditional compact strategy: compact is executed after each write/append/delete operation (to simplify the teaching logic, metadata is always atomically persisted). Production implementation can be triggered by the number of Log entries (`LOG_THRESHOLD = 214`, that is, 50% full) to reduce unnecessary erasing.

```c
// knotfs.c — compact trigger condition
#define SB_HEADER_SZ     (sizeof(knot_sb_t))
#define LOG_ENTRY_SZ     (8U)
#define LOG_ENTRIES_MAX  ((KNOTFS_BLOCK_SIZE - SB_HEADER_SZ) / LOG_ENTRY_SZ)  /* (4096-668)/8 = 428 */
#define LOG_THRESHOLD    (LOG_ENTRIES_MAX * KNOTFS_LOG_THRESHOLD / 100U)       /* 214 */
```

The compact process:
1. Select the SB slot opposite (`inactive_sb_slot()`)
2. Erase that block
3. Copy the current SB (including the solidified file entries nodes[] and free_map) to the compact buffer
4. Clear the log area (`log_offset = SB_HEADER_SZ`, `log_count = 0`)
5. Write new SB

Why is the design recommended to trigger 50% instead of triggering every modification? Because every compact you do is equivalent to a full block erase + write. If the 50% threshold is enabled, the frequency of erasing and writing SB blocks will be significantly reduced; however, the current implementation compacts every time, and the 50% threshold (214 entries) is not enabled.

However, this raises a teaching limitation of KnotFS.

>  ⚠️ Teaching Simplification Tip: KnotFS does not have separate FT (File Table) and FT Log. The production-level solution will have independent FT blocks (FT0 in block 2, FT1 in block 3), and each FT has its own independent Log append area. This means that when modifying a file entry, only one record needs to be appended to the FT Log, and the entire SB does not need to be compacted. KnotFS places the file entry `nodes[8]` in the SB. Each file operation (write/append/delete) must rewrite the entire SB through compact to persist the file entry. This results in the number of erases and writes in the SB slot being significantly higher than that of a production-level design with independent FT/FT Log. The specific multiple depends on the load. The compact trigger condition of the production-level solution is "SB Log exceeds 50%  or FT Log exceeds 50%". The independent FT+FT Log completely solves this wear problem.
