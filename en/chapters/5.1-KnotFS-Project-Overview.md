# 5.1 KnotFS Project Overview: A Teaching-Grade Asynchronous Log-Structured File System

## You have a 64KB virtual Flash in your hand and no operating system

Suppose you are a new embedded engineer and are assigned a task: implement a file system that can safely read and write on a microcontroller with only 64KB NOR Flash.

There is no FreeRTOS. No DMA. No interrupts. No hardware.

There is only a laptop at your workstation with GCC installed on it, and a coffee-stained C programming guide.

You start to wonder: What does the file system need? Superblock, inode, directory, read-write interface, atomic write, power-off protection, wear leveling... Behind every word lies thousands of lines of C code and pitfalls accumulated from decades of engineering practice.

How are you feeling now? Puzzled? Feeling overwhelmed? Still excited?

**Don't worry. This is why KnotFS exists.**

KnotFS is a teaching-grade file system. Its goal is to run inside your brain. It uses about 1770 lines of pure C code (core 1165 lines), does not rely on any external libraries (except libc), and implements an asynchronous, log-structured teaching file system with compact as the main persistence path on a 64KB NOR Flash simulated by a RAM array; power-off safety is the design goal, and the failure path still has teaching simplification.

You can compile it in one minute, run its 12 test functions (18 checkpoints) in a dozen seconds, and then slowly read its source code. Every line is worth stopping and thinking about.

---

## What is KnotFS?

The full name of KnotFS is "Knot Filesystem", which is the "knot" file system. This name was not given randomly.

Do you still remember the rope-tying story we talked about in Chapter 1? Knots are the original information encoding system. KnotFS is the modern C incarnation of this encoding system: it organizes information (your files) into a linear address space (the rope) using data blocks (knots), organizes retrieval using metadata (the rules for the location and size of the knots), and protects integrity with checksums (the Incas' check knots).

**KnotFS is the "teaching companion" to this book.** Every concept you read about, including superblock double copies, Log append, Copy-on-Write, and wear leveling, has a straightforward implementation in KnotFS. You don't need a cross-compilation toolchain, you don't need a JTAG debugger, you don't even need the Linux kernel source code.

There are only three things you need:

```
KnotFS source code structure
==================

knotfs.h (line 132) - public interface, constant definition, type declaration
knotfs.c (line 1165) - core implementation: state machine × 8, Flash simulator, CRC32
knotfs_test.c (line 474) - 12 self-test cases, including power failure recovery
Makefile (71 lines) - single file compilation, supports x86/ARM64/ARM32 three architectures
```

About 1770 lines of code in total. If you have a basic knowledge of C language, you can read it through in one afternoon. But understanding why it is written this way, such as why the state machine is designed this way, why the super block is stored in two copies, and why the current implementation compacts after each metadata operation, requires you to read the remaining sections of this chapter.

How does Makefile achieve zero dependencies? Look at these lines:

```c
// knotfs.h — the only system header file
#include <stdint.h>
#include <stdbool.h>
```

Just these two. `<string.h>` is used in `knotfs.c` for `memcpy` and `memset`. There is no `<stdio.h>`, no `<stdlib.h>`, no `<pthread.h>`. KnotFS is a **pure computing unit** that only manages data and metadata, abstracting all I/O into reading and writing `flash[]` arrays.

**The "portability" of KnotFS is that "we are not dependent on any platform at all".**

## Asynchronous architecture: event loop + state machine

The core architecture of KnotFS has only two concepts: **event loop** and **state machine**.

The event loop is `knotfs_run()`:

```c
// knotfs.c — the heart of the event loop
bool knotfs_run(void) {
  fdev_tick();

  /* handle compact completion */
  if (comp_wait && fdev_idle()) {
    comp_wait = false;
  }

  if (!fdev_idle())
    return true;

  /* if current request done, dequeue next */
  if (cur.op != OP_NONE && (cur.st == ST_OK || cur.st == ST_ERR)) {
    if (!q_empty())
      q_pop(&cur);
    else
      cur.op = OP_NONE;
  }

  /* dequeue if idle */
  if (cur.op == OP_NONE && !q_empty()) {
    q_pop(&cur);
    prog = 0;
    subst = 0;
    memset(scratch, 0, sizeof(scratch));
  }

  /* advance state machine */
  if (cur.op != OP_NONE && cur.st != ST_OK && cur.st != ST_ERR) {
    switch (cur.op) {
    case OP_FMT: do_format(); break;
    case OP_MNT: do_mount();  break;
    case OP_WRT: do_write();  break;
    case OP_RD:  do_read();   break;
    case OP_APP: do_append(); break;
    case OP_DEL: do_delete(); break;
    case OP_LS:  do_list();   break;
    case OP_ST:  do_stats();  break;
    default:     break;
    }
  }

  return !knotfs_is_idle();
}
```

This function is like the main loop of an old game console: every "tick", it checks input, updates state, and renders output. The difference is that game consoles render pixels, while KnotFS renders file system operations.

What about state machines? Each file system operation (format, mount, write, read, append, delete, list, stats) is a giant branch of `switch(cur.st)`:

```c
// knotfs.c — Operation types and status constants
typedef enum {
  OP_NONE = 0,
  OP_FMT,
  OP_MNT,
  OP_WRT,
  OP_RD,
  OP_APP,
  OP_DEL,
  OP_LS,
  OP_ST,
} knot_op_t;

typedef enum {
  /* format */
  ST_FMT_ERASE = 10,
  ST_FMT_ERASE_WAIT = 11,
  ST_FMT_WR_SB1 = 12,
  ST_FMT_DONE = 13,
  /* mount */
  ST_MNT_RD_SB0 = 20,
  ST_MNT_RD_SB1 = 21,
  ST_MNT_SEL = 22,
  ST_MNT_REPLAY = 23,
  /* write */
  ST_WRT_INIT = 30,
  ST_WRT_ALLOC = 31,
  ST_WRT_DATA = 32,
  ST_WRT_META = 33,
  ST_WRT_META_FLUSH = 34,
  ST_WRT_COMPACT = 35,
  /* ... */
  ST_OK = 90,
  ST_ERR = 91,
} knot_st_t;
```

Each state only does one thing, then returns to the event loop and waits for the next call. This seems "slow", but it's the only feasible way in embedded systems: you can't block the CPU during the 100 milliseconds of Flash erasure, because you still have a CAN bus to respond to, a motor to control, and a serial port to send and receive.

KnotFS lets you simulate this scenario on your laptop with `while(knotfs_run())`. Every time a function returns, it is equivalent to a task switch. As you watch the number of ticks increase, you gradually understand: Oh, it turns out that asynchronous has nothing to do with multi-threading. It just cuts a long operation into many small steps.

## What production-grade features are retained?

Although simple, KnotFS retains five core designs from production-grade solutions:

**1. Double super block + log structured metadata**

Superblock (Superblock) is the "master directory" of the file system, which records the allocation, file directory, and wear count of all blocks on Flash. KnotFS stores two copies: SB0 in block 0 and SB1 in block 1. In design, metadata changes can be appended as 8-byte Log records; however, the current teaching implementation rewrites the 668-byte SB header through compact every time, and the persistence path of SB Log has not yet been truly enabled.

**2. Copy-on-Write atomic write**

When you overwrite a file, KnotFS does not directly modify the original data blocks. It allocates new blocks, writes new data, and then updates metadata to point to the new blocks. Atomicity is achieved by this: either new data is written to the metadata and updated (success), or old data is not touched (failure), and there will never be an intermediate state of "half new and half old".

**3. Wear Leveling**

Each block of NOR Flash has a write and erase life (typically about 100,000 times). If a file is written to the same block repeatedly, that block will be discarded prematurely. KnotFS's `find_free_block` (called `pick_lowest_wear` in KnotFS) always selects the free block with the least wear and tear, so that write operations are evenly distributed.

**4. CRC32 metadata check**

The data on Flash may be bit flipped due to power outage, aging, and radiation. KnotFS uses CRC32 to protect the super block, and the Log record also has a CRC field; currently Log persistence is not actually enabled, and the main persistence path is still compact rewriting SB. When mounting, superblocks that fail the CRC check are discarded like a chip appraiser jumping over a frayed knot.

**5. Request queue + asynchronous completion**

The request queue structure has 4 slots, but the current public API directly returns ERR_Q_FULL when the queue is not empty or there is an operation in progress; only one pending request is actually allowed at a time, and the caller must run the event loop between two submissions.

---### Compared to production-level solutions, what does KnotFS simplify?

The production-level solution is estimated to be thousands to 10,000 lines, running on a real Cortex-R5. KnotFS simplifies the following five aspects:

| Features | KnotFS (educational version) | Production-level solution (design goal) |
|------|------------------|---------------------|
| **Running environment**| Event loop, single thread | FreeRTOS, multi-tasking |
|**Flash media** | RAM array `flash[16*4096]` | Real NOR Flash (AUTOSAR FLS driver) |
| **Max file size**| 32KB (8 direct blocks) | Determined by indirect blocks (larger) |
|**File Table (FT)**| Merged into SB (nodes[8]) | Independent FT block, with FT Log |
|**Network Terminal** | None | TCP port 8004/8005 |

Below is a detailed explanation of each simplification point.

**1. No FreeRTOS → event loop**

The production-level solution runs on FreeRTOS. The disk operation is performed by an independent DiskAsync task, and the file system operation is performed by the main task. The two communicate through queues and have different priorities (DiskAsync priority 3, main task priority 1). KnotFS serializes all operations in an event loop, and `knotfs_run()` can only do one thing at a time.

**2. No real Flash → RAM array + tick delay**

The production-level solution will call the AUTOSAR FLS driver to erase and write the real NOR Flash: erasing takes about 100ms, writing takes about 1ms, and reading takes about 1μs. KnotFS uses a `static uint8_t flash[16 * 4096]` array instead of Flash and uses counters to simulate delays (read 1 tick, write 2 ticks, erase 3 ticks). Section 5.3 will expand on this in detail.

**3. No indirect blocks → 32KB file limit**

Production-level solutions will support indirect blocks, and each file can have far more than 8 data blocks. KnotFS removes the indirect block mechanism, and each file has a maximum of 8 direct blocks (`KNOTFS_DIRECT_BLKS = 8`), which is 32KB (`8 × 4096`). This limit is sufficient for teaching purposes, since most test files are only tens to hundreds of bytes.

**4. No independent file table → FT merged into SB**

This is the most significant simplification of KnotFS. The production-level solution will have an independent File Table (FT), stored in fixed blocks 2 and 3. Each FT has its own Log append log. Modification of file entries only requires appending a record to the FT Log and does not require rewriting the entire FT block.

## What has KnotFS simplified compared with production solutions?

KnotFS places the file entry (`nodes[8]`) directly in the superblock. This means that every time a file is created, deleted, or changed in size, the entire super block must be rewritten through compact instead of just appending a Log. This results in the number of erases and writes in the SB slot being significantly higher than a production-level design with independent FT/FT Log.

**5. No network terminal → Pure API**

The production-level solution provides a TCP terminal through Terminal Services: port 8004 is used for interactive commands (mount, read, write, delete, list, stats, format), and port 8005 is used for file transfer. KnotFS only provides C API, driven by the `knotfs_test.c` self-test program.

## Why should we read the KnotFS source code?

KnotFS does something rare: it extracts the core ideas of embedded file systems, namely asynchronous state machines, log structuring, Copy-on-Write, and double-copy redundancy, from production-level design concepts and compresses them to more than a thousand lines, while retaining all key designs.

You're reading more than just C code. What you read is an engineer saying: "Look, the file system is actually not that mysterious. Look at the structure of this super block, it is a C structure. Look at this state machine, it is a switch statement. Look at this compact, it is a memcpy plus an erase."

After you understand these approximately 1,770 lines of code and look at the design of the production-level solution, you will be surprised to find: **Their cores are the same.** Most of the extra code in the production-level solution is integration glue (FreeRTOS task management, AUTOSAR driver calling, cache consistency maintenance), rather than the file system logic itself.

And this is the ultimate value of KnotFS as a "teaching companion".

---

> ⚠️ **Teaching Simplification Tips**: The goal of KnotFS is to allow readers to understand the design of asynchronous file systems without hardware. It is not suitable for direct use in production environments. KnotFS lacks the following production-level features: DMA-driven Flash I/O interrupt handling, indirect block support for large files, independent FT Log to reduce SB wear, FreeRTOS task priority scheduling, cache consistency maintenance (`arch_clean_cache_range`/`arch_invalidate_cache_range`), and network terminal services.
