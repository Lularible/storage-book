# 5.11 Append and Delete: How Files Change and Vanish

## Add: add books to bookshelf

You have a bookshelf that's half full. Now you want to move on to new books. You can't empty the bookshelf and start over, it's too expensive. You can only find the very end of the last row and continue from there.

This is file append. The difference between it and "write a new file" (write) is that: **write is a one-time overall replacement (full coverage of CoW), and append is an incremental modification (continue writing at the end of the original file).** In POSIX semantics, write(oflag=O_TRUNC) replaces and write(oflag=O_APPEND) appends. KnotFS divides these two semantics into two independent APIs: `knotfs_write` and `knotfs_append`.

But append has a complexity that write does not need to face: **Read-Modify-Write (RMW, read-modify-write).**

```
Why does append require RMW?

File layout:
  ┌─────────Block 0────────┐ ┌─────────Block 1─────────┐
  │ Existing data (4096 bytes) │ │ Existing data (1000 bytes) │ │ Blank (3096 bytes)
  └────────────────────┘ └──────────────────────┘

Now append 500 bytes. Where should new data be written?
  → Offset 1000 of block 1.

Intuitively, just write 500 bytes directly to offset 1000.
However, the Flash driver programming interface has alignment constraints: the starting address and write length must meet the boundaries of the hardware requirements (such as programming page alignment, word alignment).
When the starting point of the append is not on the alignment boundary, or the length is irregular - you cannot directly "send a write command with an offset".

So RMW must be used: first read all block 1 into `tmp`,
Splice the new 500 bytes into memory at offset 1000 - the alignment problem is solved in RAM - and write the complete concatenated content back to block 1.
(In fact, the real flash may be word-aligned and does not necessarily need to read the entire block 1. The knotfs is just to illustrate this concept and is only a teaching demonstration.)
```

This is the RMW model. It takes one more step than a simple write operation: **read first**. Because the append operation must keep the data already in the block from being lost. KnotFS's append state machine has 6 states:

```
ST_APP_LOOKUP → ST_APP_ALLOC → ST_APP_RD_BLK → ST_APP_DATA → ST_APP_META → ST_APP_COMPACT
```

## First state: ST_APP_LOOKUP - figure out where to continue writing

```c
case ST_APP_LOOKUP:
    nd = find_node(cur.name);
    if (!nd) {
      nd = alloc_node(cur.name);
      if (!nd) {
        cur.result = ERR_APP_NOFILE;
        cur.st = ST_ERR;
        return;
      }
    }
    last_used = nd->size;
    if (last_used + cur.a_sz > KNOTFS_FILE_LIMIT) {
      cur.result = ERR_APP_OVF;
      cur.st = ST_ERR;
      return;
    }
    nd->size = last_used + cur.a_sz;

    if (nd->block_count == 0) {
      scratch[SCR_APP_LAST_BLK] = 0;
      scratch[SCR_APP_LEFT] = KNOTFS_BLOCK_SIZE;
    } else {
      uint32_t li = nd->block_count - 1;
      last_blk = nd->blocks[li];
      free_in_last = KNOTFS_BLOCK_SIZE - (last_used % KNOTFS_BLOCK_SIZE);
      if (last_used % KNOTFS_BLOCK_SIZE == 0)
        free_in_last = 0;
      scratch[SCR_APP_LAST_BLK] = last_blk;
      scratch[SCR_APP_LEFT] = free_in_last;
    }
    scratch[SCR_APP_OFF] = last_used;
    subst = 0;
    prog = 0;
    cur.st = ST_APP_ALLOC;
    return;
```

The intensive calculations of this code are concentrated in one place: **How much space is left in the last block?**

```
last_used = nd->size; //The current size of the file, such as 5000
last_blk = nd->blocks[ nd->block_count - 1 ]; // The block number of the last block
free_in_last = KNOTFS_BLOCK_SIZE - (last_used % KNOTFS_BLOCK_SIZE);
             = 4096 - (5000 % 4096)
             = 4096 - 904
             = 3192 // 3192 bytes left in the last block

if (last_used % KNOTFS_BLOCK_SIZE == 0) free_in_last = 0;
  // If the file size is an exact multiple of the block size, the last block is full and a new block is needed
```

This calculation determines the subsequent direction of append:
- If `free_in_last > 0`: the last block has remaining space, new data can be directly chased into that block
- If `free_in_last == 0`: The last block is full and a new block needs to be allocated

`scratch[2] = last_used` records the file size before appending, which is the **file absolute offset starting point** for new data to be written.

## Second state: ST_APP_ALLOC - If necessary, divide a new bookshelf grid

```c
case ST_APP_ALLOC:
    if (scratch[SCR_APP_LEFT] == 0) {
      nd = find_node(cur.name);
      if (nd->block_count >= KNOTFS_DIRECT_BLKS) {
        cur.result = ERR_APP_MAXBLK;
        cur.st = ST_ERR;
        return;
      }
      new_blk = pick_lowest_wear();
      if (new_blk >= KNOTFS_BLOCK_COUNT) {
        cur.result = ERR_APP_NOBLK;
        cur.st = ST_ERR;
        return;
      }
      mark_used(new_blk);
      sb.wear[new_blk]++;
      nd->blocks[nd->block_count] = new_blk;
      nd->block_count++;
      scratch[SCR_APP_LAST_BLK] = new_blk;
      scratch[SCR_APP_LEFT] = KNOTFS_BLOCK_SIZE;
    }
    /* read existing block first to merge append data */
    fdev_read(scratch[SCR_APP_LAST_BLK], tmp, KNOTFS_BLOCK_SIZE);
    cur.st = ST_APP_RD_BLK;
    return;
```

If `scratch[1] == 0` (the last block is full), a new block is allocated. Then read the target block into tmp, **Whether it is an old block or a new block, the first step of RMW is to read, because you need the existing data in the block to splice with the new appended content.**

## The third and fourth states: ST_APP_RD_BLK + ST_APP_DATA - splicing and writing back

```c
case ST_APP_RD_BLK: {
    uint32_t blk = scratch[SCR_APP_LAST_BLK];
    write_off = scratch[SCR_APP_OFF] % KNOTFS_BLOCK_SIZE;
    uint32_t space = KNOTFS_BLOCK_SIZE - write_off;
    uint32_t n = (cur.a_sz - prog < space) ? cur.a_sz - prog : space;

    const uint8_t *s = (const uint8_t *)cur.a_buf + prog;
    memcpy(tmp + write_off, s, n);
    fdev_write(blk, tmp, 0, KNOTFS_BLOCK_SIZE);
    prog += n;
    scratch[SCR_APP_OFF] += n;
    cur.st = ST_APP_DATA;
    return;
}

case ST_APP_DATA:
    if (prog >= cur.a_sz) {
      log_reset();
      log_push(LT_BITMAP, (uint8_t)scratch[SCR_APP_LAST_BLK], 1);
      log_flush();
      compact_erase();
      comp_wait = true;
      cur.st = ST_APP_META;
      return;
    }
    scratch[SCR_APP_LEFT] = 0;
    cur.st = ST_APP_ALLOC;
    return;
```

Key operations:
```
write_off = scratch[2] % KNOTFS_BLOCK_SIZE
          =last_used% 4096
          = The offset of the writing starting point within the current block

space = KNOTFS_BLOCK_SIZE - write_off
      = How many bytes can the current block hold?

n = min(cur.a_sz - prog, space)
  = Number of bytes written this time (may be truncated by block boundaries)
```

Then `memcpy(tmp + write_off, s, n)` splices the new data into the correct position of tmp. If the data the user wants to append crosses the block boundary (for example, the last block has only 100 bytes left and the user appends 1000 bytes), then ST_APP_DATA will detect `prog < cur.a_sz`, set `scratch[1] = 0` to trigger the allocation of a new block, and then jump back to ST_APP_ALLOC to enter the next cycle.

```
Example of appending across block boundaries:

The file is currently 5000 bytes, block 0 is full (4096), block 1 has 904 bytes used (4096~4999)
Append 1500 bytes:

Round 1 (block 1, offset 904):
  write_off = 5000 % 4096 = 904
  space = 4096 - 904 = 3192
  n = min(1500, 3192) = 1500
  memcpy(tmp+904, buf, 1500) → all written into block 1, no boundary crossed
  prog = 1500 ≥ cur.a_sz → done

If appending 4000 bytes:
Round 1 (block 1, offset 904):
  n = min(4000, 3192) = 3192
  memcpy(tmp+904, buf, 3192) → block 1 is full
  prog = 3192 < 4000 → return to ST_APP_ALLOC

Round 2 (new block 2):
  write_off = (5000+3192) % 4096 = 0
  space = 4096
  n = min(4000-3192, 4096) = 808
  memcpy(tmp, buf+3192, 808)
  prog = 4000 ≥ cur.a_sz → done
```

## The fifth and sixth states: ST_APP_META + ST_APP_COMPACT - metadata implementation

```c
case ST_APP_META:
    compact_write();
    cur.st = ST_APP_COMPACT;
    return;

case ST_APP_COMPACT:
    compact_finish();
    log_commit();
    cur.st = ST_OK;
    return;
```

The meta phase of append is simpler than write. There is no need to release the old block (because there is no CoW replacement, just increment). It only needs to persist the new file entry (updated `nd->size` and possible new `nd->blocks[]`) to Flash through compact.

## Delete: Erase all traces of a file

Delete is the simplest operation in the file system. It does not need to read or write any data blocks, it only needs to do two things:
1. Release all blocks of the file (return free_bitmap)
2. Clear the file entry (so that the slot can be reused by new files)

KnotFS delete is completed in three states:

```c
case ST_DEL_LOOKUP:
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_DEL_NOFILE;
      cur.st = ST_ERR;
      return;
    }
    log_reset();
    for (i = 0; i < nd->block_count && i < KNOTFS_DIRECT_BLKS; i++) {
      if (nd->blocks[i] < KNOTFS_BLOCK_COUNT) {
        log_push(LT_BITMAP, (uint8_t)nd->blocks[i], 0);
        log_push(LT_USED, (uint8_t)nd->blocks[i], 0);
        mark_free(nd->blocks[i]);
      }
    }
    memset(nd, 0, sizeof(knode_t));
    log_flush();
    compact_erase();
    comp_wait = true;
    cur.st = ST_DEL_META;
    return;
```

Note that each block is logged twice: once for `LT_BITMAP` to mark free, and once for `LT_USED` to clear used_bytes. Why is it needed twice?

`LT_BITMAP` is responsible for free_map and marks whether the block is occupied. `LT_USED` is responsible for block_used_bytes, recording the number of valid data bytes in the block. In the simplified design of KnotFS, `LT_USED` does not have much significance for deletion (because used_bytes is no longer of concern after the block is free), but it is a requirement for the integrity of the log structure. Every change in free_bitmap should be accompanied by a change in used_bytes, so that log_replay can completely restore the state.

Then `memset(nd, 0, sizeof(knode_t))` directly clears the file entry. After `nd->size = 0`, this slot is reusable in `alloc_node`.

```
Streamlined process for deletion operations:

ST_DEL_LOOKUP:
  ① Find files → ② log_reset
  ③ Traverse all blocks: log_push(BITMAP, blk, 0) + log_push(USED, blk, 0) + mark_free
  ④ memset(nd, 0, sizeof(knode_t)) ← file entry clear
  ⑤ log_flush + compact_erase → jump

ST_DEL_META:
  compact_write → jump

ST_DEL_COMPACT:
  compact_finish + log_commit → ST_OK
```

> ⚠️ **Teaching Simplification Tip**: Here the delete of KnotFS directly clears the entry through `memset(nd, 0, sizeof(knode_t))`. The delete of the production-level solution involves complex processing of indirect blocks, and it is necessary to determine whether the indirect block (indirect block) has been released and whether it is referenced by other files. In addition, it does not directly clear the file entry, but marks the entry as DELETED through the FT Log (File Table Log), and only recycles it after compaction. Moreover, its `process_delete_file` needs to call `is_old_block()` when releasing a block to check whether the block is marked as to be released during the compression process to prevent the release of a block that is being referenced by SB compact.

## The semantic dividing line between append and write

You may ask: Why are there two APIs? Isn’t it okay to design append as a variant of write?

In KnotFS, `knotfs_write` is a **full replacement**, which does not matter whether the file exists before, CoW a brand new one. `knotfs_append` is **incremental modification**, keeping the existing data unchanged and appending it at the end.

These two semantics are controlled by the flag of `open` in POSIX system calls:
```
open("file", O_WRONLY | O_TRUNC); // Truncate write → corresponds to knotfs_write
open("file", O_WRONLY | O_APPEND); // Append writing → corresponds to knotfs_append
```

In embedded file systems, separating the two semantics has two benefits:
1. **Performance difference**: append only requires the last block of RMW, and write requires all reallocation. Separation can avoid unnecessary read operations in write.
2. **Metadata update amount**: append only updates the `size` of the file entry and a possible new `blocks[]`; write needs to update all `blocks[]`. The workload of compact is different.

## If you design

Try to answer: If the user loses power during the append process (for example, after appending 500 bytes and writing 200 bytes to Flash), what will he see next time he mounts? Answer: There are two possibilities. ① If compact has not been done yet, the old SB still points to the file status before appending (size=old value). Although the appended new data is on Flash, it is not within the scope of any file entry. After mounting, the file is restored to the size before appending, and the appended 200 bytes are lost. ② If compact has been written to the new SB but compact_finish has not been executed yet, mount will select the SB with the larger sequence. If it is a new SB, the file size = old value + 500. But only 200 bytes of Flash are valid appended data, and the remaining 300 bytes are unpredictable (0xFF or residual data). Therefore, the atomicity of **append is weaker than that of write**. Write is a full replacement of CoW. You will either see the complete old version or the complete new version. The intermediate state of append is "the file has become larger but the data is incomplete". This is a problem that requires additional processing in log-structured file systems, which is ensured by FT Log's atomic commit in production-level solutions.
