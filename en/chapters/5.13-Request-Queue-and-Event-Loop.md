# 5.13 Request Queue and Event Loop: Cooperative Non-Blocking Scheduling

## You only have one administrator but two hundred operations to handle

You don't have multithreading. You don't have a `pthread_create`. There is no `xTaskCreate` for FreeRTOS. You only have a `while` loop inside the `main` function.

But you need to handle it at the same time: the user types the write command on the command line, the Flash simulator is running the read and write delay, the compact process is asynchronously erasing SB, and the log buffer is waiting to be flushed... How can these "simultaneous" things be done in an O(n) single-threaded loop?

The answer is **event loop**. KnotFS's `knotfs_run()` is a miniature scheduler. Each time it is called, it advances a small step: letting the Flash simulator take a tick, checking whether the compact is completed, popping a request from the request queue, and advancing the current request's state machine one step. All non-blocking, all collaborative.

```
knotfs_run()'s "heartbeat pulse":

  ┌─────────────────────────────────────────────────┐
  │ 1. fdev_tick()      ← advance flash 1 tick     │
  │ 2. Check compact    ← wait for SB erase/write  │
  │ 3. Flash busy? return ← wait for device idle   │
  │ 4. Request done? dequeue next ← queue schedule │
  │ 5. Advance request state machine by 1 step     │
  │ 6. return true/false ← any work left?          │
  └─────────────────────────────────────────────────┘
```

## Request queue: capacity 4, but the current API only allows 1 pending request

KnotFS uses a fixed-size circular buffer to implement the request queue:

```c
/* knotfs.c: global queue */
#define Q_CAPACITY (4U)

static kreq_t q[Q_CAPACITY];
static int q_hd, q_tl, q_cnt;
```

The ring queue capacity is 4; however, the current public API directly returns ERR_Q_FULL when the queue is not empty or there is an operation in progress, so there is actually only 1 pending request at most. The caller must run the event loop between commits.

```c
static bool q_empty(void) { return q_cnt == 0; }
static bool q_full(void) { return (uint32_t)q_cnt >= Q_CAPACITY; }

static int q_push(kreq_t *r) {
  if (q_full())
    return ERR_Q_FULL;
  memcpy(&q[q_tl], r, sizeof(kreq_t));
  q_tl = (q_tl + 1) % Q_CAPACITY;
  q_cnt++;
  return 0;
}

static void q_pop(kreq_t *r) {
  if (q_empty()) {
    memset(r, 0, sizeof(*r));
    return;
  }
  memcpy(r, &q[q_hd], sizeof(kreq_t));
  q_hd = (q_hd + 1) % Q_CAPACITY;
  q_cnt--;
}
```

When joining the team, write `q_tl`, then `q_tl = (q_tl + 1) % Q_CAPACITY`. When leaving the queue, take it from `q_hd`, then `q_hd = (q_hd + 1) % Q_CAPACITY`. This is the most basic ring queue operation, with time complexity O(1) and no malloc required.

But you may find a problem: `q_cnt` is global, but does not have any lock protection. This is not a problem in KnotFS, because in the event loop model, all operations occur in the same call stack. The user calls `knotfs_write` to join the queue, and the event loop is not running at this time. Then the user calls `while(knotfs_run())` to consume the queue, and no other threads will join the queue at this time. Here's the benefit of single-threaded cooperative scheduling: you don't need locks.

## kreq_t: A request is a task order

```c
typedef struct {
  knot_op_t op;
  knot_st_t st;
  int result;
  char name[KNOTFS_NAME_LEN];
  const void *w_buf;
  uint32_t w_sz;
  void *r_buf;
  uint32_t r_sz;
  uint32_t r_off;
  uint32_t *r_out;
  const void *a_buf;
  uint32_t a_sz;
  knotfs_entry_t *ls_ents;
  uint32_t *ls_cnt;
  uint32_t *st_tot;
  uint32_t *st_free;
} kreq_t;
```

This structure uses a less elegant design: **All operation parameters share a union-less struct**. Use `w_buf/w_sz` for write operations, `r_buf/r_sz/r_off/r_out` for read operations, `a_buf/a_sz` for append operations, `ls_ents/ls_cnt` for list operations, and `st_tot/st_free` for statistical operations. At any one time, only one operation is running, so these fields do not conflict.

This is a common pattern in embedded programming, saving memory at the cost of type safety. A more standardized approach is to use `union` to add tags, but unions need to be handled carefully in MISRA C. Some coding standards prohibit mixing pointers and non-pointer types in unions. KnotFS chooses simplicity.

```c
/* Take knotfs_write as an example to see the enqueuing process */
int knotfs_write(const char *name, const void *buf, uint32_t size) {
  if (!name || !buf || !size || size > KNOTFS_FILE_LIMIT)
    return ERR_BAD_PARAM;
  if (!q_empty() || cur.op != OP_NONE)
    return ERR_Q_FULL;
  kreq_t r;
  memset(&r, 0, sizeof(r));
  r.op = OP_WRT;
  r.st = ST_WRT_INIT;
  strncpy(r.name, name, KNOTFS_NAME_LEN - 1);
  r.w_buf = buf;
  r.w_sz = size;
  return q_push(&r);
}
```

Note that for `if (!q_empty() || cur.op != OP_NONE) return -1`, if you try to submit a new request before the request has been processed, it will reject it directly. **KnotFS does not support request stacking**. The caller is responsible for waiting for the file system to be idle (`knotfs_is_idle()`) before submitting a new request.

## Event loop: A complete walkthrough of knotfs_run()

```c
bool knotfs_run(void) {
  fdev_tick();

  /* handle compact completion */
  if (comp_wait && fdev_idle()) {
    comp_wait = false;
  }

  if (!fdev_idle())
    return true;

  /* if current request done, dequeue next */
  if (cur.op != OP_NONE && (cur.st == ST_OK || cur.st == ST_ERR)) {
    if (!q_empty())
      q_pop(&cur);
    else
      cur.op = OP_NONE;
  }

  /* dequeue if idle */
  if (cur.op == OP_NONE && !q_empty()) {
    q_pop(&cur);
    prog = 0;
    subst = 0;
    memset(scratch, 0, sizeof(scratch));
  }

  /* advance state machine */
  if (cur.op != OP_NONE && cur.st != ST_OK && cur.st != ST_ERR) {
    switch (cur.op) {
    case OP_FMT: do_format(); break;
    case OP_MNT: do_mount();  break;
    case OP_WRT: do_write();  break;
    case OP_RD:  do_read();   break;
    case OP_APP: do_append(); break;
    case OP_DEL: do_delete(); break;
    case OP_LS:  do_list();   break;
    case OP_ST:  do_stats();  break;
    default: break;
    }
  }

  return !knotfs_is_idle();
}
```

Let’s break it down piece by piece:

Step 1: `fdev_tick()`, clock advancement of Flash emulator. Each tick is decremented by `fdev.ticks_left`. When it drops to 0, memcpy (read/write) or memset (erase) is actually executed. This is the physical layer of the event loop.**Step 2: Compact completes detection**, `comp_wait && fdev_idle()`. If compact is in progress and the Flash device is idle, the `comp_wait` flag is cleared. `comp_wait` is more like a residual flag; the actual advancement is determined by `fdev_idle()` and the state machine.

**Step 3: Return early when the device is busy**, `if (!fdev_idle()) return true`. If Flash is performing read and write operations, the entire state machine does not advance, because each step in the state machine depends on the result of the completion of the Flash operation. This is the most critical **choking point** in the event loop.

**Step 4: The current request is completed, and the next one is dequeued**. If the state of `cur` is ST_OK or ST_ERR, it means that the current request has been processed. Pop the next request from the queue. If there are no new requests, `cur.op = OP_NONE`.

**Step 5: Actively dequeue when idle**, if there is no request being processed (`cur.op == OP_NONE`) and the queue is not empty, pop a request to start processing. Reset `prog`, `subst` and `scratch[]` at the same time.

**Step 6: Advance state machine**, core scheduling. According to the value of `cur.op`, dispatch to the corresponding `do_xxx()` function. Each `do_xxx()` function executes a small step (a case branch) and then returns. The next time `knotfs_run()` is entered, this switch will be entered again to process the next state of the same op.

Step 7: `return !knotfs_is_idle()`, if there is still something to do (there are requests being processed or Flash is busy), return true; otherwise, return false. The caller uses this return value for polling: `while(knotfs_run());`.

## The power and cost of serialization

The design of KnotFS ensures that: **Only one request is executed at the same time.** This is the result of the event loop itself not allowing concurrency, rather than the mutual exclusion protection of multi-threads.

what does that mean?

```
Benefits of serialization:
  ✓ No mutex required - no race conditions
  ✓ No atomic operations required - all shared variable accesses are safe
  ✓ No need to consider deadlock - only one execution flow
  ✓ The intermediate states of the state machine are private - there is no "half-finished state read by another thread"
  ✓ Predictability – you know what you are doing every step of the way

The cost of serialization:
  ✗ No true I/O concurrency - reads cannot run in parallel with writes
  ✗ Request delays are cumulative; the current API actually only allows 1 pending request, and there will not be 3 waiters in the queue
  ✗ Unable to take advantage of multiple cores - low CPU utilization
  ✗ Long-term operations block the entire system - for example, format needs to erase 16 blocks, all of which must wait for you
```

For KnotFS teaching scenarios and the actual situation of embedded NOR Flash, serialization is completely acceptable. The Flash device itself is not multi-channel parallel and can only perform one operation (read or write or erase) at a time. The real concurrency occurs on another layer: network tasks (TCP service of the terminal), Flash I/O tasks, and file system state machine tasks. These three can run on different FreeRTOS tasks. But that's a problem for production-grade solutions to deal with.

## Scheduling timeline: a complete "write + read"

Let's take a look at the ticks in the scheduling process:

```
tick 0: user calls knotfs_write("hello.txt", "Hello!", 6)
        → q_push, there is 1 request in the queue
        → knotfs_write returns 0

tick 1: knotfs_run()
        → fdev_tick() (idle)
        → cur.op == OP_NONE, q_pop(&cur) — cur is now OP_WRT, ST_WRT_INIT
        → Advance state machine: do_write() → ST_WRT_INIT
          → alloc_node, calculate need=1, scratch[9]=1
          → cur.st = ST_WRT_ALLOC, return

tick 2: knotfs_run()
        → fdev_tick() (idle)
        → cur.st != ST_OK/ST_ERR, push state machine: ST_WRT_ALLOC
          → pick_lowest_wear() → block 2, mark_used
          → subst++=1, cur.st = ST_WRT_DATA (subst>=need), return

tick 3: knotfs_run()
        → fdev_tick() (idle)
        → Push state machine: ST_WRT_DATA
          → fdev_write(block2, tmp, 0, 4096) — ticks_left=2
          → subst++=2, return

tick 4: knotfs_run()
        → fdev_tick() — ticks_left=2→1, device is busy
        → !fdev_idle(), return true

tick 5: knotfs_run()
        → fdev_tick() — ticks_left=1→0, memcpy completed
        → fdev_idle()
        → cur.st=ST_WRT_DATA, push: subst(2)>=need(1) → cur.st=ST_WRT_META, return
        → cur.st is ST_WRT_META and is not OK/ERR, so the request is not changed.

tick 6: knotfs_run()
        → fdev_tick() (idle)
        → Push state machine: ST_WRT_META
          → log_push, compact_erase, comp_wait=true
          → cur.st = ST_WRT_META_FLUSH, return

tick 7~9: compact erase (3 ticks asynchronous wait)

tick 10: knotfs_run()
         → fdev_idle, comp_wait=false
→ Push state machine: ST_WRT_META_FLUSH
           → compact_write, cur.st = ST_WRT_COMPACT

tick 11~12: compact write (2 ticks)

tick 13: knotfs_run()
         → fdev_idle
         → Push state machine: ST_WRT_COMPACT
           → compact_finish, log_commit, cur.st = ST_OK

tick 14: knotfs_run()
         → cur.st == ST_OK, q_pop → empty, cur.op = OP_NONE
         → knotfs_is_idle() == true → return false
```

12 ticks to complete a 6-byte write operation. The tick here is the delay introduced by simulator scheduling; real NOR page programming is usually on the order of 100μs, and erasure is on the order of tens of milliseconds.

## Rejection strategy when the queue is full: let the caller try again

```c
if (!q_empty() || cur.op != OP_NONE)
  return ERR_Q_FULL;
```

KnotFS's API directly returns -1 when the queue is busy. **No blocking wait, no spin lock, no semaphore.** This is because the KnotFS API is designed to be called from FreeRTOS's synchronization wrapper layer, and the caller's thread can `vTaskDelay(10)` and then try again.

In `knotfs_test.c`, the test code does not need to be retried because `drive()` (i.e. `while(knotfs_run())`) is called immediately after each test call to the API, and the queue is empty before the next API call:

```c
static int drive(void) {
  int t = 0;
  while (knotfs_run()) {
    if (++t % 15 == 0)
      printf("    tick %d...\n", t);
  }
  if (t > 0 && t % 15 != 0)
    printf("    tick %d... done\n", t);
  return knotfs_get_result();
}
```

`drive()` is a synchronous blocking wrapper for the test program, a "wait until idle" implemented using polling. In a production-level deployment, this polling will be replaced by FreeRTOS's `xTaskNotifyWait`. The task is suspended when there are no events and is awakened when an event occurs.> ⚠️ **Teaching Simplification Tip**: The request queue of KnotFS here has a capacity of 4 but there is no timeout detection. The request queue of the production-level solution has a **timeout detection mechanism**. Each operation has an independent timeout period. After the timeout, the request is marked as failed and the task is notified.

## If you design

Try to answer: If KnotFS is moved to a real NOR Flash that "can only do one thing at a time", what needs to be changed in the event loop?

Answer: Just replace the `fdev_tick()` implementation. Change the RAM simulator to real Flash HAL calls, such as `callback_on_complete` mode. The structure of the event loop does not require any changes; it already assumes that "Flash is asynchronous and can only do one thing at a time."

Specifically: `fdev_tick()` no longer decrements `ticks_left`, but checks the hardware status register (SR) to see if the operation is complete. `fdev_read/write/erase` no longer sets `ticks_left`, but writes a command to the Flash control register and starts the operation. The `if (!fdev_idle()) return true` event loop is equivalent to "wait for the Flash operation to complete before advancing the state machine".

This is the core value of KnotFS teaching design, the event loop and the hardware abstraction layer are completely decoupled.
