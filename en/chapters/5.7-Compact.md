# 5.7 Compact: Rewriting the Catalog

The principle of Compact has been discussed in Chapter 3: when the SB Log accumulates too much, write the complete status in the memory (nodes[] + free_map + wear[]) to the spare SB slot and switch the active pointer. Look directly at the code here.

## Compact triggering conditions: each current metadata operation

```c
// knotfs.c
#define SB_HEADER_SZ     (sizeof(knot_sb_t))
#define LOG_ENTRY_SZ     (8U)
#define LOG_ENTRIES_MAX  ((KNOTFS_BLOCK_SIZE - SB_HEADER_SZ) / LOG_ENTRY_SZ)  /* (4096-668)/8 = 428 */
#define LOG_THRESHOLD    (LOG_ENTRIES_MAX * KNOTFS_LOG_THRESHOLD / 100U) /* 214 */
```

The Log area can hold up to 428 records. The current implementation is compact after every write/append/delete; `KNOTFS_LOG_THRESHOLD` (50%, about 214 entries) is only a reserved design and is not used in the code.

There are two reasons:

1. **Power-off safety**: compact itself requires a complete erase + write cycle. If the power is lost during compaction and the new SB is damaged, the old SB is still intact (because it has not been erased). However, if the Log area is filled to 90% and then compacted, the frequency of compaction will be reduced, but the more uncompacted Logs are lost each time a power failure occurs, there may be more changes only in the Log but not in the SB header before the power failure occurs, and the "window" of replay will be larger.

2. **Write buffer**: compact only writes the 668-byte SB header; whether the Log area is close to full will not change the amount of data written this time. 50% is an empirical balance point.

But please note: in KnotFS, the actual triggering of compact is manually triggered after each operation (write/append/delete) that requires persistent file entries, rather than automatically triggered by "log_count exceeds the threshold".

Look at the end of the write operation:

```c
// knotfs.c — write operation triggers compact
case ST_WRT_META: {
    /* ... Log records of releasing old blocks and allocating new blocks ... */
    compact_erase();
    comp_wait = true;
    cur.st = ST_WRT_META_FLUSH;
    return;
}
case ST_WRT_META_FLUSH:
    compact_write();
    cur.st = ST_WRT_COMPACT;
    return;

case ST_WRT_COMPACT:
    compact_finish();
    log_commit();
    cur.st = ST_OK;
    return;
```

This code exposes a key simplification of KnotFS: it triggers a complete compact process after every write/append/delete operation. It triggers compact to persist changes to file entries (name, size, block_count, blocks[] in nodes[]) to Flash, and it has nothing to do with whether the Log is full.

## Compact process: three-step dance

Compact is a three-step asynchronous process:

```
Compact asynchronous state machine
====================

                            start
                             ↓
              ┌───────────────────────────┐
   Step one: │ compact_erase() │
   compact │ → fdev_erase(tgt) │ Erase the opposite SB slot
   _erase │ → ticks_left = 3 │ (requires 3 ticks)
              └────────────┬─────────────┘
                           │ Waiting for fdev_idle()...
                           ↓
              ┌───────────────────────────┐
   Step 2: │ compact_write() │
   compact │ → memcpy(&compact_buf, │ Copy the current SB to the compact buffer
   _write │ &sb, ...) │ → increment sequence
              │ → Clean up log_offset/count │ → Write 668-byte SB header to the target block
              │ → fdev_write(tgt, ...) │ (requires 2 ticks)
              └────────────┬─────────────┘
                           │ Waiting for fdev_idle()...
                           ↓
              ┌───────────────────────────┐
   Step 3: │ compact_finish() │
   compact │ → sb.sequence++ │ Update the sequence number in memory
   _finish │ → sb.log_offset = 668 │ → Reset Log area
              │ → sb.log_count = 0 │
              └───────────────────────────┘
                             ↓
                          Complete
```

Let’s look at the code one by one.

**Step one: compact_erase**

```c
// knotfs.c
static void compact_erase(void) {
  uint32_t tgt = inactive_sb_slot();
  fdev_erase(tgt);
}
```

`inactive_sb_slot()` selects the block opposite the currently active SB, which is complementary to `active_sb_slot()`:

```c
// knotfs.c — A pair of mutually exclusive selectors for active and lazy slots
static uint32_t active_sb_slot(void) {
  return (sb.sequence & 1U) ? KNOTFS_SB1_BLK : KNOTFS_SB0_BLK;
}

static uint32_t inactive_sb_slot(void) {
  return (sb.sequence & 1U) ? KNOTFS_SB0_BLK : KNOTFS_SB1_BLK;
}
```

Logic: If the current sequence is an odd number, it means that the last compact was written to SB1 → the current active one is SB1 → the idle (compact target) is SB0. The reverse is true for even numbers. Log is added to the active slot (`log_flush` uses `active_sb_slot()`), and compact is used to cover the inactive slot. By alternating between SB0 and SB1, the wear of the two SB blocks is evened out.

**Step 2: compact_write**

```c
// knotfs.c
static void compact_write(void) {
  memcpy(&compact_buf, &sb, sizeof(knot_sb_t));
  compact_buf.sequence = sb.sequence + 1;
  compact_buf.log_offset = SB_HEADER_SZ;
  compact_buf.log_count = 0;
  compact_buf.crc32 = sb_checksum(&compact_buf);

  uint32_t tgt = inactive_sb_slot();
  fdev_write(tgt, &compact_buf, 0, sizeof(knot_sb_t));
}
```

There is a key detail here: `compact_buf` is a global static variable, not a stack variable. The reason has been mentioned in Section 5.3. `fdev_write` is asynchronous, and the stack variable will become invalid after the function returns. If compact_buf is a stack variable, memcpy in fdev_tick will read garbage data after 2 ticks.

`compact_buf.sequence = sb.sequence + 1`: The serial number of the new SB is 1 greater than the old SB. This is the basis for selecting "which update" when mounting later.

`compact_buf.log_count = 0`: The Log area of ​​the new SB is empty. All changes (block allocation/release) accumulated in the previous Log have been solidified into the SB header through the `sb.free_map` and `sb.nodes[]` operations called in the write/append/delete process.

**Step 3: compact_finish**

```c
// knotfs.c
static void compact_finish(void) {
  sb.sequence++;
  sb.log_offset = SB_HEADER_SZ;
  sb.log_count = 0;
}
```

What is updated in this step is the `sb` (currently active SB image) in the memory, making it consistent with the content that has been written to the Flash. If this step is not done, the sb in the memory will think that it is an old version, and compact may write to the same slot repeatedly next time.

## Compact coordination in the event loop

The three steps of compaction are not executed continuously in one function. They are broken into three steps, and each step requires waiting for `fdev_idle()`. This coordination work is done in the event loop:

```c
// knotfs.c — Completion of compact processing in event loop
if (comp_wait && fdev_idle()) {
  comp_wait = false;
}
```

`comp_wait` is set to true after `compact_erase`; the event loop clears Flash after detecting it is idle. The actual advancement is still determined by `fdev_idle()` and the state machine, and `comp_wait` is more like a residual flag.

The next case in the state machine will automatically enter the next step (for example, `ST_WRT_META` → `ST_WRT_META_FLUSH` → `ST_WRT_COMPACT`) and continue to advance the compact process.

## Why are compact writes and the compact states of ordinary writes managed separately?

Note the three states at the end of the write operation:

```
ST_WRT_META → Initiate compact_erase() → Transfer to ST_WRT_META_FLUSH
ST_WRT_META_FLUSH → Initiate compact_write() → Transfer to ST_WRT_COMPACT
ST_WRT_COMPACT → call compact_finish() → transfer to ST_OK
```

Why does compact occupy three states in the write state machine, instead of independent one state for the event loop to schedule?

Because in the simplified architecture of KnotFS, **compact is a sub-step** of the write/append/delete operation, not an independent background task. When the write operation enters ST_WRT_META, it knows that the Log has been accumulated, the metadata has been updated, and now the entire super block needs to be persisted. It must drive compact to complete by itself and cannot declare the write operation successful before compact is completed.

Production-level plans are different. It has an independent GC (garbage collection) module, compact runs as a background task and does not block file operations. The operation only needs to ensure that its Log record has been appended to the SB Log, and the remaining compact (consolidating the Log into a header and releasing the Log space) is completed by the GC in the background. This significantly reduces file operation latency.

## Library Metaphor: Rewriting the catalog is not tearing it down and rebuilding it

You manage a century-old hotel. The book cover is worn and the air is damp. You need to recatalog, but you can't tear down the entire library because there are still readers in it.

Compact is this recataloging process:

1. **Preserve the index structure (file entry nodes[]).** Recataloging does not change the collection structure. Originally there were 3 borrowing areas (3 files), but there are still 3 after recataloging. The number of books (file size) in each area also remains unchanged.

2. **Update catalog and tags (rewrite SB).** Tear off the old label (erase target block) and reattach the new label (write new SB). The label is new at this point, but the borrowing area and layout inside are the same as before.

3. **Change the directory cabinet to work (alternating SB0/SB1).** If you always label the same cabinet, that cabinet will wear out sooner than the others. So this time I use the front cabinet (SB0) and next time I use the back cabinet (SB1), alternately. Both cabinets aged together.

4. **Unregister the old one (the old SB becomes the new "opposite").** After the new SB is written, the cabinet where the old SB is located becomes the target cabinet for the next compact. In this way, every compaction "ping-pongs" between the two SB cabinets.

The difference between recataloging and reconstruction: the cost of recataloging is O (one erase and write of SB blocks), and the cost of reconstruction is O (one erase and write of all blocks). KnotFS will always only do compact (recatalog), not rebuild (rebuild).

>  ⚠️ Teaching Simplification Tip: KnotFS’s compact trigger frequency is much higher than that of production-level solutions. KnotFS triggers compact after each write/append/delete operation (to persist nodes[]), and the compact triggering condition of the production-level solution is "SB Log exceeds 50%  or FT Log exceeds 50%". Since it has independent FT blocks and FT Log, more than 90% of file operations do not require compact, they only need to append a record to the FT Log. This means that the SB slot wear of KnotFS is significantly higher than that of production-grade designs, depending on the load. For a teaching scenario (12 test cases, less than 100 compacts in total), this is not a problem. If two SB slots are alternately responsible for compacting, each slot will be erased approximately 100,000 times, and the total number of compactions will be approximately 200,000. In addition, the compact of the production-level solution (in the GC module) is an independent background task that does not block foreground file operations, which benefits from the asynchronous appending of SB Log and the design of independent FT Log.
