# 4.1 The LittleFS Design Philosophy: Minimal Metadata, Maximum Reliability

## You write files on a chip with 32KB of memory

Imagine a scene: in front of you is a Cortex-M4 microcontroller, 32KB RAM, 512KB ROM. It hangs a 4MB SPI NOR Flash and communicates with the main control through four lines (MISO/MOSI/SCK/CS). Your task is to provide a complete file system on this device that supports directory structure and does not lose data when powered off.

The first reaction in your mind is most likely: How is this possible?

For ext4, which I have learned in operating system classes, the kernel code size is measured in 100,000 lines, and the memory usage is measured in MB. Although the FAT series is simple, its FAT table needs to be maintained in memory, and your 32KB RAM cannot even fit a 4MB FAT table. SPIFFS is designed for embedded use, but it makes overly optimistic assumptions about the writing characteristics of NOR Flash: it relies on NOR Flash's feature of supporting byte-by-byte cumulative writing for metadata updates, and problems may occur if the Flash model is changed. YAFFS is designed for NAND, and its large page assumptions and OOB (Out-Of-Band) area concepts are completely inapplicable on NOR.

**In the field of embedded storage, file system design is a question of "which constraint tortures you the least". **

In Chapter 3, we established the theoretical basis of file system design, including block device abstraction, lessons learned from FAT, LFS log philosophy, triple protection of metadata, wear leveling, and power-off safety. In Chapter 5 we'll get our hands dirty implementing KnotFS, an educational file system that puts these theories into code.

And sandwiched in between is Chapter 4, a "contrast laboratory." We study LittleFS because it is currently one of the most successful open source implementations of embedded file systems; as to whether it is "better" than KnotFS, the two are products of different constraints. Its Metadata Pair, CTZ Skhipu-List, lookahead allocator, each data structure is an industrial-grade response to the theory of Chapter 3. **Understand the design decisions of LittleFS, and you will know when writing KnotFS in Chapter 5: where I copied industrial answers, where I had different constraints and needed to find new ways, and where industrial-level complexity was deliberately cut off in my teaching version. **

This is the background for the birth of LittleFS. In 2017, the ARM Mbed team (now maintained by the Linaro community) faced a classic embedded dilemma: they needed a file system, but it had to satisfy three almost contradictory requirements at the same time.

---

## Three competing demands

Let’s put these three requirements on the table:

**First: Power-Loss Resilience. **

There is no shutdown process for embedded devices. Your refrigerator control board, drone flight control, industrial sensors, and smart wearable devices may be powered off during any command cycle. If the file system is writing metadata at the moment of a power outage, such as copying a file's "directory entry" from an old location to a new location, the results may be catastrophic: the directory structure is damaged, files are orphaned, and the entire file system cannot be mounted.

This is not a matter of probability. If the design life of the equipment is 10 years and the power is off once a day, that is 3650 write-power-off states. As long as the "window period" of metadata update hits, the device will be useless.

```
Danger window for writing metadata
============================

[Erase old block] [Write new data] [Update pointer] [Write checksum]
    ^ ^
    | |
    └──── Power outage window ———— Power outage within this interval, ─────┘
         Old data erased, new data incomplete, file system corrupted
```

In an embedded system, you can't solve this problem by "adding a UPS." You must ensure that if the power is cut off at any time, the file system will either return to the previous complete state or reach the next complete state, never staying in an intermediate state.

**Second: Wear Leveling. **Each erase block (usually 4KB) of NOR Flash has an erase life limit. Consumer-grade chips can be erased approximately 100,000 times, and industrial-grade chips may be even less. If a file system writes the same block repeatedly, such as a FAT file system that rewrites the sector where the FAT table is located every time the file is updated, then the life of this block is the life of the entire device.

A more insidious problem is: the wear is not uniform. Metadata blocks (superblock, FAT table, inode table, directory area) are updated much more frequently than data blocks. A root directory's directory blocks may be updated every minute, while a log file's data blocks may be written only once a day. This means that the **metadata area will be worn out dozens of times earlier than the data area**.

```
The scary truth about uneven wear
=========================================

Metadata block (superblock): ████████████████████ written every minute
Metadata block (directory): ████████████████████ Written dozens of times per hour
Data blocks (log files): ████ written several times per day
Data blocks (configuration files): ██ Almost never written

              When the metadata block dies, the device dies.
              Even if 99% of the data blocks are still intact.
```

**Third: Bounded RAM/ROM (Bounded RAM/ROM). **

This is the most cruel one. Your RAM is only 32KB. You can't maintain an inode cache pool in memory like ext4, you can't build a B-tree to index free blocks like btrfs, and you can't initialize it by "scanning the whole disk first" because scanning means traversing all data, traversing means caching, and caching means RAM.

Moreover, the amount of RAM used must remain constant during runtime, whether there is 1 file or 10,000 files on the file system, whether the free space is 99% or 1%, the RAM you occupy must be the same. This requirement kills all the "allocate a dynamic array to cache something" solutions.

## LittleFS’s core answer: weld the log and COW together

Faced with these three requirements, the designers of LittleFS made a very smart observation.

Let’s look at two extreme designs first:

**Pure log file system (SPIFFS, JFFS2, YAFFS):**

The journaling file system treats the entire storage space as a ring buffer. Each write operation appends a new record to the end of this buffer. Because it is never overwritten in place, the safety of power outage is naturally guaranteed. During a power outage, at most the last unfinished appended record will be lost, while the previous status will be completely retained. At the same time, because the data is constantly "flowing" in the ring buffer, the wear is naturally even.

But the Achilles heel of journaling file systems is performance. Reading a file requires traversing from the beginning of the log to the end of the log. You are equivalent to reading "the entire history of this file from its creation to the present." SPIFFS attempts to use the rewritable feature of NOR Flash to optimize this, but at the cost of being bound to a specific physical medium. YAFFS uses RAM cache to speed up, but at the cost of O(n) memory growth. **The runtime of a pure journaling file system is either O(n²) or requires O(n) RAM, both of which are unacceptable in an embedded environment. **

```
Pure journaling file system
=========================================

Equipment:
┌──────┬──────┬─────┬─────┬─────┬──────┬──────┬──────┐
│ C │ newB │ newA │ │ A │ B │ │ │
│ │ │ │ → │ │ │ │ │
└──────┴──────┴──────┴─────┴──────┴──────┴──────┴───────┘
                              ↑
                        Writing direction (circular)

Want to read file A? Need to trace back from the latest "newA" record to the original "A" record
```

**COW (Copy-On-Write) file system (btrfs, ZFS):**

The core principle of the COW file system is "never modify in place". When you need to update a data block, you copy it to a new block, make changes to the new block, and then update the pointer to it, but the pointer is also stored in the block, so the pointer modification also triggers a copy... This process propagates upward until it reaches the root node.

The performance of COW is very good because the read path is O(log n) like a normal file system. But the problem is: (1) One write may trigger a series of level-by-level replications, amplifying the amount of writes; (2) The upward propagation of writes will concentrate the wear on the upper levels of the tree, and the wear on the root node block will be much more severe than that on the leaf nodes.

```
COW file system
=========================================

               ┌──────┐ ┌──────────┐
               │ root │ write file │ new root │
               │ │ ==> │ │
               └──────┘ └──────────┘
              ┌─┘ └─┐ ┌─┘ │
             │ │ │ ┌───────┘
             v v │ v
          ┌──────┐ ┌──────┐ │ ┌───────────┐
          │ A │ │ B │ │ │ new B │ ← copied B
          │ │ │ │ │ │ │
          └──────┘ └──────┘ │ └───────────┘
          ┌─┘ ┌─┘ └─┐ │ ┌─┘ │
         │ │ │ │ │ ┌───────┘
         v v v │ v v
      ┌──────┐ ┌──────┐ ┌──────┐ │ ┌──────────┐
      │ C │ │ D │ │ E │ │ │ new D │ ← copied D
      │ │ │ │ │ │ │ │ │
      └──────┘ └──────┘ └──────┘ │ └───────────┘

  D is modified → B is copied → root is copied → wear is concentrated on root
```

---

LittleFS's insight is: **The weaknesses of the two are antidotes to each other. **

The weakness of the log is poor runtime efficiency, but if the size of the log is limited to two pieces (metadata pair), the log operation becomes O(1) (because the input is bounded).The weakness of COW is that wear propagates upward, but if the "write once and copy" is changed to "write N times before copying" (Copy-on-Bounded-Writes, CObW), then the wear propagation will be divided by N on each layer. When N is large enough (larger than the branching factor), the upper layer no longer wears faster than the lower layer.

The combination of the two creates miracles: the metadata pair (small log) provides atomic update capabilities at any location; the CObW tree provides compact data storage and read performance. **Each solves the other's problem, and together they form a complete, elegant solution. **

```
LittleFS = log + welding of COW
=========================================

                    root ← This is a metadata pair (two blocks of logs)
                   ┌──────────┬──────────┐
                   │ A'│ B' │ │
                   │ │ │ → │
                   └──────────┴──────────┘
                ┌────┘ └─────────.
       A v B v
      ┌──────────┬──────────┐ ┌──────────┬───────────┐
      │ C'│ D' │ │ │ E'│new │ │
      │ │ │ → │ │ │ E' │ → │
      └──────────┴──────────┘ └───────────┴────────────┘
      ┌─┘ └─┐ ┌─┘ └──────────.
     v v │ v
┌────────┐ ┌────────┐ ┌─┘ ┌────────┐
│ C │ │ D │ v │ new E │ ← COW data block
└────────┘ └────────┘ ┌────────┐ └─────────┘
                       │ E │
                       └────────┘
```

This is the core design philosophy of LittleFS: **Metadata Pair (two pages of logs that back up each other) is responsible for atomic metadata submission, CTZ Skhipu-List (COW skhipu list) provides compact data storage, and Lookahead Buffer (fixed-size pre-search buffer) limits block allocation to bounded memory. **

## “Strong Guarantee”——LittleFS’s reliability philosophy

At the beginning of DESIGN.md, the designer of LittleFS wrote a paragraph that can be regarded as the "constitution" of this file system:

> “The question was: How would you build a filesystem that is resilient to power-loss and flash wear without using unbounded memory?”

The translation is: **"How to build a file system that is both power-off and wear-resistant without unlimited memory?"**

This question defines all design decisions for LittleFS. It is not a "I want to make a file system with the best performance", nor is it "I want to make a file system with the most functions". Its goal is extremely focused: ensuring data integrity in the harshest embedded environments. **

Let’s look at what exactly the “strong guarantees” provided by LittleFS are:

**1. Atomic directory submission. ** LittleFS is not "as atomic as possible", it guarantees the atomicity of directory operations. A directory commit (create files, delete files, rename files...) either happens completely or not at all. Submit and append to the active block when there is space; only compaction/split writes the spare block, and the active state is exchanged after writing. Atomicity comes from the fact that the old CRC is still valid and double copied.

**2. Bounded RAM. **The RAM usage of LittleFS has nothing to do with the size of the file system, the number of files, and the size of the files. Whether you have 1GB or 1MB of storage space, the RAM occupied by LittleFS is fixed and determined by the compile-time configuration. This is very difficult to achieve. It means that you cannot cache file lists, inodes, free block bitmaps... every common optimization method is prohibited.

**3. Dynamic wear leveling. ** LittleFS does not maintain precise erase counts for each block (that requires additional memory), but implements wear leveling through statistical distribution. When allocating free blocks, the block allocator always continues to scan forward from where it last stopped, forming an even allocation pattern that surrounds the device. At the same time, during each mount, a random seed based on disk CRC is used to determine the starting offset of allocation, ensuring that the allocation mode is different after each power-on.

**4. Bad block detection and recovery. ** When the caller requests verification and the program cache is flushed, LittleFS will read back the data and compare. It does not have a persistent bad block table and retries rely on block device errors and reallocations. This is achieved through the natural ability of the CObW structure, any block can be replaced losslessly in a COW operation.These four guarantees form the bottom line of LittleFS reliability. **It does not promise the fastest speed, it does not promise the least write amplification, but it does promise: in any power loss scenario, your data will be either complete or recoverable. **

## Positive comparison with FAT, SPIFFS, YAFFS

A table is worth a thousand words:

```
File system comparison
======================================================
              LittleFS FAT32 SPIFFS YAFFS2
---------------------------------------------------------------
Power outage safety ✅ Atomic ❌ Danger ✅ Log ✅ Log
Wear Leveling ✅ Dynamic ❌ None ✅ Perfect ✅ Perfect
Bounded RAM ✅ Yes ⚠️ Configurable ❌ No ❌ No
Code size ~7K lines ~3K lines ~4K lines ~15K lines
Target media NOR/NAND disk NOR NAND
Dynamic Bad Block Management ✅ Yes ❌ No ❌ No ✅ Yes
Directory structure tree + linked list tree flat tree
File name length: up to 255 8+3/255 up to 255 up to 255
Maximum file size 2GB 4GB No limit No limit
Need to close the operation ✅ sync ✅ Yes ✅ Yes ✅ Yes
======================================================
```

FAT is a "file system that accidentally became an embedded standard." It is simple and widely supported, but its FAT table is a single point of failure: a damaged FAT table means that the entire file system's directory structure is lost. Moreover, FAT does not have any power-down protection. Cutting off power when modifying the FAT table in situ is equivalent to suicide.

SPIFFS is specially designed for SPI NOR Flash. It takes advantage of a characteristic of NOR Flash: changing 1 to 0 does not require erasure (only programming), so it can gradually write data on an erased page. This allows SPIFFS to be a RAM-free journaling file system. However, this strategy is bound to physical characteristics and cannot be used on NAND, nor can it be used on some NOR chips that do not guarantee "invariance of accumulated writes". Moreover, SPIFFS garbage collection takes O(n²) time, and the performance is severely degraded on large file systems.

YAFFS is a classic in the NAND world. It uses NAND's OOB (spare area) to store metadata tags and implements a highly optimized log structure. However, its design is deeply bound to the NAND page structure (2KB data + 64B OOB) and cannot work at all on NOR Flash.

**LittleFS has chosen a different path: it is not tied to any special properties of physical media. It requires four required callbacks: read, prog, erase, and sync (lock/unlock optional), which are three basic operations supported by all Flash. This minimalist abstraction allows it to run on NOR, NAND, eMMC, SD cards, and even RAM disks. Its reliability is achieved through pure software algorithms (metadata pair + CRC + atomic commit) and does not rely on any special capabilities of the hardware. **

## Data structure panorama: from Superblock to CTZ Skhipu-List

The on-disk data structure of LittleFS forms a clearly hierarchical system that performs its own duties:

```
Overview of LittleFS data structures
=========================================

                    ┌──────────────────────┐
                    │ lfs_t (RAM) │ ← Runtime status
                    │ root[2], cache, │
                    │ global state, lookahead │
                    └──────────┬───────────┘
                               │
                    ┌──────────┴───────────┐
                    │ Superblock Pair │ ← Two blocks, block 0 and block 1
                    │ (embedded in the root directory) │ Store version number, block size, number of blocks, etc.
                    └──────────┬───────────┘
                               │
                    ┌──────────┴───────────┐
                    │ Metadata Pair │ ← One per directory
                    │ (two blocks alternate) │ Atomic commit log
                    │ revision + tag + data │
                    └──────────┬───────────┘
                               │
               ┌────────────────┼────────────────┐
               │ │ │
        ┌──────┴──────┐ ┌──────┴──────┐ ┌──────┴───────┐
        │ File Entry │ │ File Entry │ │ Dir Entry │ ← Directory Entry
        │ name+CTZ │ │ name+CTZ │ │ name+pair │
        └──────┬──────┘ └──────┬──────┘ └──────┬───────┘
               │ │ │
        ┌──────┴──────┐ ┌──────┴──────┐ ┌──────┴───────┐
        │ CTZ Skhipu- │ │ Inline │ │ Subdirectory │
        │ List (COW) │ │ Small files │ │ Metadata │
        │ │ │ (directly save to directory)│ │ Pair │
        └─────────────┘ └────────────┘ └──────────────┘
```

Breakdown of core concepts:

**Superblock:** LittleFS's superblock is a special entry embedded in the metadata pair of the root directory. Its content is very simple: file system version number, block size, number of blocks, maximum name length, maximum file size, maximum attribute size, a total of 6 fields, 24 bytes. This reflects LittleFS's "metadata minimization" principle.

```c
// superblock structure in lfs.h
typedef struct lfs_superblock {
    uint32_t version;
    lfs_size_t block_size;
    lfs_size_t block_count;
    lfs_size_t name_max;
    lfs_size_t file_max;
    lfs_size_t attr_max;
} lfs_superblock_t;
```

Yes, that's all. No magic number, no mount count, no last check time, no volume label, no redundant information whatsoever. The superblock of the teaching-level implementation (KnotFS in Chapter 3) is much "bloated" in comparison (including version number, block size, volume label, mount status, etc.), but the design context of the two is different: the superblock of KnotFS is two independent blocks, while the superblock of LittleFS is just an entry in the root directory, and the metadata pair of the root directory itself already provides CRC checksum revision protection.

**Metadata Pair:** This is the core invention of LittleFS. Each directory (including the root directory) is associated with a metadata pair, that is, two physical blocks, one active and one standby. All modifications to the directory (creating files, deleting files, updating file sizes...) are written to the active block in the form of "append entries". When the active block is full, compaction is triggered, and the still valid entries are copied to the spare block, and then the spare block is flipped to the new active block and the old block is erased.This process naturally guarantees atomicity: in the last step before compaction writes the CRC checksum, if the power is lost, the data on the old block will still be intact. After writing the CRC, the new block becomes an active block. Although the content of the old block is still complete, it is no longer the "latest version". This is a safe state: you only have two options: "old data" and "new data", and there is no third "partially written" corruption state.

**CTZ Skhipu-List:** This is a pure COW data structure, specially designed for append writing and random reading of files. Blocks are linked in the form of a "backward skhipu list". Each block contains a number of pointers to previous blocks. The number of pointers is determined by the binary tail zeros (CTZ, Count Trailing Zeros) of the index of the block. This makes append operations O(1) (only the last block needs to be created) and random reads O(log n) (quickly skhipuping irrelevant blocks via skhipu lists).

The CTZ jump table also has an exquisite design: **Only one pointer (head) and a size (size) are needed to uniquely determine the entire jump table. ** Because given the block index, you can calculate how many pointers it should have through the CTZ formula, and then calculate the position of each byte. This minimizes the storage overhead of metadata. To store a file in a directory, you only need to record its name, type, and two values ​​(ctz_head, ctz_size).

## The trade-offs you must accept

Any design is a trade-off. The design philosophy of LittleFS is "to be reliable, to save memory, and to be resistant to wear and tear". These three goals are ranked significantly higher than "to be fast" and "to save storage space". But you have to know what these trade-offs mean to you:

**1. Storage utilization. ** The two-block structure of the Metadata pair means that in the best case (no splitting), your metadata space utilization is 50% (one active and one standby). Coupled with the 50% threshold of compaction (starting splitting when it reaches 50% instead of waiting for 100%), the actual metadata utilization is about 25%. This means that if you have 128 4KB blocks, the metadata pair of the root directory takes up at least 8KB, and the actual metadata that can be stored is only about 2KB, enough to store dozens of directory entries.

**2. Additional performance. ** The addition of CTZ skhipu table is O(1), but each time you append a new block, you need to allocate the block, erase the block, write the skhipu table pointer in the new block, and copy part of the data of the old block. Compared to in-place modification (such as FAT), the write amplification factor is 1.5-2 times.

**3. Cost of random writes. ** If you modify a block of data in the middle of the file, the CTZ jump table needs to recreate the entire chain from that point, copying each subsequent block. Random writing is O(n). This reflects LittleFS's assumption that "files are mainly written appended": for log files, configuration files, and data collection scenarios, the assumption is true; for database files and frequently modified binary files, you need to be mentally prepared.

**4. Initialization overhead of orphan traversal. ** When mounting, LittleFS will traverse the entire directory list to check whether there are orphan directories. The time complexity of this operation is O(n²) because it requires a cross comparison for each directory pair and each directory entry. For file systems with a large number of directories, mount times can be long. Fortunately, LittleFS designed a global state mechanism to avoid full checks in most cases.

## From design document to 6500 lines of C code

LittleFS's DESIGN.md can be called a model of embedded software design documents. It does not tell you "how the code is written", but tells you "why it is written like this". From "Why the metadata pair is two blocks instead of three blocks", to "OEIS mathematical derivation of CTZ formula", to "xorshift entropy source selection of random number seeds", every design decision has a clear reason.The 6500 lines of lfs.c is a faithful execution of the design document. Almost all the core logic is in one file. There is no "magic" of dynamic memory allocation. Every function is small and clear, and every data structure has a clear on-disk format.
