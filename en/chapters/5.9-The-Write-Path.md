# 5.9 The Write Path: A Full State-Machine Walkthrough

## Watch the whole drama first, then watch each scene

Before jumping into the line-by-line code, here's a peek at the play's full program. A write to KnotFS, from API call to completion, has a total of **6 states**:

```
State machine panorama
=======================

ST_WRT_INIT - Find files with the same name, record old blocks, allocate new file entries
    ↓
ST_WRT_ALLOC - allocate free blocks for new data (pick_lowest_wear)
    ↓
ST_WRT_DATA - Write user data to tmp buffer and initiate Flash write (CoW core)
    ↓
ST_WRT_META - mark old blocks as free (log_push), update file entries, compact persistence
    ↓
ST_WRT_META_FLUSH - wait for erase to complete, compact_write writes new SB
    ↓
ST_WRT_COMPACT —— compact_finish update sequence, log_commit confirm submission
    ↓
ST_OK → Notify the caller
```

These 6 states are 6 frames, not 6 function calls. Between each frame, `knotfs_run()` is called once, advancing one Tick. Flash erasing and writing are done asynchronously from frame to frame.

> Note: In the current implementation, Log mainly remains in the memory, and the real persistence is the compact in the META stage; do not understand it as the WAL that has been placed on the disk.

Below are the details of each scene.

## You are not running a function, you are performing a drama

You called `knotfs_write("hello.txt", buf, 11)`. You expect that after this function is executed, the file will be written.

It doesn't. It just puts a note into the request queue and returns.

Then `knotfs_run()` is called repeatedly. In the KnotFS test program, `while(knotfs_run())` is idling. Each call is a scene. The state machine jumps from `ST_WRT_INIT` to `ST_WRT_ALLOC`, then to `ST_WRT_DATA`... Between each jump, the Flash simulator is executing read and write delays. This is a six-act play. After each act, the actors have to wait for the props team to bring up the scenery for the next scene, rather than synchronous function calls.

Let's follow the script of this drama.


---

## Act 1: ST_WRT_INIT - Find the old bookshelf and apply for a new bookshelf

```
What ST_WRT_INIT does:
  1. Find whether a file with the same name exists
  2. If it exists, record its old block number (for preparation of CoW release)
  3. Clear the size of the old entry (let alloc_node empty this slot)
  4. Calculate how many blocks are needed for new data
  5. Allocate a new entry and fill in the file name, size, and block_count
  6. Store the old block information in the scratch[] array (for cross-state transfer)
```

Here is a counter-intuitive operation: `nd->size = 0`. What it clears is the old entry, but the pointer `nd` points to the slot in `sb.nodes[]`. `alloc_node` will reuse it when it encounters size==0 when traversing `sb.nodes[]`. Therefore, clearing the size of the old entry is to allow `alloc_node` to "recycle" this slot to put new entry information with the same name, instead of giving up this slot:

```c
case ST_WRT_INIT:
    nd = find_node(cur.name);
    oldcnt = 0;
    if (nd) {
      for (i = 0; i < nd->block_count && i < KNOTFS_DIRECT_BLKS; i++)
        oldb[i] = nd->blocks[i];
      oldcnt = nd->block_count;
      nd->size = 0; /* invalidate old entry so alloc_node won't skip it */
    }
    need = (cur.w_sz + KNOTFS_BLOCK_SIZE - 1) / KNOTFS_BLOCK_SIZE;
    if (need > KNOTFS_DIRECT_BLKS) {
      cur.result = ERR_TOO_MANY;
      cur.st = ST_ERR;
      return;
    }
    nd = alloc_node(cur.name);
    if (!nd) {
      cur.result = ERR_NO_NODE;
      cur.st = ST_ERR;
      return;
    }
    nd->size = cur.w_sz;
    nd->block_count = (uint32_t)need;

    scratch[SCR_OLD_CNT] = oldcnt;
    for (i = 0; i < oldcnt && i < KNOTFS_DIRECT_BLKS; i++)
      scratch[SCR_OLD_BLK(i)] = oldb[i];
    scratch[SCR_NEW_NEED] = need;
    subst = 0;
    cur.st = ST_WRT_ALLOC;
    return;
```

The `scratch[]` array is a bridge for passing parameters across states in the KnotFS state machine. Because each time the state machine enters, it can only know "which state I am in" through `cur.st`, and what is shared between each state is a `static uint32_t scratch[16]` array, a global sticky note. `scratch[0]` stores the old block count, `scratch[1..8]` stores the old block number, and `scratch[9]` stores the new block demand number. It's not an elegant design, but it is transparent.

## Act 2: ST_WRT_ALLOC - Block Selection for Wear Leveling

```c
case ST_WRT_ALLOC:
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_COPY;
      cur.st = ST_ERR;
      return;
    }
    need = scratch[SCR_NEW_NEED];
    if (subst >= need) {
      subst = 0;
      cur.st = ST_WRT_DATA;
      return;
    }

    {
      uint32_t blk = pick_lowest_wear();
      if (blk >= KNOTFS_BLOCK_COUNT) {
        cur.result = ERR_NO_BLK;
        cur.st = ST_ERR;
        return;
      }
      mark_used(blk);
      sb.wear[blk]++;
      nd->blocks[subst] = blk;
    }
    subst++;
    return;
```

Pay attention to the usage of `subst`: it is both a block serial number index and a counter of "how many blocks have been allocated". Each call `pick_lowest_wear()`, `subst++`, then `return`. On the next tick, the state machine re-enters ST_WRT_ALLOC, and `subst` continues to increment until it reaches `need`.

There is a key to asynchronous here: `pick_lowest_wear` itself is synchronous (it just traverses the memory array), but the state jump after it is asynchronous. The state machine design principle of KnotFS is: each state only does "one thing", returns when done, and returns control to the event loop. When the next tick comes in, the state machine re-enters from the top of this state. If the thing is not done yet (for example, there are still blocks to be allocated), do it again and return.

The implementation of `pick_lowest_wear` is simple but effective:

```c
static uint32_t pick_lowest_wear(void) {
  uint32_t best = KNOTFS_BLOCK_COUNT;
  uint32_t best_w = 0xFFFFFFFFU;
  for (uint32_t i = KNOTFS_DATA_START; i < KNOTFS_BLOCK_COUNT; i++) {
    if (!(sb.free_map & (1U << i)) && sb.wear[i] < best_w) {
      best_w = sb.wear[i];
      best = i;
    }
  }
  return best;
}
```

It traverses the data area (block 2~15), only considers the blocks marked FREE in the free_bitmap (`!(sb.free_map & (1U << i))`), and then selects the one with the smallest wear_count. `sb.wear[blk]++` after each allocation. wear_count is a 32-bit unsigned integer. Long before overflow, the typical life of NOR Flash has come to an end (100,000 erases and writes).

## Act III: ST_WRT_DATA - Asynchronous delay of Flash programming

```c
case ST_WRT_DATA: {
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_COPY;
      cur.st = ST_ERR;
      return;
    }
    need = scratch[SCR_NEW_NEED];
    if (subst >= need) {
      cur.st = ST_WRT_META;
      return;
    }

    uint32_t blk = nd->blocks[subst];
    uint32_t off = subst * KNOTFS_BLOCK_SIZE;
    uint32_t rem = cur.w_sz - off;
    uint32_t n = (rem < KNOTFS_BLOCK_SIZE) ? rem : KNOTFS_BLOCK_SIZE;
    const uint8_t *s = (const uint8_t *)cur.w_buf + off;

    memcpy(tmp, s, n);
    if (n < KNOTFS_BLOCK_SIZE)
      memset(tmp + n, 0xFF, KNOTFS_BLOCK_SIZE - n);
    fdev_write(blk, tmp, 0, KNOTFS_BLOCK_SIZE);
    subst++;
    return;
}
```

This paragraph does several important things:

1. **Data Segmentation**: Cut the user buffer into 4KB fragments according to block boundaries. `off = subst * KNOTFS_BLOCK_SIZE` calculates the starting offset of the current block, and `rem = cur.w_sz - off` calculates how much data is left. The last block may be less than 4KB.

2. **0xFF padding**: After Flash is erased, it is all 1 (0xFF). KnotFS maintains this convention. If the last block is less than 4KB, the remaining bytes are filled with 0xFF. This is the standard state of the "unprogrammed area" on NOR Flash.

3. `fdev_write` has a delay of 2 ticks: `fdev_write` sets `fdev.ticks_left = 2`. This means that on the next `knotfs_run()` and the next `knotfs_run()`, `fdev_tick()` will be `continue` (because of `ticks_left > 0`). It is not until the third tick that the data is actually `memcpy` to the flash array.

4. Return after `subst++`: ST_WRT_DATA writes one block at a time. After writing, the state machine returns and enters ST_WRT_DATA on the next tick. However, if `subst >= need` (all blocks have been written), it jumps to ST_WRT_META.

```
Timeline of asynchronous writing (taking 3 blocks as an example):

tick 0: ST_WRT_DATA(subst=0) → fdev_write(block A) [ticks_left=2]
tick 1: fdev_tick → ticks_left=1 → The device is busy and the state machine is not advanced.
tick 2: fdev_tick → ticks_left=0 → memcpy completed, device idle
tick 3: ST_WRT_DATA(subst=1) → fdev_write(block B) [ticks_left=2]
tick 4: fdev_tick → ticks_left=1
tick 5: fdev_tick → memcpy completed
tick 6: ST_WRT_DATA(subst=2) → fdev_write(block C) [ticks_left=2]
tick 7: fdev_tick → ticks_left=1
tick 8: fdev_tick → memcpy completed
tick 9: ST_WRT_DATA(subst=3) → subst>=need → jump to ST_WRT_META
```

Writing three blocks of data consumes 10 ticks. This is why there is a progress print of `tick % 15 == 0` in the `drive()` function of the test program, because the asynchronous delay makes everything slower, but in exchange for a controllable state.

## Act 4: ST_WRT_META - Write Log and start Compact

```
ST_WRT_META does:
  1. log_reset() — clear the Log buffer
  2. Traverse the old block list, log_push(LT_BITMAP, blk, 0) + mark_free — release the old block
  3. Traverse the new block list, log_push(LT_BITMAP, blk, 1) — occupy the new block
  4. compact_erase() — Erase inactive SB slots
  5. Wait for compact to complete
```

```c
case ST_WRT_META: {
    log_reset();
    oldcnt = scratch[SCR_OLD_CNT];
    for (i = 0; i < oldcnt && i < KNOTFS_DIRECT_BLKS; i++) {
      uint32_t blk = scratch[SCR_OLD_BLK(i)];
      if (blk < KNOTFS_BLOCK_COUNT) {
        log_push(LT_BITMAP, (uint8_t)blk, 0);
        mark_free(blk);
      }
    }
    need = scratch[SCR_NEW_NEED];
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_COPY;
      cur.st = ST_ERR;
      return;
    }
    for (i = 0; i < need && i < KNOTFS_DIRECT_BLKS; i++)
      log_push(LT_BITMAP, (uint8_t)nd->blocks[i], 1);

    compact_erase();
    comp_wait = true;
    cur.st = ST_WRT_META_FLUSH;
    return;
}
```

`log_push` only appends an 8-byte record to the memory buffer `log_buf[]` and does not involve Flash operations. `compact_erase()` starts the erase process (3 tick delay). `comp_wait = true` tells the event loop to wait for compact to complete.

There is an easily overlooked detail here: `mark_free(blk)` directly modifies `sb.free_map` in memory. This means that from this moment on, the old block is FREE from a memory perspective. However, since compact has not yet been completed (the SB on Flash is still an old version), if the power is cut off now, the old SB will be loaded the next time the mount is performed, and the old blocks will still be USED. So this "advance" operation of `mark_free` is safe because it only really takes effect after compact is successful.

## Act 5: ST_WRT_META_FLUSH - New SB after writing Compact

```c
case ST_WRT_META_FLUSH:
    compact_write();
    cur.st = ST_WRT_COMPACT;
    return;
```

`compact_write()` does three things:
1. Completely copy the SB in the memory to `compact_buf`
2. Set `compact_buf.sequence` to `sb.sequence + 1`
3. `fdev_write(target_slot, &compact_buf, 0, sizeof(knot_sb_t))`, start a write delay of 2 ticks


---

## Act Six: ST_WRT_COMPACT - Declare the new directory to take effect

```c
case ST_WRT_COMPACT:
    compact_finish();
    log_commit();
    cur.st = ST_OK;
    return;
```

`compact_finish()`：
```c
static void compact_finish(void) {
  sb.sequence++;
  sb.log_offset = SB_HEADER_SZ;
  sb.log_count = 0;
}
```

`sb.sequence++` declares: "From now on, the new SB is the authoritative version." `log_offset` returns to the initial position and `log_count` is cleared. `log_commit()` is also a line: `sb.log_count += log_cnt; log_cnt = 0;`, and the accumulated number of log entries is recorded in SB.


---

## Act 7: ST_OK - next request can be processed

`cur.st = ST_OK`. The event loop detects `cur.st == ST_OK` and pops the next request from the queue. If there are no new requests, `cur.op = OP_NONE`. The file system returns to idle.

## State machine overview diagram

```
knotfs_write("hello.txt", data, 8192)
      │
      ▼
[Enqueue ──→ Event loop starts scheduling]
      │
      ▼
  ST_WRT_INIT ────── find old entry, record old blocks, allocate new entry
      │
      ▼
  ST_WRT_ALLOC ───── allocate block 0 (pick_lowest_wear, sync)
      │ return (continue next tick)
      ├── ST_WRT_ALLOC ── allocate block 1
      │ return
      └── subst>=need → jump
      │
      ▼
  ST_WRT_DATA ─────── write block 0 (fdev_write, 2 ticks async)
      │ …wait ticks_left=0…
      ├── ST_WRT_DATA ── write block 1
      │ …wait ticks_left=0…
      └── subst>=need → jump
      │
      ▼
  ST_WRT_META ─────── write Log (free old + use new), compact_erase(3 ticks)
      │ …wait ticks_left=0…
      ▼
  ST_WRT_META_FLUSH ─ compact_write(2 ticks)
      │ …wait ticks_left=0…
      ▼
  ST_WRT_COMPACT ──── compact_finish + log_commit
      │
      ▼
  ST_OK ──────────── file write complete ✓
```

## The "asynchronous philosophy" of state machines

Every state of KnotFS is **non-blocking**. No state will "wait". It will either complete the task and jump to the next state, or submit an asynchronous operation and return, returning control to the event loop. When the asynchronous operation completes (`fdev_idle() == true`), the event loop re-enters the state machine, and the state machine is re-entered from the top of the same `case`.

This model has several advantages:

1. **Stackless switching**: No OS thread/coroutine support is required, it can be achieved by pure C function call + switch/case.
2. **Observable**: The behavior of each tick is deterministic. You can accurately know which state it is currently in and what operations Flash is doing.
3. **Testable**: The test program can accurately control the time advancement by controlling the number of calls to `knotfs_run()`.
4. **Portable**: By replacing the underlying implementation of `fdev_read/write/erase`, KnotFS can be migrated to any platform that supports asynchronous I/O.

> ⚠️ **Teaching Simplification Tips**: The write state machine of KnotFS here has 6 states (INIT→ALLOC→DATA→META→META_FLUSH→COMPACT). The write state machine of the production-level solution has 9 sub-states for metadata update, because in addition to SB Log, it also has FT Log (file table log), which requires additional state processing: SB compact → FT compact → log prepare → flush → commit. Moreover, its alloc and data stages also need to handle the loading and saving of indirect blocks. KnotFS does not have indirect blocks, so don't worry about it.

## If you design

Now try to answer: If the delay of `fdev_write` is 10 ticks instead of 2 ticks, how does the state machine of the write operation change?

Answer: The state machine itself does not require any changes. It is only responsible for submitting the write request (`fdev_write` sets `ticks_left`) and then returns. The length of the delay only affects the number of ticks that pass between the next tick and the actual writing of the data. The event loop decrements `ticks_left` in `fdev_tick()`, checking whether it is 0 after each decrement. This is the charm of asynchronous programming: decoupling delay parameters and business logic.
