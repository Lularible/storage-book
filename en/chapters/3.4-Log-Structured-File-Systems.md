# 3.4 Log-Structured File Systems: Append, Never Overwrite

## You have a typewriter that never corrects typos

Imagine a scenario: You have an old-fashioned typewriter. Unlike your grandfather's, this is an "append-only, not backwards" typewriter. You can only type forward. You can't backspace. You can't apply correction fluid. You cannot pull the paper out and write on the back.

What should you do if you typed a word wrong?

You press enter and write the correction on a new line. The old line just stays there, a piece of history, a record of a program that never needs to be deleted.

This is the core idea of ​​Log-Structured File System (LFS): **You always only append, never overwrite. Old data are not deleted, they die naturally (and are cleaned up by subsequent garbage collection).**

This idea was born in the famous paper "The Design and Implementation of a Log-Structured File System" by Mendel Rosenblum and John Ousterhout in 1992. This paper was originally designed to solve the problem of "lower write amplification" of disks, which is the seek overhead caused by many small simultaneous writes on the disk. But they found that this design naturally fit perfectly with the physical characteristics of Flash.

---

## Insights from 1992: Why Disks Hate Small Writes

In 1992, the performance bottleneck of disks was seek time. A random seek takes about 10 milliseconds. If you were to log 100 times per second, updating an inode and a data block each time, that's 200 random seeks per second, about 2 seconds of pure seek latency. Disk throughput collapses.

Rosenblum and Ousterhout's observation is: "If we append both inode and data block writes to the end of a continuous log stream, then the disk's write head never needs to move. It just needs to stay in one place and keep writing."

```
In-place update vs log append on disk
=======================

In-place update (traditional FS, such as Unix FFS):
  Disk layout:
  ┌──────┬──────┬─────┬─────┬──────┬──────┐
  │inode1│inode2│Block A │Block B │Block C │Block D │
  └──────┴───────┴──────┴──────┴──────┴───────┘
    ↑ ↑ ↑ ↑ ↑ ↑
  Every time an inode or data block is modified, the head must move to the corresponding position.
  Seek latency ≈ 100 times write latency

Log append (LFS):
  Disk layout:
  ┌─────────────────────────────────────────────
  │ inode1 │Block A│inode2│Block B│inode1│Block A'│inode3│Block C│ ... → Log stream → │
  └──────────────────────────────────────────┘
                    ↑ The head stays here and writes more
                    No need to search! Write speed = disk sequential write speed
```

But here is a core question: **If data block A is appended with a new version (block A'), what about the old version (block A)?**

Answer: Old block A becomes "garbage", waiting to be recycled.

```
Version evolution of LFS
=======================

First write:
  Log: ...[inode1: version=1, pointing to block A]...[block A: content="Hello"]...

Modify file:
  Log: ...[inode1: version=2, pointing to block A']...[block A': content="World"]...

Status of old block A: [Block A: content="Hello"] ← Still on disk, but marked as garbage
                                  There is no inode pointing to it anymore

After GC:
  The old block A is reclaimed (erased or reallocated) and the space is returned to the system.
```

The on-disk performance gains from this design are staggering. In tests at the time, LFS achieved over 10 times the write throughput of Unix FFS (for small file write loads).

**But what Rosenblum and Ousterhout did not expect was that their design would become a natural template for the Flash file system 30 years later.**

---

## Why log structure is naturally suitable for Flash

Align each design choice of LFS with the physical constraints of Flash one by one:

```
LFS Design Choice → Flash Physical Fit
=======================

1. Only append, not overwrite
   LFS: All writes are appended to the end of the log
   Flash: Programming can only be done from 1→0, and it is impossible to overwrite it in place.
   Fit: ★★★★★ Perfect fit

2. The old version will be retained naturally
   LFS: Old data blocks are not deleted, they become garbage waiting for GC
   Flash: Old data blocks are retained before erasure, providing power-off recovery
   Fit: ★★★★★ Perfect use of Flash’s Copy-on-Write feature

3. Garbage collection (GC)
   LFS: Scan the log regularly and move valid data (latest version) to the end of the log
   Flash: GC must be used to reclaim invalid blocks to make room for writing
   Compatibility: ★★★★★ All are necessary mechanisms for space recycling

4. Sequential writing
   LFS: log stream = sequential write stream
   Flash: Sequential writes to NAND are faster than random writes (page programming pipeline)
   Fit: ★★★★ Sequential writing has performance advantages

5. No in-place modification
   LFS: There is no concept of "modifying an inode", a new one is created every time
   Flash: There is no "in-place modification", it is Copy-on-Write every time
   Fit: ★★★★★ The concept is completely consistent

6. Version snapshot
   LFS: Each checkpoint is a snapshot
   Flash: Old data is naturally retained; after power failure, playback starts from the last complete checkpoint and discards the incomplete tail.
   Fit: ★★★★★ Naturally supports power-off recovery
```

**The design philosophy of LFS and the physical constraints of Flash are a "destined" fit.**

This is no coincidence. This is because physical constraints determine the data structure, and the data structure in turn verifies the rationality of the physical constraints. The three original sins of Flash (erase before writing, one-way programming, and limited lifetime) push the file system design towards log structure, and log structure is the optimal solution to these original sins.

## Core data structure of LFS

Specifically look at the data structure of LFS. In KnotFS, you will see the shadow of these structures in many places.

**1. Superblock**

```
LFS Superblock = direct ancestor of KnotFS Superblock
=======================

LFS:
  Two superblock copies, one at each end of the disk
  ┌──────────┐ ┌───────────┐
  │ SB Copy 1 │ │ SB Copy 2 │
  │ (disk head) │ ... log segment ... │ (disk tail) │
  └──────────┘ └───────────┘

  Each superblock contains:
    - The starting position of the log tail (tail pointer)
    - The starting position of the segment usage table
    - The starting position of the inode mapping table (imap)
    - Timestamp and serial number

KnotFS:
  Two superblock replicas, located at block 0 and block 1
  ┌──────────┐ ┌───────────┐
  │ SB0 (Block 0) │ │ SB1 (Block 1) │
  └──────────┘ └───────────┘

  Each superblock contains:
    - sequence_number (determines which one is valid)
    - Location information of the file table
    - The starting point of the free bitmap
    - magic number and CRC
```

**2. Inode mapping table (Imap)**

```
LFS Imap → KnotFS File Table
=======================

LFS:
  imap is a compact array: imap[inode_number] → the latest position of the inode in the log
  Every time the inode is updated (put at the end of the log), the imap is also updated.
  imap itself is also stored in the form of log append.

KnotFS:
  The file table is embedded in Superblock (nodes[8]), and the double copies are guaranteed by SB double slots.
  nodes[x] → {file name, starting block number, size, attributes}
  Every time a file is modified, the entire SB is rewritten through Compact to persist the file table.
```

**3. Segment and Segment Cleaner**

```
LFS Segment → KnotFS GC Block
=======================

LFS:
  The disk is divided into fixed-size segments, usually 512KB-1MB
  segment cleaner = garbage collector

  ┌────── Segment 1 ────────┐ ┌────── Segment 2 ────────┐
  │[valid│garbage│valid│garbage│valid]│ │[valid│valid│valid│valid│valid]│
  │ 60% 40% │ │ 100% 0% │
  └────────────────────────┘ └──────────────────────────┘

  Select Segment 1 for cleaning (most garbage)
  Read valid data → append to the end of the log → Segment 1 is cleared → reusable

KnotFS:
  Each block (Block) is a "segment"
  gc_recycle() selects the blocks with the most garbage
  Relocate valid data to new blocks → Erase old blocks → Return old blocks to free pool
```

## Log structured "metadata flood"

But LFS has a famous engineering cost: **Metadata Flood**. Because everything is log append, any modification, even just changing the timestamp of an inode, requires appending a record to the end of the log. That is to say:

```
Modify the timestamp of an inode:

Unix FFS:
  1. Read inode block
  2. Modify the timestamp field (8 bytes)
  3. Write back the same sector in place
  Physical I/O: 1 read + 1 write

LFS:
  1. Read in the old inode
  2. Modify timestamp in memory
  3. Append the modified inode (the entire 128 bytes or so) to the end of the log
  4. Update imap → append an imap record to the end of the log
  5. Mark old inodes as garbage
  Physical I/O: 1 read + 2 additional writes + 2 additional garbage records
```

The write amplification of LFS is higher than that of traditional FS at the metadata level. This "metadata flooding" is evened out on disk by the performance benefits of sequential writes, but on Flash you also have the wear-out problem.

This is why KnotFS is tailored based on LFS: each record of **SB Log is only 8 bytes (tag+blk+val+crc32).** It does not record "what the inode was modified to", it only records "which block is marked as used/free". Modifications to the file table are not recorded in the log. The file table is embedded in the SB Header and persisted in one go through Compact. This design turns "append an entire inode" into "append a few bytes + regular compact".

```
KnotFS metadata compact log
=======================

LFS approach:
  Modify inode field → append entire inode(128B) + imap entry(16B) → 144B

KnotFS approach:
  Modify free_map → add an SB Log record (8B)
  Modify the file table → accumulate in memory, write new SB at once during Compact

Advantages of compact log:
  - A 4KB block can fit ~400 SB Log records
  - Minimal logging, reducing wear and tear
```

This is a key optimization of KnotFS on LFS and an enrichment of LFS.

## Checkpoint mechanism of LFS: both ends of a line

Another important contribution of LFS is the Checkpoint mechanism.

Because all writes are append, you can always find the "status of the last complete write". If power fails during a write, you replay the log forward from the last complete checkpoint, discarding only the incomplete tail.

```
LFS Checkpoint = KnotFS's ancestor of the dual-slot Compact
=======================

Checkpoint N (valid):
  ┌─────────────────────────────────┐
  │ Superblock → imap → inodes → data│
  └─────────────────────────────────┘
          ↓ Start writing new data
  ┌─────────────────────────────────┐
  │ new inode │ new data │ new imap │ ... │ ← append to log tail
  └─────────────────────────────────┘
          ↓ Power outage! !
  The end of the log is incomplete – but that’s okay
  When remounting: Read Checkpoint N information
  Scan the log starting from the location of Checkpoint N
  Incomplete records found → discarded → Checkpoint N becomes the recovery point

Checkpoint N+1 is written only after "All data is safely landed".
```

The dual-slot Compact in KnotFS writes the complete status in the memory (file table + free_map + wear[]) to the spare SB slot, and switches the active pointer after the writing is successful. It is essentially a reduced version of LFS Checkpoint: Checkpoint writes a complete inode mapping table, and Compact writes a complete SB Header (embedded file table).

## One paper and one hundred and twenty-eight Flash blocks

In 1992, when Rosenblum and Ousterhout wrote LFS on Stanford's SUN workstation, they faced the performance bottleneck of a 300MB SCSI hard disk, 16MB of memory, and hundreds of random I/Os per second.

In 2026, when you design KnotFS on the Cortex-R5 core, you face the deterministic requirements of 512KB NOR Flash, 64KB SRAM, and real-time scheduler.

The hardware is about two and a half orders of magnitude worse. But the core problem is exactly the same:

```
1992 LFS → 2026 KnotFS
=======================

LFS faces: KnotFS faces:
Disk seek latency (10ms) Flash erase latency (200ms)
Lowercase amplification (random seek cost) Lowercase amplification (erase-rewrite cost)
Sequential writing is required to improve throughput. It must be updated off-site to survive.
GC wastes disk bandwidth and GC wastes Flash P/E life.
Checkpoint anti-crash and dual-slot Compact anti-power-down
Segment management (512KB-1MB) Block management (4KB)
```

**Isomorphic problems have produced isomorphic solutions at different scales.**

This is why you need to read the LFS paper and understand the LFS idea, because it reveals a more essential engineering law: **When a storage medium does not allow in-place modification, log structuring is the only correct data structure choice.**

## Why KnotFS is "Log Structured" and not just "Copy-on-Write"

There is a subtle distinction that needs to be made clear: Copy-on-Write and log structuring are not the same thing.

Copy-on-Write works piece by piece. You have a data tree, you modify a leaf node, you propagate the modification all the way up to the root node, allocating new blocks (CoW) at each level and keeping the old ones as garbage.

Log structuring is a stream. You keep appending new records to the end of the log, whether it's a data block, an inode, or a directory entry. Everything is an entry on the log stream.

```
CoW vs Log-Structured
=======================

CoW (such as Btrfs, ZFS):
  Block 0: [A] → modified A → Block 0: [A old]
                             Block N: [A'new]
  Modifications only affect "the tree path where the modified block is located"
  Reference count management: all nodes on the old tree path are recycled when they lose references

Log-Structured (such as LFS, KnotFS):
  Log: [entry 1│entry 2│entry 3│entry 4│...] → modify entry 2 → append entry 2' to the end
  All changes are appended to the end of the log
  The valid version is always in the "log tail" direction
  Garbage is the previous record in the log that is overwritten by the later record.
```

KnotFS adopts a **hybrid strategy**:
- **Metadata (Superblock): Log Structured + Compact.** SB Log is a miniature version of the LFS log stream, and incremental changes in free_map are appended as 8-byte log records. The file table is embedded in the SB Header and persisted through Compact.
- **Data block: Copy-on-Write.** File data exists in independent data blocks. When modified, new blocks are allocated, old data is copied + modified, and old blocks are marked as garbage. This is closer to Btrfs' CoW than LFS's pure log.

```
KnotFS’s hybrid architecture
======================

Metadata layer (Log-Structured + Compact):
  ┌──────────────┐ ┌──────────────┐
  │ SB0 SB Log│ │ SB1 SB Log│
  │ nodes[8] │ │ nodes[8] │
  │ [rec1][rec2] │ │ [Empty log area] │
  │ [... │ │ │
  └──────────────┘ └──────────────┘
    additional write additional write

Data layer (Copy-on-Write):
  ┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐
  │ Block 3 │ │ Block 5 │ │ Block 8 │ │ Block 12 │
  │ File 1 │ │ File 1 │ │ File 2 │ │ File 1 │ ← Old
  │ (old) │ │ (old) │ │ (old) │ │ (new CoW) │
  └────────┘ └────────┘ └────────┘ └─────────┘
     Garbage Garbage Garbage Valid
```

Why layer it like this? Because the metadata is very "small" (several bytes per record), it is suitable for compact logs; the data blocks are very "large" (4KB each), so it is more natural to do CoW. Both are managed uniformly using the same garbage collection mechanism (traversing valid blocks, relocating to new blocks, and erasing old blocks).
