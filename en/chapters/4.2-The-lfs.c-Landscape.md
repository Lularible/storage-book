# 4.2 The lfs.c Landscape: The Engineering Wisdom of a Single File

## A business card with 6500 lines

On GitHub, the file listing for the LittleFS repository will confuse you for three seconds:

```
littlefs/
├── lfs.h (line 801)
├── lfs.c (6549 lines)
├── lfs_util.h (tool macro/function)
├── LICENSE.md
├── DESIGN.md (2173 lines, design document)
├── SPEC.md (on-disk format specification)
├── Makefile
├── tests/ (test file)
└── bd/ (block device driver example)
```

**The core code consists of two files: lfs.h (line 801) and lfs.c (line 6549). ** There is no sub-module compilation, no division of "pumping directory operations to lfs_dir.c and file operations to lfs_file.c". All block device abstractions, metadata pair operations, CTZ jump tables, block allocators, directory traversal, file reading and writing, orphan processing, global state management... are all in lfs.c.

This is not laziness. If you understand the context of embedded compilation, you will understand the engineering wisdom of this decision.

---

## Why single file?

Imagine you are an embedded firmware engineer. Your project uses the IAR EWARM compiler, and the `.c` files are added one by one through the Makefile. Every time you add a source file, it means:
- One more compile call
- One more target file to link to
- One more set of symbols to parse across files
- The linker has to process one more set of relocation tables

The number of compilation units for an embedded project is a linear cost. Moreover, many embedded compilers have poor support for cross-file inlining, and the `static inline` function can only be expanded within the translation unit in which it is defined. If you put `lfs_bd_read` in a separate file, all files that call it will either see a single function call (sacrifice performance), or it will be defined repeatedly at each call (violating ODR).

**Single file design zeroes out all these costs. ** The compiler only compiles one lfs.c, all internal functions are declared as `static`, and the linker does not need to care about them at all. The internal logic of the entire file system is fully parsed at compile time, and the traditional "module interface" is maintained by the sectioning and function naming conventions within the file.

```c
// The internal modules of lfs.c are divided by section comments instead of files.

/// Caching block device operations ///
static int lfs_bd_read(...)   { /* ... */ }
static int lfs_bd_prog(...)   { /* ... */ }
static int lfs_bd_erase(...)  { /* ... */ }

/// Small type-level utilities ///
static inline bool lfs_pair_isnull(...) { /* ... */ }
static inline void lfs_pair_swap(...)   { /* ... */ }

/// Block allocator ///
static int lfs_alloc(...)       { /* ... */ }
static int lfs_alloc_scan(...)  { /* ... */ }

/// Metadata pair and directory operations ///
static int lfs_dir_fetch(...)   { /* ... */ }
static int lfs_dir_commit(...)  { /* ... */ }
static int lfs_dir_compact(...) { /* ... */ }

/// File index list operations ///
static int lfs_ctz_index(...)   { /* ... */ }
static int lfs_ctz_find(...)    { /* ... */ }
static int lfs_ctz_extend(...)  { /* ... */ }
```

In LittleFS's design philosophy, the "public interface" of each module is the `lfs_mount`, `lfs_file_open`, and `lfs_dir_read` functions exposed to users in lfs.h, which constitute a stable API. ** Internal modules call each other through the `static` function. After the compiler performs dead code elimination, the unused internal functions will not appear in the final binary.

## The module structure of lfs.c - although the layers are there, the files are missing

Although all code is in one file, LittleFS's internal layering is exceptionally clear. Through comment separation in the code (`/// Caching block device operations ///`, `/// Metadata pair and directory operations ///`...), the author marks the module boundaries. Let's look at it from bottom to top:

```
lfs.c internal hierarchical structure
=========================================

┌───────────────────────────────────────────┐
│ Public API encapsulation (lfs_mount, lfs_file_open, ...) │ ← Call internal _ suffix function
├───────────────────────────────────────────┤
│ File system level operations │
│ lfs_fs_deorphan, lfs_fs_forceconsistency, │
│ lfs_fs_gc, lfs_fs_grow, lfs_fs_traverse │
├────────────────┬─────────────┬────────────────┤
│ File operations │ Directory operations │ CTZ jump table │
│ lfs_file_* │ lfs_dir_* │ lfs_ctz_* │
│ open/close/ │ fetch/commit │ index/find/ │
│ read/write/ │ /compact/ │ extend/ │
│ sync/truncate│ traverse/ │ traverse │
│ │ split/alloc │ │
├────────────────┴──────────────┴────────────────┤
│ Block allocator (lfs_alloc, lfs_alloc_scan) │
├───────────────────────────────────────────┤
│ Block device abstraction layer (lfs_bd_read, lfs_bd_prog, ...) │
│ + cache layer (lfs_cache_drop, lfs_cache_zero) │
├───────────────────────────────────────────┤
│ Type/tool layer (tag operation, pair operation, CRC, endian) │
└────────────────────────────────────────────┘
```

**Block Device Abstraction Layer (lfs_bd_*)**, this is LittleFS’s only interface with physical storage. It encapsulates the `read`/`prog`/`erase`/`sync` callbacks provided by the user in `lfs_config`, and superimposes two layers of cache on top: read cache (rcache) and programming cache (pcache).

```c
// lfs.c:44-126 — lfs_bd_read, the core logic of block device reading
static int lfs_bd_read(lfs_t *lfs,
        const lfs_cache_t *pcache, lfs_cache_t *rcache, lfs_size_t hint,
        lfs_block_t block, lfs_off_t off,
        void *buffer, lfs_size_t size) {
    uint8_t *data = buffer;

    while (size > 0) {
        lfs_size_t diff = size;

        // 1. Check the programming cache first (pcache may contain new data that has not been refreshed)
        if (pcache && block == pcache->block &&
                off < pcache->off + pcache->size) {
            if (off >= pcache->off) {
                diff = lfs_min(diff, pcache->size - (off-pcache->off));
                memcpy(data, &pcache->buffer[off-pcache->off], diff);
                data += diff; off += diff; size -= diff;
                continue;
            }
            diff = lfs_min(diff, pcache->off-off);
        }

        // 2. Check the cache again
        if (block == rcache->block && off < rcache->off + rcache->size) {
            if (off >= rcache->off) {
                diff = lfs_min(diff, rcache->size - (off-rcache->off));
                memcpy(data, &rcache->buffer[off-rcache->off], diff);
                data += diff; off += diff; size -= diff;
                continue;
            }
            diff = lfs_min(diff, rcache->off-off);
        }

        // 3. If the request is large enough, bypass the cache and read directly
        if (size >= hint && off % lfs->cfg->read_size == 0 &&
                size >= lfs->cfg->read_size) {
            diff = lfs_aligndown(diff, lfs->cfg->read_size);
            int err = lfs->cfg->read(lfs->cfg, block, off, data, diff);
            if (err) return err;
            data += diff; off += diff; size -= diff;
            continue;
        }

        // 4. Load from device to read cache
        rcache->block = block;
        rcache->off = lfs_aligndown(off, lfs->cfg->read_size);
        rcache->size = lfs_min(/* ... */, lfs->cfg->cache_size);
        int err = lfs->cfg->read(lfs->cfg, rcache->block,
                rcache->off, rcache->buffer, rcache->size);
        if (err) return err;
    }
    return 0;
}
```

Note the subtlety of this read function: **pcache has the highest priority**, because the programming cache may contain the latest data that has not yet been written to Flash. Read cache comes second. If the size of the request exceeds the read threshold (hint), the cache is bypassed and the hardware is read directly. This is a performance optimization: large blocks of data do not pollute the cache.

**Type/Tool Layer**, the lowest layer of LittleFS is a set of bit operations and inline functions used to operate its core data structures. The most important of these is the tag system.

LittleFS uses 32-bit tags to encode the type, ID, and size of directory entries:

```c
// lfs.c:342-343 — 32-bit tag encoding format
#define LFS_MKTAG(type, id, size) \
    (((lfs_tag_t)(type) << 20) | ((lfs_tag_t)(id) << 10) | (lfs_tag_t)(size))

// Bit field layout of tag:
// [31] = valid bit (0=valid)
// [30:20] = type (11 bits)
// [19:10]      = ID   (10 bits)
// [9:0] = size (10 bits)
```

This tag is a common "data header" for LittleFS metadata. Each record written to a metadata pair starts with a tag. The tag tells the parser what type this record is (file name, file data, CTZ structure...), which file it belongs to (ID), and how long the data content is (size).

**Metadata pair and directory operation layer (lfs_dir_*)**, this is the most complex module of LittleFS and the largest part of the 6500 lines. Contains:
- `lfs_dir_fetch`, loads a metadata block from Flash
- `lfs_dir_traverse`, traverse all entries in the metadata pair
- `lfs_dir_commit`, atomically submit a directory update (including compaction and splitting logic)
- `lfs_dir_compact`, compact a metadata pair
- `lfs_dir_split`, split a metadata pair when full
- `lfs_dir_alloc`, allocate a new metadata pair

**CTZ jump table layer (lfs_ctz_*)**, four functions, less than 200 lines of code, implements a complete COW jump table:
- `lfs_ctz_index`, calculate block index from file offset (O(1))
- `lfs_ctz_find`, find the block where the given offset is located (O(log n))
- `lfs_ctz_extend`, append a new block (O(1))
- `lfs_ctz_traverse`, traverse all blocks (O(n), for garbage collection)

**Block allocator (lfs_alloc_*)**, three or four functions, about 150 lines, implements lookahead scanning and block allocation.

**Top-level API**, namely `lfs_mount`, `lfs_file_open`, `lfs_file_read`, `lfs_file_write`, `lfs_dir_open`, `lfs_dir_read`...these public interfaces are at the end of the file. They are basically thin wrappers around the internal `_` suffix functions:

```c
// Implementation mode of public API in lfs.c:
// Public functions call internal functions, which do the actual work

int lfs_mount(lfs_t *lfs, const struct lfs_config *config) {
    return lfs_mount_(lfs, config);     // internal implementation
}

int lfs_file_open(lfs_t *lfs, lfs_file_t *file,
        const char *path, int flags) {
    return lfs_file_open_(lfs, file, path, flags);  // internal implementation
}
```

This "public = thin shell" model exposes an interesting feature of LittleFS: **LittleFS's API design is strictly decoupled from its internal implementation. ** The public API promises a behavioral contract ("open a file, return a handle"), the internal implementation can be freely refactored, and you can optimize lfs_dir_compact without affecting any callers.

## lfs_t: One structure holds the entire file system

All runtime states of LittleFS are encapsulated in the `lfs_t` structure. The size of this structure is fixed, no matter how big your file system is:

```c
// lfs.h:435-470 — File system runtime status
typedef struct lfs {
    lfs_cache_t rcache;              // Read cache (~12 bytes + buffer)
    lfs_cache_t pcache;              // Programming cache (~12 bytes + buffer)

    lfs_block_t root[2];             // The metadata pair address of the root directory (8 bytes)
    struct lfs_mlist {
        struct lfs_mlist *next;      // Open directory/file list
        uint16_t id;
        uint8_t type;
        lfs_mdir_t m;
    } *mlist;                        // (Pointer, 8 bytes on 32-bit)

    uint32_t seed;                   // Random number seed (4 bytes)

    lfs_gstate_t gstate;             // runtime global state
    lfs_gstate_t gdisk;              // On-disk global status
    lfs_gstate_t gdelta;             // Increment of modifications in this round

    struct lfs_lookahead {
        lfs_block_t start;           // Start block of pre-search window
        lfs_block_t size;            // Presearch window size
        lfs_block_t next;            // next position within window
        lfs_block_t ckpoint;         // Checkpoint counter
        uint8_t *buffer;             // Presearch bitmap buffer pointer
    } lookahead;                     // (~20 bytes + buffer)

    const struct lfs_config *cfg;    // Configuration pointer (8 bytes on 32-bit)
    lfs_size_t block_count;          // Total number of blocks (4 bytes)
    lfs_size_t name_max;             // Maximum file name length (4 bytes)
    lfs_size_t file_max;             // Maximum file size (4 bytes)
    lfs_size_t attr_max;             // Maximum attribute length (4 bytes)
    lfs_size_t inline_max;           // Maximum inline file size (4 bytes)
} lfs_t;
```

You can see RAM usage = `sizeof(lfs_t)` + `cache_size * 2` (read cache + program cache) + `lookahead_size` (pre-search buffer). These three numbers are completely determined at compile time. For a typical configuration (cache_size=64, lookahead_size=16), the total RAM is about 200 bytes, plus the buffer's 128+16=144 bytes, for a total of about 350 bytes. **This number does not grow as the file system gets larger. **

## lfs_config: How do you let LittleFS know your Flash

LittleFS does not assume your Flash model, what driver you use, or which RTOS you are running on. All external dependencies are injected via `lfs_config`:

```c
// lfs.h:157-293 — User-provided configuration structure
struct lfs_config {
    void *context;               // User-defined context

    int (*read)(const struct lfs_config *c, lfs_block_t block,
            lfs_off_t off, void *buffer, lfs_size_t size);
    int (*prog)(const struct lfs_config *c, lfs_block_t block,
            lfs_off_t off, const void *buffer, lfs_size_t size);
    int (*erase)(const struct lfs_config *c, lfs_block_t block);
    int (*sync)(const struct lfs_config *c);

    lfs_size_t read_size;        // Minimum read granularity
    lfs_size_t prog_size;        // Minimal programming granularity
    lfs_size_t block_size;       // Erase block size (LittleFS "logical block")
    lfs_size_t block_count;      // Total number of blocks (0 = read from on-disk superblock)
    int32_t   block_cycles;      // Relocation threshold (how many times to erase metadata before relocation)
    lfs_size_t cache_size;       // cache size
    lfs_size_t lookahead_size;   // Presearch buffer size
    lfs_size_t compact_thresh;   // GC compression threshold

    void *read_buffer;           // Optional: statically allocated read cache
    void *prog_buffer;           // Optional: statically allocated programming cache
    void *lookahead_buffer;      // Optional: statically allocated pre-search buffer
    // ...
};
```

This is very much like KnotFS's "block device asynchronous abstraction layer", but LittleFS's is more concise. It does not require you to implement "asynchronous reading", all I/O is synchronous. If you need async, that's the caller's responsibility (like calling the LittleFS API within a FreeRTOS task).**The four callback functions (read/prog/erase/sync) are the only hardware adaptation code you need to implement. ** For example for a SPI NOR Flash:

```c
// The read callback you implemented
int my_flash_read(const struct lfs_config *c, lfs_block_t block,
        lfs_off_t off, void *buffer, lfs_size_t size) {
    uint32_t addr = block * c->block_size + off;
    spi_flash_read(addr, buffer, size);  // Call your SPI driver
    return 0;
}

// The prog callback you implemented
int my_flash_prog(const struct lfs_config *c, lfs_block_t block,
        lfs_off_t off, const void *buffer, lfs_size_t size) {
    uint32_t addr = block * c->block_size + off;
    spi_flash_write(addr, buffer, size);  // Programming (can only change 1 to 0)
    return 0;
}

// The erase callback you implemented
int my_flash_erase(const struct lfs_config *c, lfs_block_t block) {
    uint32_t addr = block * c->block_size;
    spi_flash_erase_4k(addr);   // Erase 4KB block (change all bits to 1)
    return 0;
}
```

Then you fill them into `lfs_config` and call `lfs_mount`:

```c
const struct lfs_config cfg = {
    .read  = my_flash_read,
    .prog  = my_flash_prog,
    .erase = my_flash_erase,
    .sync  = my_flash_sync,
    .read_size      = 16,       // Minimum read granularity of SPI Flash
    .prog_size      = 16,       // Minimum programming granularity of SPI Flash (usually 1-256 bytes)
    .block_size     = 4096,     // erase block size
    .block_count    = 1024,     // 4MB / 4KB = 1024 blocks
    .cache_size     = 64,       // 64-byte cache
    .lookahead_size = 16,       // 16-byte pre-search buffer = track up to 128 blocks
};

lfs_t lfs;
int err = lfs_mount(&lfs, &cfg);
if (err) {
    // Mount failed, may need to be formatted
    lfs_format(&lfs, &cfg);
    lfs_mount(&lfs, &cfg);
}
```

With just these three lines, you have a complete, power-off safe file system on a 4MB NOR Flash.

## Some engineering details in the code

Walking through LittleFS’s 6500 lines of C code, you’ll notice some rustic but solid engineering practices:

**Endian processing everywhere. ** The data on the LittleFS disk is in little-endian order, but in order to be compatible with different architectures (ARM, MIPS, PowerPC), each multi-byte value written to the disk must be converted through `lfs_tole32`:

```c
// lfs.c:497-500
static inline void lfs_superblock_tole32(lfs_superblock_t *superblock) {
    superblock->version     = lfs_tole32(superblock->version);
    superblock->block_size  = lfs_tole32(superblock->block_size);
    // ... Convert each field one by one
}
```

**goto cleanup mode. ** In paths such as initialization/mounting that require multi-layer resource cleaning, LittleFS uses goto:

```c
// lfs.c:4482-4560 — Typical error handling for lfs_mount_
static int lfs_mount_(lfs_t *lfs, const struct lfs_config *cfg) {
    int err = lfs_init(lfs, cfg);
    if (err) {
        return err;              // init failed, no need to clean up
    }

    // ...mounting logic...

    if (tag < 0) {
        err = tag;
        goto cleanup;            // Jump to unified cleanup code
    }

    // ...

cleanup:
    lfs_deinit(lfs);             // Release resources allocated in lfs_init
    return err;
}
```

**Bad block retry loop. ** The `relocate` tag is used extensively in the write code. When a write verification failure is detected, an error is not returned, but an automatic attempt is made to allocate a new block for rewriting:

```c
// lfs.c:2921-3017 — Bad block retry in lfs_ctz_extend
while (true) {
    lfs_block_t nblock;
    int err = lfs_alloc(lfs, &nblock);
    // ...
    err = lfs_bd_erase(lfs, nblock);
    if (err) {
        if (err == LFS_ERR_CORRUPT) {
            goto relocate;       // Erase failed, change a block
        }
        return err;
    }
    // ... write data ...

relocate:
    LFS_DEBUG("Bad block at 0x%"PRIx32, nblock);
    lfs_cache_drop(lfs, pcache);  // Clear the cache and enter the next cycle
}
```

## From compilation to run-a complete life cycle

When you compile LittleFS into your firmware:

1. **Compilation period:** The compiler processes the file lfs.c. All `static` functions are parsed within a single translation unit, and the linker does not do any relocation of LittleFS internal symbols. The final binary contains only those API paths you actually called (dead code elimination by the compiler).

2. **Initialization:** You call `lfs_mount(&lfs, &cfg)`. LittleFS calls `lfs_init` to verify the configuration parameters. The block size must be an integer multiple of cache_size, cache_size must be an integer multiple of read_size/prog_size, and block_cycles cannot be 0. Then allocate the read cache and programming cache (use static buffers if the user provides them). Then start scanning the metadata pair list on the disk, looking for the superblock, and rebuilding the global state.

3. **Runtime:** Each file operation (read, write, open, close...) is completed through the internal function chain in lfs.c. Block device operations → cache → directory lookup/commit → CTZ jump table navigation. All operations are synchronous, and when the call returns, the data has already been written (or at least in the cache ready to be flushed).

4. **Uninstall:** `lfs_unmount` releases all applied memory and clears the cache.

KnotFS also puts all core logic in one `knotfs.c`, and the core implementation is about 1165 lines (about 1771 lines including header files and tests). But the difference is: KnotFS does not have an RTOS, it cannot call `lfs_file_write()` and then block waiting for completion. LittleFS's synchronization API relies on the operating system's scheduler to ensure that the caller does not starve to death; KnotFS must split each operation into multiple steps of the state machine and advance a small step in each call of `knotfs_run()`.
