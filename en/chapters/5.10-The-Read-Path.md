# 5.10 The Read Path: Block Addressing and Offset Calculation

## Data is like a row of bookshelves, all you want is a small piece of it

You have a 1000 page book. You'll start at line 8 on page 423 and read lines 50. These 50 lines could span the end of page 423, page 424, or even the beginning of page 425.

In a file system, this is how read operations work: the offsets and lengths requested by the user are almost never aligned with block boundaries. ** Your job is to translate "continuous byte range from user perspective" into "several block reading + cropping and splicing from block device perspective".

KnotFS's `do_read` uses three states to accomplish this: ST_RD_LOOKUP, ST_RD_DATA, and ST_RD_COPY. Among them, ST_RD_DATA and ST_RD_COPY are executed alternately, forming a cycle of "read one block → copy one section → read the next block → copy the next section".


---

## First state: ST_RD_LOOKUP - find the file and calculate the interval

```c
case ST_RD_LOOKUP:
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_NOFILE;
      cur.st = ST_ERR;
      return;
    }
    if (cur.r_off >= nd->size) {
      if (cur.r_out)
        *cur.r_out = 0;
      cur.st = ST_OK;
      return;
    }
    {
      uint32_t end = cur.r_off + cur.r_sz;
      if (end > nd->size)
        end = nd->size;
      sblk = cur.r_off / KNOTFS_BLOCK_SIZE;
      eblk = (end + KNOTFS_BLOCK_SIZE - 1) / KNOTFS_BLOCK_SIZE;
      if (eblk > nd->block_count)
        eblk = nd->block_count;
    }
    scratch[SCR_RD_SBLK] = sblk;
    scratch[SCR_RD_EBLK] = eblk;
    subst = sblk;
    prog = 0;
    cur.st = ST_RD_DATA;
    return;
```

LOOKUP does three things:

**First, boundary inspection. ** If the requested offset exceeds the file size, 0 bytes will be returned directly. This is the semantics of "the file has been read", not an error. `cur.r_out` (a `uint32_t *bytes_read` output parameter) is set to 0.

**Second, interval clipping. ** `end = cur.r_off + cur.r_sz` is the end of the request interval. If `end > nd->size`, it means that the user wants to read more than the actual file, and the file is cut to the end. This is the standard behavior of POSIX `read()` system calls: return the actual number of bytes read.

**Third, block number mapping. **This is the key step:

```
sblk = cur.r_off / KNOTFS_BLOCK_SIZE ← starting block number
eblk = (end + KNOTFS_BLOCK_SIZE - 1) / KNOTFS_BLOCK_SIZE ← end block number (rounded up)
```

If requesting `offset=2000, size=100`, file size is 5000 bytes:
-`end = 2100`
- `sblk = 2000 / 4096 = 0` (starting from block 0)
- `eblk = (2100 + 4095) / 4096 = 1` (requires reading block 0)

If requesting `offset=2000, size=5000`, file size is 5000 bytes:
- `end = 5000` (cropped to the end of the file)
-`sblk = 2000 / 4096 = 0`
- `eblk = (5000 + 4095) / 4096 = 2` (needs to read block 0 and block 1)

`scratch[0] = sblk` and `scratch[1] = eblk` save these calculated intervals. `subst = sblk` is used as the cursor of "which block is currently being processed", and `prog = 0` is used as the cumulative value of "how many bytes have been copied to the user buffer".

## Second state: ST_RD_DATA - read the entire block to tmp

```c
case ST_RD_DATA: {
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_NODE;
      cur.st = ST_ERR;
      return;
    }
    eblk = scratch[SCR_RD_EBLK];
    if (subst >= eblk) {
      if (cur.r_out)
        *cur.r_out = prog;
      cur.st = ST_OK;
      return;
    }
    fdev_read(nd->blocks[subst], tmp, KNOTFS_BLOCK_SIZE);
    cur.st = ST_RD_COPY;
    return;
}
```

The logic here is intuitive: if the current block number `subst` has exceeded the end block number `eblk`, it means that all required blocks have been read, `prog` (the cumulative number of copied bytes) is written to `cur.r_out`, and ST_OK is returned.

If it has not finished reading, initiate an asynchronous read operation: `fdev_read(nd->blocks[subst], tmp, KNOTFS_BLOCK_SIZE)`. It reads the entire block (4KB) into the global `tmp` buffer. `fdev_read` has a delay of 1 tick (`ticks_left = 1`), and then jumps to ST_RD_COPY.

**Why read the entire block? ** Because Flash read operations are performed in blocks, you cannot only read a certain offset range in a block. You have to read the entire block into memory (tmp buffer) and then do the cropping in memory.

## Third state: ST_RD_COPY - crop from tmp to user buffer

```c
case ST_RD_COPY: {
    nd = find_node(cur.name);
    if (!nd) {
      cur.result = ERR_RD_COPY;
      cur.st = ST_ERR;
      return;
    }

    uint32_t bs = subst * KNOTFS_BLOCK_SIZE;
    uint32_t be = bs + KNOTFS_BLOCK_SIZE;
    uint32_t rs = cur.r_off;
    uint32_t re = cur.r_off + cur.r_sz;
    if (re > nd->size)
      re = nd->size;

    uint32_t seg_s = (rs > bs) ? rs : bs;
    uint32_t seg_e = (re < be) ? re : be;
    uint32_t seg_n = (seg_e > seg_s) ? seg_e - seg_s : 0;
    uint32_t src_o = seg_s - bs;

    memcpy((uint8_t *)cur.r_buf + prog, tmp + src_o, seg_n);
    prog += seg_n;
    subst++;
    cur.st = ST_RD_DATA;
    return;
}
```

This section is the most core and most error-prone offset calculation in the read operation. Let’s break it down:

```
Variable definition:
  bs = "file absolute offset" starting position of the current block (for example, block 0: 0~4095, block 1: 4096~8191)
  be = "file absolute offset" end position of the current block + 1
  rs = starting offset requested by user
  re = user requested ending offset (clipped to file size)

Intersection calculation:
  seg_s = max(rs, bs) ← Request the "overlapping starting point" of the interval and the current block
  seg_e = min(re, be) ← Request the "overlapping end point" of the interval and the current block
  seg_n = seg_e - seg_s ← length of overlap
  src_o = seg_s - bs ← offset in tmp buffer
```

Give a specific example. Assume the file size is 5000 bytes and the user requests `offset=2000, size=3000`:

```
File layout: ┌─────────Block 0────────┐┌──Block 1──┐
Byte offset: 0...1999|2000...4095|4096...4999|
            ▲ ▲ ▲
            │ rs=2000 re=5000 (=nd->size)

Block 0 (subst=0):
  bs=0, be=4096
  seg_s = max(2000, 0) = 2000
  seg_e = min(5000, 4096) = 4096
  seg_n = 4096 - 2000 = 2096
  src_o = 2000 - 0 = 2000
  Copy: tmp[2000..4095] → r_buf[0..2095] ← 2096 bytes

Block 1 (subst=1):
  bs=4096, be=8192
  seg_s = max(2000, 4096) = 4096
  seg_e = min(5000, 8192) = 5000
  seg_n = 5000 - 4096 = 904
  src_o = 4096 - 4096 = 0
  Copy: tmp[0..903] → r_buf[2096..2999] ← 904 bytes

prog = 2096 + 904 = 3000 → *bytes_read = 3000
```

## Boundary Case: Four Corners Trap

**Case 1: The offset is in the middle of the first block. **When `cur.r_off` is not divisible by `KNOTFS_BLOCK_SIZE`, `src_o` of the first block is not 0, and you start copying from the middle of tmp. This is the most common scenario.

**Case 2: The read interval is less than one block. **

If `offset=100, size=50` is requested, then `sblk=0, eblk=1`. In ST_RD_COPY, the `seg_n` in the overlapping interval will only have 50 bytes. Only these 50 bytes are copied and other areas are not affected.

**Case 3: Reading beyond the end of the file. **

`end = nd->size` has been cropped in the LOOKUP stage. So `re` in ST_RD_COPY will not exceed the file size. The overlapping interval of the last block is naturally truncated.

**Case 4: The file size is exactly an integer multiple of the block size. **

If the file is exactly 4096 bytes, request `offset=4096, size=100`. LOOKUP detects `cur.r_off >= nd->size` and returns 0 bytes directly. No attempt will be made to read a non-existent block 1.

## tmp buffer: a story of scratch space

`static uint8_t tmp[KNOTFS_BLOCK_SIZE]` is the only additional memory required for the entire read operation. It is only 4KB, but it is enough to serve as a "transfer station", reading the entire block from Flash into tmp, trimming it in tmp, and copying the required fragments to the user buffer.

This mode is called "**read into scratch, copy segment**". It is not an invention of KnotFS, almost all block device read operations do this. The difference is that the Linux kernel's `bread()` reads blocks into the page cache, while KnotFS uses a global 4KB array.

Why can't Flash be read directly to the corresponding location in the user buffer? Because the starting position of the user buffer is usually not aligned with the block boundary. Assume that the user requests `offset=3000, size=500`. The first 500 bytes of the user buffer need to be from offset 3000 of block 0, but the first 3000 bytes of block 0 do not. If you read block 0 directly from Flash to the beginning of the user buffer, you overwrite the first 3000 bytes of the user buffer, which is not what the user wants. So you must first read into the temporary buffer and then memcpy.

## Three-stage loop for reading

```
ST_RD_LOOKUP ──→ ST_RD_DATA ──→ ST_RD_COPY ──→ ST_RD_DATA ──→ ST_RD_COPY ──→ ST_OK
                   ▲____________________│____________________│
                     Loop: read a block → copy a block → read the next block
```

The condition for terminating this loop is `subst >= eblk`, and the current block number has exceeded the block range that needs to be read.

Each loop does two things: ST_RD_DATA issues an asynchronous read (1 tick), and ST_RD_COPY does a memory copy (synchronous, very fast). The two states combined constitute a "read-splice" atomic operation.


---

## A subtle question: What if the file is modified during reading?

In KnotFS, this does not happen because all operations are serialized by the request queue. When you are reading a file, there cannot be other threads writing to the same file. The write operation must wait until the read operation is completed (`cur.st == ST_OK` or `ST_ERR`) before it can be dequeued from the queue.

But in a real production-level deployment (such as running on FreeRTOS), read operations and write operations may be performed in different tasks, which raises the issue of "file system concurrency control". The production-level solution will avoid read-write competition by placing the File Table and metadata cache in shared memory and ensuring that only one operation is modifying metadata at the same time.

## If you design

Try to answer: Why is `src_o = seg_s - bs` in `ST_RD_COPY` instead of `src_o = cur.r_off - bs`?Answer: Because `cur.r_off` is the **total starting offset** requested by the user, it is unchanged during the entire read operation. The offset calculation of each block should be based on the overlapping starting point of the current block and the requested interval. Assume that `offset=2000` is requested, `seg_s=2000, bs=0` of block 0, `src_o=2000`, which is coincidentally the same as `cur.r_off - bs = 2000 - 0 = 2000`. But if `offset=2000` is requested, `seg_s=4096` is processed when block 1 is processed (because block 1 starts at 4096), and `cur.r_off - bs = 2000 - 4096 = -2096` is out of bounds. So `seg_s - bs` must be used, which is the correct starting point for cutting within the block.
