# 3.2 Block Device Abstraction: The File System's First Lie

## There is something in your hand, it looks like a disk

You walk back to the workshop and turn on the oscilloscope. In front of you is a Winbond W25Q32JV, which is a 32Mbit (4MB) serial NOR Flash. 8 pins: VCC, GND, CS, CLK, DI, DO, WP, HOLD.

You pick up the probe of the logic analyzer, clamp it on DI and DO, and prepare to see how this "storage device" talks.

You send a read command to the master to read the 256 bytes starting at address 0x000100. This waveform appears on the SPI bus:

```
Read operation SPI bus waveform
=======================

CS ___/''''''''''''''''''''''''''''''''\___
CLK _/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ \_
DI __/ 0x03 \__/ 0x00 \__/ 0x01 \__/ 0x00 \______________
    ↑ Read command ↑ Address 23..16 ↑ Address 15..8 ↑ Address 7..0

DO ______________/data0 \__/data1 \__
                  \____________________________/ \____________________________/
                 ↑ The first byte read from address 0x000100
```

25MHz clock. One byte every 8 clock cycles. 256 bytes, read in about 82 microseconds. So fast that you can't see it.

You issue another erase command to erase the 4KB sector where address 0x000000 is located:

```
Sector erase SPI bus waveform
=======================

CS ___/''''''''''''''''''''''''''''''''''''''''''''''''''''''''''''\___
CLK _/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ \_/ ... (200ms wait) ... / \_/ \_/ \_/ \_/ \_
DI __/ 0x06 \____________________/ 0x20 \__/ 0x00 \__/ 0x00 \__/ 0x00 \______________
    ↑ Write enable ↑ Sector erase command ↑ 24-bit address

Wait 200 milliseconds - during this time, the high-pressure pump inside the Flash is running,
The electrons in the floating gate are returning to the substrate through the oxide layer. CS can be pulled high, but the status register
The BUSY bit remains 1 until erase is completed.

DO ____________________/ BUSY=0 \_______________________________________________
                         ↑ Erase is completed and the WIP bit of the status register is cleared.
```

Note: 0x06 WREN and 0x20 sector erase are two independent CS frames; after WREN, CS is pulled high, and then pulled low to send the erase command. Reading 256 bytes ≈ 82µs, reading 4KB ≈ 1.3ms; erasing 4KB takes about 200ms.

**Erasing 4KB takes about 200ms, reading 4KB takes about 1.3ms, a difference of about 150 times; if only comparing 256B reading, it is about 2,400 times.**

The performance gap between read operations and write/erase operations is of this order of magnitude. What you learned about "block devices", the two symmetric function signatures of read_block and write_block, masks the entire existence of this gap.

## Block Device Abstraction: A Lie

In operating system textbooks, "Block Device" is a beautiful concept:

```
Textbook block device abstraction
=======================

struct block_device {
    int (*read_block)(int block_no, void *buf);
    int (*write_block)(int block_no, const void *buf);
};

// It works like magic:
char buf[4096];
read_block(5, buf);       // Read the 5th block → 4KB data
buf[100] = 'A';           // Modify one of the bytes
write_block(5, buf);      // Write back block 5
// Done!
```

The core promise of this level of abstraction is: **reading and writing are symmetrical. You operate on logical block numbers and don't care about the physical structure inside. You can modify data "in place".**

For a real disk (HDD), this level of abstraction basically holds:
- `read_block(5, buf)` → The head moves to the cylinder where the 5th sector is located → Read a sector (512B or 4KB)
- `write_block(5, buf)` → The magnetic head moves to the same position → The magnetic field flips and rewrites → The old data is overwritten by the new data

The cost of reading and writing is roughly the same (both seek + rotation delay + read and write time). The granularity is also the same (both sectors).

But for NOR Flash:

```
The Real Situation of "Block Devices" on Flash
=======================

read_block(5, buf):
  → Send 0x03 0x00 0x50 0x00 (address=5×4096=0x5000)
  → Pull CLK and receive data
  → 82 microseconds
  → ✓ Really read it back

write_block(5, buf): ← Wait, can you "write directly"?
  → You can't.
  → Block 5 may not be in erased state (not all 0xFF)
  → You must:
      1. Erase block 5 — 200 ms
      2. Byte-by-byte programming — ~14 microseconds per byte, 4KB = 58 milliseconds (conservative engineering estimate)
      Total time taken: ~258 milliseconds
  → And: if there are other "blocks" logically mapped to different offsets of the same physical block
           You will destroy that data by erasing the 5th physical block!
```

**write_block is not an atomic operation on Flash. It may consist of two steps [erase] + [program], and the physical scope of erasure is much larger than "you want".**

This is the essence of "lie". The block device abstraction makes you think you can "write a block in place", but the physical reality of Flash is: **You can only write a block that has been erased, and the granularity of erasure is greater than you think.**

## The Price of Abstraction: Who Pays for the Lies

Who is paying for this lie? The answer depends on whether you live above or below this level of abstraction.

If you live in the upper echelon and you are a file system developer calling `read_block`/`write_block`, then you are well protected by this lie. You don't need to know that sector erase is 200ms, you don't need to know that the granularity of program and erase is asymmetric, you don't need to know that each block has a 100,000 P/E lifetime. You only need to read and write logical block numbers.

**But your file system may commit suicide without even realizing it.**

For example, you store a frequently modified small file in logical block 5. You call `write_block(5, buf)` every time you modify it. The upper-level block device driver helps you erase + program behind the scenes, every 258 milliseconds. It doesn't tell you "this block is dying", it just faithfully executes your commands. Until one day, `write_block(5, buf)` returns an error. A certain unit in block 5 cannot be programmed, and your entire file system collapses. This is the price of abstraction: **It prevents you from needing to know the physical details, but it also prevents you from making correct decisions based on the physical details.**

If you live in the lower class and you're a NOR Flash driver developer, your life is an endless game of patching. You need:

```
Physical realities faced by NOR Flash drivers
=======================

1. Sector misalignment problem
   write_block(5, buf) requests logical block 5
   But logical block 5 may span two physical sectors
   You erase sector A → destroy the first half of logical block 4
   You erase sector B → destroy the second half of logical block 6

2. Write pause problem
   What if a high priority interrupt comes during the erase 200ms?
   You must handle it in the interrupt service routine
   Or implement erase pause/resume

3. Address mapping problem
   What the file system considers to be a logical block number
   It may not correspond to the physical sector number one-to-one.
   (If there are bad blocks, remap is required)

4. Error handling issues
   What should I do if erasure fails? How many times to retry?
   What should I do if programming fails? Record bad blocks? Migrate data?
   What should I do if ECC correction fails?
```

**"Abstracting" these physical limitations is a huge project in itself.**

## The world of three APIs

In the embedded world, the API design of Flash block devices is basically divided into three schools. Each faction is a different degree of confession of "lies."

**School 1: Synchronization API, the most straightforward lie**

```c
// Synchronous block device interface (suitable for scenarios with OS)
sint32 flash_read_block(uint32 block_id, uint8 *buf);
sint32 flash_write_block(uint32 block_id, const uint8 *buf);
sint32 flash_erase_block(uint32 block_id);
```

The calling thread blocks waiting for the Flash operation to complete. Read blocks for about 82 microseconds (acceptable), write blocks for about 258 milliseconds (which will jam the scheduler), and erase is directly exposed (honest).

This is the most "traditional" design and the default assumption for file systems such as FATFS. The problem with it is: **258 milliseconds of blocking is unacceptable for an RTOS.** In FreeRTOS, a task blocked for 258 milliseconds means:
- If it is the highest priority task (such as Flash writing task), the entire system can do nothing during these 258 milliseconds
- If it is preempted, the mutex it holds may lock other tasks for 258 milliseconds
- If you have CAN messages that need to be processed within 10 milliseconds, then your CAN task has to accompany Flash erasure

**Second School: Asynchronous API, First Confession**

```c
// Asynchronous block device interface (suitable for hard real-time systems)
typedef enum {
    DISK_ASYNC_OP_READ,
    DISK_ASYNC_OP_WRITE,
    DISK_ASYNC_OP_ERASE
} disk_async_op_t;

typedef void (*disk_async_callback_t)(sint32 result);

sint32 disk_async_submit(
    disk_async_op_t op,
    uint32 block_addr,
    uint8 *buf,
    disk_async_callback_t callback
);

bool disk_async_is_idle(void);
sint32 disk_async_wait(void);
```

This is the path typically chosen for production-grade deployments. Submit a Flash operation request, return immediately, and continue running other tasks. When the Flash operation completes, the registered callback function is called, or the task checks the completion status the next time it is polled.

The focus is on the design philosophy of this interface:

```
Synchronous vs Async: Time Escape Diagram
=======================

Synchronous mode (blocking wait):
  Task A: [submit] . . . . . . . . . . . . . . . . [done][process]
                  ↑ ↑
                  └── During the 258ms Flash erase period, Task A cannot do anything ──┘

Asynchronous mode (event-driven):
  Task A: [submit][run other stuff...][poll: done? no][more stuff...][poll: done!][process]
  Flash: . . . . . . . . . . . . . 258ms erase . . . . . . . . . . . . . . . . . . . [done]
          ↑ Flash is busy in the background, Task A continues to run
          At this time, Task A can process CAN messages, update displays, and respond to key presses.
```

**The asynchronous API admits the fact that Flash operations are not "call-return" mode. It is "request-notify" mode. You make a request and then wait for an event.**

Confession comes at a price: asynchronous programming models are far more complex than synchronous ones. You can no longer write:

```c
write_block(5, buf);
process_data(buf);
```

Instead write:

```c
disk_async_submit(DISK_ASYNC_OP_WRITE, 5, buf, on_write_done);
// You cannot touch buf after returning because Flash may still be reading it.
// You cannot call process_data before the on_write_done callback arrives
```

State machines, callbacks, polling, these are a whole new set of complexities introduced by asynchronous programming. But for an ECU that needs to respond every 10 milliseconds on the CAN bus, this is the only option.

**Third school: DMA+interrupt API, complete confession**

```c
// The lowest level Flash access interface (MCAL layer)
void Fls_Read(
    Fls_AddressType SourceAddress,
    uint8 *TargetBufferPtr,
    Fls_LengthType Length
);

void Fls_Write(
    Fls_AddressType TargetAddress,
    const uint8 *SourceBufferPtr,
    Fls_LengthType Length
);

void Fls_Erase(
    Fls_AddressType TargetAddress,
    Fls_LengthType Length
);

// Completion notification via callback
void Fls_JobEndNotification(void);
// Error notification via callback
void Fls_JobErrorNotification(void);
```

This is the standard interface of AUTOSAR FLS (Flash Driver). It doesn't even hide the concept of "address", you pass the physical address directly. There is no block number, no abstraction layer.

Between these three layers of API, each layer is a translation:

```
Translation chain for Flash access
=======================

Fls_Erase(0x5000, 4096) ← MCAL layer: physical address, physical length
        ↓
disk_async_erase(block_5) ← Block device layer: logical block number
        ↓
fs_erase_block(5) ← File system layer: file system block number
```

It is this layer of translation chain that allows the upper-layer file system to think that it is operating a "logical block" without caring whether the physical address is 0x5000 or 0x6000.

## Why embedded systems must take the asynchronous path

Some people may ask: Isn’t the file system on the PC synchronized? Aren’t Linux’s `read()` and `write()` system calls blocking? Doesn’t erasing PC’s NVMe SSD also take time?

The answer is: **PC's NVMe SSD has its own FTL (Flash Translation Layer) controller, which is a firmware running on the ARM Cortex-R or similar core inside the SSD.** This controller takes the pain of asynchrony for you.

```
Asynchronous processing of PC SSD is transparent
=======================

Your program: write(fd, buf, 4096);
          ↓ System call, your thread enters D state (uninterruptible sleep)
NVMe driver: Submit write commands to submission queue
SSD controller: Receive command → allocate free block → write data → update mapping table
           → Background GC → Ring doorbell after completion
          ↓ Your thread is awakened
Your program: write() returns

Do you think write() is "synchronous"?
But the SSD controller is out of sight,
All complex logic is handled with an asynchronous state machine.
```

Embedded systems don't have this luxury. Your MCU may not even have an SSD controller. You connect it directly to the SPI bus of NOR Flash, and programmed erasure and programming are completely under your control. **You are both the application and the FTL controller.** Therefore, asynchronous I/O is a "must" choice. Your ECU cannot stop doing nothing for 258 milliseconds. If an emergency braking command comes on the CAN bus during these 258 milliseconds, you must respond at the microsecond level.

## The "Art of Blocking" for Block Devices: How to Choose Block Size

Last question: How big is the block?

In `disk_async.h`, you see this definition:

```c
#define FS_BLOCK_SIZE (4096) // 4KB = one NOR Flash sector
#define FS_BLOCK_COUNT (128) // 128 blocks × 4KB = 512KB
```

Why 4KB?

For NOR Flash, the answer is: **Because the erase sector of NOR Flash is 4KB.** It's not your choice, it's the chip manufacturer's choice.

But why is the sector of NOR Flash 4KB? Because this is an engineering compromise between erase block architecture, page programming/ECC overhead, metadata granularity, and GC efficiency:
- Too small (such as 512B): The number of sectors increases sharply → metadata management costs increase → the wear record table becomes larger
- Too large (e.g. 64KB): too much data is destroyed in one erase → GC is inefficient → write amplification soars

4KB is a proven sweet spot.
