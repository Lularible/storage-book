# 4.6 Directory: The Directory Is a File

## Your folder is completely different than you imagined

Let’s do an experiment first. Open your terminal and type `ls -l /usr/bin`. You see hundreds of file entries, names, sizes, permissions, timestamps, neatly arranged. You think that a "directory" is a special structure with grids inside, and each grid contains a file.

This is a convenient lie.

In LittleFS, directories are not "containers of files". A directory is just a file. To be more precise, the directory is a metadata pair marked with the `LFS_TYPE_DIR` type. It is stored in a block just like an ordinary file. It uses the same two-block log mechanism to perform atomic updates and has no privileges at the bottom of the data block.

```
The directory you thought: The truth about LittleFS:
┌─────────────────┐ ┌──────────────────┐
│ Directory container │ │ metadata pair │
│ ┌───┐ ┌───┐ │ │ [revision=5] │
│ │ A │ │ B │ │ │ name="foo" REG │
│ └───┘ └───┘ │ │ name="bar" DIR │
│ ┌───┐ │ │ name="baz" REG │
│ │ C │ │ │ [checksum] │
│ └───┘ │ └─────────────────┘
└─────────────────┘
                                           ↑
                              It is a file with a special tag
```

This design is extremely elegant. The directory does not require an independent storage structure, allocator or power-off protection. All codes for processing files (log append, garbage collection, CRC check) are all reused on the directory. Less code, less bugs.

How does the directory know "who is in this folder"? The answer is hidden in the entry of the metadata pair.

## Name Game in Metadata Pair

Recall the format of the data block. Each metadata pair is a two-block log structure that stores several entries. Each entry is a combination of tag + data.

When the tag type of an entry is `LFS_TYPE_NAME` (type number `0x0xx`), its data part stores a **file name**. The id field (10 bits) in tag associates this name with subsequent structural information.

```
The complete composition of a directory entry:

tag: LFS_TYPE_CREATE, id=3
     → "Creator" tag, declares the existence of file id=3

tag: LFS_TYPE_NAME, id=3, type=REG, data="hello.txt"
     → The name is "hello.txt", which is an ordinary file

tag: LFS_TYPE_CTZSTRUCT, id=3, data={head=0x2A, size=4096}
     → Header block and file size of CTZ skip-list

tag: LFS_TYPE_CRC
     → Submission completed, CRC verification stamped
```

This is the whole secret of the LittleFS directory: the directory is a metadata pair, and the directory entries are the entries in the metadata pair.

Directories do not have separate "directory entry structures". The file name is stored in the name tag. The file type is stored in the chunk field of the name tag. The location of the file data is stored in the struct tag (CTZSTRUCT or DIRSTRUCT or INLINESTRUCT). id strings these scattered tags together.

This is the power of the "tag system", one of the most genius inventions in LittleFS: a 32-bit tag that is both a type, an index, and a length. A `LFS_TYPE_DIRSTRUCT` tag is followed by an 8-byte metadata pair pointer (two 32-bit block numbers) pointing to the location of the subdirectory on disk.

```
root directory (metadata pair at block 0,1)
                    ┌───────────────────────────┐
                    │ revision = 3 │
                    │ name="subdir", id=1, DIR │ ← declares that id=1 is a directory
                    │ struct=DIRSTRUCT, id=1, │ ← metadata pair pointing to the subdirectory
                    │ pair={block=14,block=27}│
                    │ name="readme.txt", id=2 │
                    │ struct=CTZSTRUCT, id=2, │
                    │ head=40, size=1024 │
                    │CRC │
                    └───────────────────────────┘
                              │
                              v
                    sub directory (metadata pair at block 14,27)
                    ┌───────────────────────────┐
                    │ revision = 1 │
                    │ name="config.json", id=1 │
                    │ struct=INLINESTRUCT, id=1,│
                    │ data="{...}" │
                    │CRC │
                    └───────────────────────────┘
```

## lfs_dir_find: Find a fish in the ocean of metadata pairs

`lfs_dir_find()` is one of the most called functions in LittleFS. `lfs_file_open()` calls it, `lfs_mkdir()` calls it, `lfs_remove()` calls it, `lfs_stat()` calls it. The first step in almost all file system operations is to "find the directory entry for the target file."

Its core logic is very simple:1. Start from the root directory and take the path `"/subdir/hello.txt"`.
2. Find the first name `"subdir"`, traverse all name tags in the root metadata pair, and perform string comparison.
3. After finding it, extract the metadata pair pointer of the subdirectory from the corresponding struct tag.
4. `lfs_dir_fetch()` loads the metadata pair of the subdirectory from disk to RAM.
5. Repeat step 2 until the last segment of the path.

```
"/subdir/hello.txt"
     ↓
    root pair (block 0,1)
     │ Traverse name tags and find "subdir"
     │ Find → Extract pair={14,27}
     ↓
    subdir pair (block 14,27)
     │ Traverse name tags and find "hello.txt"
     │ Find → Return tag (contains id and type information)
     ↓
    The caller takes the returned tag and continues the operation.
```

But LittleFS's implementation is much more elegant than this overview. Look at the source code of `lfs.c:1483`:

```c
static lfs_stag_t lfs_dir_find(lfs_t *lfs, lfs_mdir_t *dir,
        const char **path, uint16_t *id) {
    const char *name = *path;
    lfs_stag_t tag = LFS_MKTAG(LFS_TYPE_DIR, 0x3ff, 0);
    dir->tail[0] = lfs->root[0];
    dir->tail[1] = lfs->root[1];
    // ...
```

At the beginning of the function, dir points to root and tag is set to DIR type. Then it enters an infinite loop and parses the path step by step. In this loop, LittleFS does a few very smart things:

First thing: use `strspn + strcspn` to parse the path piece by piece, but not simply split.

It uses `strspn(name, "/")` to skip slashes and `strcspn(name, "/")` to find the end of the name. It then also looks ahead the rest of the path, processing `..` and `.`. If there is a symmetrical `..` in the remaining path that can offset the current path segment, it will directly skip the current segment without actually reading the parent directory.

```c
        // skip if matched by '..' in name
        const char *suffix = name + namelen;
        lfs_size_t sufflen;
        int depth = 1;
        while (true) {
            suffix += strspn(suffix, "/");
            sufflen = strcspn(suffix, "/");
            if (sufflen == 0) break;
            if (sufflen == 2 && memcmp(suffix, "..", 2) == 0) {
                depth -= 1;
                if (depth == 0) {
                    name = suffix + sufflen;
                    goto nextname;
                }
            } // ...
```

The meaning of this code is: if the path is `"a/../b"`, when LittleFS parses `"a"`, it will find that the following `".."` can offset `"a"`, so it directly jumps the name pointer to the position of `"b"`, without a disk read.

This is the ultimate optimization thinking. On a 32 MHz Cortex-M0, one less Flash read equals hundreds of microseconds less latency.

The second thing: `lfs_dir_fetchmatch()`, with callback function to match.

`lfs_dir_fetchmatch()` is another exquisite design in LittleFS. It loads the metadata pair, iterates through all tags in it, and then calls a user-provided callback function (here `lfs_dir_find_match`) to compare the current tag's data with the target name.

```c
            tag = lfs_dir_fetchmatch(lfs, dir, dir->tail,
                    LFS_MKTAG(0x780, 0, 0),
                    LFS_MKTAG(LFS_TYPE_NAME, 0, namelen),
                    id,
                    lfs_dir_find_match, &(struct lfs_dir_find_match){
                        lfs, name, namelen});
```

`lfs_dir_fetchmatch` only processes the current metadata pair. The loop across split pairs is in `lfs_dir_find`: as long as `dir->split` is true, it continues to call fetchmatch.

The third thing: When the tag's id is `0x3ff`, it represents the global tag.

`0x3ff` (10 bits all 1) is a special id, indicating that this entry is not associated with any specific file. The tag of the Root directory itself is `LFS_MKTAG(LFS_TYPE_DIR, 0x3ff, 0)`, the type is DIR, and the id is `0x3ff`. This means that root is not a "file", it is just the starting point of the system.

When `lfs_dir_find` traverses to an id other than `0x3ff`, it means it found a real subdirectory. At this time, it calls `lfs_dir_get()` to extract the metadata pair pointer from the struct tag, and then continues the recursion.

If no matching name is found after traversing all split pairs, the function returns `LFS_ERR_NOENT`, which is "No Entry". This is not an error, this is the normal semantics of "file does not exist".

## lfs_dir_read: Traversing a directory is like flipping through a book`lfs_dir_read` is the "page turning" operation of the directory. Each call returns a `lfs_info` structure, including file name, type, and size. Returns 0 to indicate the end of the directory.

```c
static int lfs_dir_read_(lfs_t *lfs, lfs_dir_t *dir, struct lfs_info *info) {
    memset(info, 0, sizeof(*info));
    if (dir->pos == 0) {
        info->type = LFS_TYPE_DIR;
        strcpy(info->name, ".");
        dir->pos += 1;
        return true;
    } else if (dir->pos == 1) {
        info->type = LFS_TYPE_DIR;
        strcpy(info->name, "..");
        dir->pos += 1;
        return true;
    }
    while (true) {
        if (dir->id == dir->m.count) {
            if (!dir->m.split) return false;
            int err = lfs_dir_fetch(lfs, &dir->m, dir->m.tail);
            if (err) return err;
            dir->id = 0;
        }
        int err = lfs_dir_getinfo(lfs, &dir->m, dir->id, info);
        dir->id += 1;
        if (err != LFS_ERR_NOENT) break;
    }
    dir->pos += 1;
    return true;
}
```

There are several things worth noting about this design:

Virtual `.` and `..`. These two entries are not stored on disk. They are the first position (pos=0) and the second position (pos=1) of Read generated directly by the code. This saves two entries on disk and the trouble of maintaining these two entries every time the directory is updated.

**across split pairs**. When `dir->id` reaches the boundary of the current metadata pair (`dir->m.count`), the function checks `dir->m.split`. If split is true, it means that the data in this directory spans multiple metadata pairs (because the current pair is full), and the function automatically loads the next pair and resets the id to 0.

**Skip deleted entries**. `lfs_dir_getinfo` Returns `LFS_ERR_NOENT` for deleted entries. The `lfs_dir_read_`'s while loop will skip these entries and continue looking for valid entries. This is why users never see deleted files: they are automatically filtered while traversing.

## lfs_mkdir: Creating a directory is creating a file

The implementation of `lfs_mkdir` further proves the concept of "directory as file".

```c
static int lfs_mkdir_(lfs_t *lfs, const char *path) {
    int err = lfs_fs_forceconsistency(lfs);  // Do orphan cleanup first
    struct lfs_mlist cwd;
    uint16_t id;
    err = lfs_dir_find(lfs, &cwd.m, &path, &id);
    if (!(err == LFS_ERR_NOENT && lfs_path_islast(path))) {
        return (err < 0) ? err : LFS_ERR_EXIST;
    }
    // ...assign a new directory pair...
    err = lfs_dir_alloc(lfs, &dir);
    // ...submit a new entry in the parent directory...
    err = lfs_dir_commit(lfs, &cwd.m, LFS_MKATTRS(
            {LFS_MKTAG(LFS_TYPE_CREATE, id, 0), NULL},
            {LFS_MKTAG(LFS_TYPE_DIR, id, nlen), path},
            {LFS_MKTAG(LFS_TYPE_DIRSTRUCT, id, 8), dir.pair},
            {LFS_MKTAG_IF(!cwd.m.split,
                LFS_TYPE_SOFTTAIL, 0x3ff, 8), dir.pair}));
    return 0;
}
```

This code does four things:

1. **Orphan Cleanup**: `lfs_fs_forceconsistency()`. This is a safety check before each write operation. If the last power outage left a semi-finished product, clean up the mess first this time.

2. **Check that the names do not conflict**: Call `lfs_dir_find` to find the target name. If found (not `LFS_ERR_NOENT`), the file already exists and `LFS_ERR_EXIST` is returned.

3. **Allocate a new metadata pair**: `lfs_dir_alloc` allocates an empty metadata pair. This pair will henceforth be the "flesh" of this new directory.

4. **Commit** in the parent directory: up to four tags (`SOFTTAIL` appears when not split):
   - `LFS_TYPE_CREATE`: Mark the presence of file id
   - `LFS_TYPE_DIR`: name + type (directory)
   - `LFS_TYPE_DIRSTRUCT`: metadata pair pointer of subdirectory

Note that `LFS_MKATTRS` packages these tags into an atomic commit. The entire mkdir consists of multiple commits; the parent directory will not be visible to the user until this submission is successful. A power outage will not leave a semi-remnant directory with "only names and no structure".

## lfs_remove: Deleting a directory also deletes a file

```c
static int lfs_remove_(lfs_t *lfs, const char *path) {
    int err = lfs_fs_forceconsistency(lfs);
    lfs_mdir_t cwd;
    lfs_stag_t tag = lfs_dir_find(lfs, &cwd, &path, NULL);
    // ...directory must be empty...
    if (lfs_tag_type3(tag) == LFS_TYPE_DIR) {
        lfs_block_t pair[2];
        lfs_stag_t res = lfs_dir_get(lfs, &cwd, ...);
        err = lfs_dir_fetch(lfs, &dir.m, pair);
        if (dir.m.count > 0 || dir.m.split) {
            return LFS_ERR_NOTEMPTY;
        }
        err = lfs_fs_preporphans(lfs, +1);  // Mark orphan status
    }
    // Delete entry
    err = lfs_dir_commit(lfs, &cwd, LFS_MKATTRS(
            {LFS_MKTAG(LFS_TYPE_DELETE, lfs_tag_id(tag), 0), NULL}));
```

The process of deleting a directory is almost the same as deleting an ordinary file, the only difference is that the directory must be empty (`dir.m.count > 0 || dir.m.split`). LittleFS refuses to delete non-empty directories through `LFS_ERR_NOTEMPTY`. This classic POSIX semantics is also faithfully implemented in the 32 KiB Flash file system.

Another detail is the `lfs_fs_preporphans(lfs, +1)`. When a directory is deleted, if the metadata pair of the parent directory is split during submission, the deleted subdirectory may temporarily remain in the threaded linked-list and become an "orphan". `preporphans` adds a global counter so that the file system knows that orphan cleaning needs to be done when mounting.

## Comparison with KnotFS: a tree and a blank paperLittleFS has a complete directory tree. KnotFS has no directories, it is a **flat file system**.

```
Directory tree of LittleFS: Flat structure of KnotFS:
/ ┌──────────────────────┐
├── config/ │ hello.txt 4KB │
│ ├── can.json │ can_config 512B │
│ └── lidar.json │ firmware.bin 128KB │
├── logs/ │ diag.log 64KB │
│ └── diag.log └──────────────────────┘
└── hello.txt
```

KnotFS does not have `mkdir`. All files are in a flat namespace, directly indexed by 32-byte names. The File Table is an array with fixed 8 slots. Each slot either stores a file entry or `size == 0` indicates free/deleted.

This design stems from the target scenario of KnotFS: functions running on the automotive MCU do not require multi-layer directories. A few configuration files, a log file, a firmware upgrade package, 8 slots are more than enough. The flat file table structure eliminates all the complexity of directory traversal, no recursive parsing paths, no linked list tracking of split pairs, and no semantic processing of `..` and `.`.

But flat structures also sacrifice organization. If you have 30 configuration files of different types (CAN matrices, LIDAR parameters, sensor calibrations...), you can only prefix the file names with something like `can_matrix_v2.bin`, `lidar_calib_v1.bin`, with no real way to group them.

LittleFS's directory design also has an issue that KnotFS doesn't cover at all: **name sorting**. In LittleFS directory metadata pairs, file entries are arranged alphabetically. This is thanks to the two splice tags `LFS_TYPE_CREATE` and `LFS_TYPE_DELETE`, which allow items to be inserted and deleted in the ordered list without rewriting the entire list.

```
Storage of directory entries in metadata pairs (sorted by name):

[name="apple", id=1] [name="banana", id=2] [name="cherry", id=3]
                                                    ↑
                   When inserting "blueberry", CREATE tag inserts id=2.5 into
                   Between banana and cherry, the relative position of the ids of other entries moves
```

This insertion mechanism is very clever. The id can be allocated arbitrarily within the 10-bit space and is not fixed. When inserting a new file, you only need to assign a virtual id to the new file (the middle value of two adjacent file ids), and then attach the `LFS_TYPE_CREATE` tag when submitting to tell the scanner "this id is here".

The file table of KnotFS does not need to be sorted. The order of the 8 slots is the physical storage order of the files. The find operation simply traverses the array and performs string comparison.

## The secret of directory traversal: Threaded Linked-List

LittleFS's directory tree has an additional structure: **threaded linked-list**. This linked list goes through every metadata pair in the file system, making it possible to traverse the entire file system.

```
            .--------.
           .| root   |-.
           ||        | |        ← soft tail
    .------||        |-'
    |      |'--------'
    |      '---|--|-'
    |       .-'    '-------------------------.
    |      v                                  v
    |  .--------.        .--------.        .--------.
    '->| dir A  |------->| dir A  |------->| dir B  |
      ||        |       ||        |       ||        |
      ||        |       ||        |       ||        |
      |'--------'       |'--------'       |'--------'
      '---|--|-'        '----|---'        '---|--|-'
       .-'    '-.            |             .-'    '-.
      v          v           v            v          v
 .--------.  .--------.  .--------.  .--------.  .--------.
 | file C |  | file D |  | file E |  | file F |  | file G |
 |        |  |        |  |        |  |        |  |        |
 '--------'  '--------'  '--------'  '--------'  '--------'
```

Each metadata pair has a soft tail pointer that points to the next pair on the linked list. This linked list exists for two reasons:

1. **Bounded RAM Traversal**: LittleFS promises O(1) memory usage. You cannot maintain a directory tree in RAM. threaded linked-list allows traversal to proceed step by step while only remembering the "current position".

2. **Orphan Detection**: Traverse this linked list when mounting and check whether each pair has a parent node in the directory tree. Nodes without a parent are orphans, which may have been left behind by the last power outage.

After six sections, you have seen all the core data structures of LittleFS. Metadata Pair's atomic metadata update, CTZ Skip-List's O(log n) file data management, and lookahead allocator running on 4MB Flash. These are the results of ten years of polishing of industrial-grade code. But you don’t read LittleFS to copy it. You read it to understand one thing: the same theory can grow into completely different implementations when the design constraints are different.  LittleFS chose the synchronous API because it targets MCUs with RTOS and callers can accept blocking. And the thought experiment we did in Chapter 3 tells you: In a bare metal/RTOS scenario, the file system cannot "block waiting for Flash erasure to complete". During the 200ms erase delay, the CPU has more important things to do.

So in the next chapter we will not copy LittleFS. We took its proven core concepts, namely Metadata Pair's atomic commit, log-structured metadata, and Copy-on-Write's power-down safety, and put them into a completely different shell: **Asynchronous State Machine + Collaborative Event Loop**. This is KnotFS.

No operating system, no dynamic memory allocation, just about 1165 lines of core C code and 64KB of "paper Flash". See if the theory in Chapter 3 and the industrial practice in Chapter 4 can all be realized on a 16-block chessboard.

Suspense left: All operations of LittleFS are synchronous, and the `lfs_file_write()` call will block until the Flash erase is completed. In a bare-metal cycle without an operating system, you can't "wait". You have to break down the 100ms erase into a cooperative state machine of dozens of ticks. How does KnotFS achieve "non-blocking"?
