# 5.2 Flash Layout: A 16-Block × 4KB Board

## A 64KB map

You get a NOR Flash chip. There are 65536 independently addressable bytes on it, which is 64KB.

But you don't think of these 64KB as 65536 independent grids. You would cut it into 16 chunks of 4096 bytes each. This is not arbitrary. The smallest erasing unit of NOR Flash is "block" (block, also called sector). You can write (program) at any byte position within the block, but to make the already written place writable again, you must erase it in blocks, that is, reset the entire block to 0xFF.

**Erase is the breath of Flash. You cannot directly overwrite the written area with a new value. You must first erase the entire block to 0xFF and then write into it.** This is a law of physics, not a bug. The electrons in the floating-gate transistor are trapped and can only be released through an erase operation (applying a reverse high voltage).

So the first design question of the file system is: How to divide these 16 blocks?

KnotFS's answer is:

```
KnotFS Flash layout (16 blocks × 4096 bytes = 64KB)
=====================================================

 Block 0 [██████████████████████████████████████] SB0 Super Block A
        ┌───────────────────────────────────────┐
        │ magic=KNFS version=1 sequence=... │ ← 668-byte header
        │ free_map wear[16] nodes[8] crc32 │
        ├───────────────────────────────────────┤
        │ log[0] log[1] log[2] ... │ ← 3424-byte Log area = 428 records + 4-byte tail
        │ (8 bytes each: tag/blk/val/crc32) │
        └───────────────────────────────────────┘

 Block 1 [██████████████████████████████████████] SB1 Super Block B
        Same as SB0 structure - this is the "backup directory"

 block 2 [ ] ← data block
 Block 3 [ ] ← data block
 Block 4 [ ] ← data block
 Block 5 [ ] ← data block
 Block 6 [ ] ← data block
 Block 7 [ ] ← data block
 Block 8 [ ] ← data block
 Block 9 [ ] ← data block
 Block 10 [ ] ← data block
 Block 11 [ ] ← data block
 Block 12 [ ] ← data block
 Block 13 [ ] ← data block
 Block 14 [ ] ← data block
 Block 15 [ ] ← data block

Blocks 2~15 = 14 data blocks = 56KB available space
Maximum 8 direct blocks per file = 32KB
```

This layout is hardcoded in the code as a few macros:

```c
// knotfs.h — Flash geometric constants
#define KNOTFS_BLOCK_SIZE     (4096U)    /* bytes per flash block            */
#define KNOTFS_BLOCK_COUNT    (16U)      /* total blocks (16 x 4K = 64 KB)   */
#define KNOTFS_SB0_BLK        (0U)       /* superblock A lives in block 0     */
#define KNOTFS_SB1_BLK        (1U)       /* superblock B lives in block 1     */
#define KNOTFS_DATA_START     (2U)       /* first data block                 */
#define KNOTFS_DATA_BLKS      (KNOTFS_BLOCK_COUNT - KNOTFS_DATA_START)  /* 14 */
#define KNOTFS_DIRECT_BLKS    (8U)       /* max data blocks per file         */
#define KNOTFS_FILE_LIMIT     (KNOTFS_DIRECT_BLKS * KNOTFS_BLOCK_SIZE) /* 32K */
```

Pay attention to the calculation of `KNOTFS_DATA_BLKS`: `16 - 2 = 14`, "two blocks were deducted to make a directory backup".

## Why does the super block occupy two separate blocks?

You may ask: The super block is only 4096 bytes. Can I put SB0 in the first 2048 bytes of block 0 and SB1 in the last 2048 bytes of block 0? Wouldn't this save a data block?

cannot. Because the smallest erase unit of Flash is a block. If you put SB0 and SB1 in the same block, and each time you need to update one of them (such as rewriting SB1 to do compact), you must erase the entire block, which will also kill SB0. If there is a power outage during the erasure process, you will lose two super blocks and the file system will hang.

**Placing two copies of the super block on different physical blocks is the first life-saving rule of the Flash file system.**

There is a deeper reason: SB0 and SB1 are not just backups, they are used interchangeably. KnotFS has a pair of mutually exclusive slot selection functions:

```c
// knotfs.c — Active slots (target for Log writing) and inactive slots (target for compact)
static uint32_t active_sb_slot(void) {
  return (sb.sequence & 1U) ? KNOTFS_SB1_BLK : KNOTFS_SB0_BLK;
}

static uint32_t inactive_sb_slot(void) {
  return (sb.sequence & 1U) ? KNOTFS_SB0_BLK : KNOTFS_SB1_BLK;
}
```

The parity of `sequence` determines the current active slot: even → block 0 active/block 1 inactive, odd → the opposite. At the end of each compact, the two slots switch ping-pong and take turns assuming the role of "currently valid copy". This has two benefits:
1. **Power-off safety**: Even if the power is cut off when writing a new SB, the old SB will still be intact.
2. **Even wear**: The number of erasing and writing times of SB0 and SB1 is roughly equal. There will be no situation like "SB0 is erased and written 100,000 times, SB1 is erased and written 10 times".

## How to divide the "layout" inside the super block?

A superblock is 4096 bytes and is divided into two areas:

```
Superblock internal layout (4096 bytes)
=====================================

 Byte 0···667 [header header area] 668 bytes
     magic (4B) ← "KNFS" magic number
     version (4B) ← version number
     sequence (4B) ← monotonically increasing sequence number
     log_offset (4B) ← Current writing position of Log area
     log_count (4B) ← Number of Log entries written
     free_map (4B) ← 16-bit block allocation bitmap
     wear[16] (64B) ← Erase count per block
     nodes[8] (576B) ← 8 file entries (72 bytes each)
     crc32 (4B) ← header checksum

 Bytes 668···4095 [log log area] 3424 bytes + 4B tail
     log[0] (8B) ← 1st log
     log[1] (8B) ← Log 2
     log[2] (8B) ← Log 3
     ... ← Up to 428 items (3424/8)
     (Fill the remaining space with 0xFF) ← Unused Flash default state
```

Constants in the code:

```c
// knotfs.c — SB internal space calculation
#define SB_HEADER_SZ     (sizeof(knot_sb_t))
#define LOG_ENTRY_SZ     (8U)
#define LOG_ENTRIES_MAX  ((KNOTFS_BLOCK_SIZE - SB_HEADER_SZ) / LOG_ENTRY_SZ)  /* 428 */
#define LOG_THRESHOLD    (LOG_ENTRIES_MAX * KNOTFS_LOG_THRESHOLD / 100U)       /* 214 */
```

668-byte header + 3424-byte Log area + 4-byte tail = 4096 bytes, which exactly fills one block. The design recommends compacting the log when it is used 50% (approximately 214 entries); the current teaching implements compacting after every metadata operation, and this threshold is not enabled.

## knode_t: Anatomy of a file entry

The file entry for KnotFS is called `knode_t`:

```c
// knotfs.c — file entry structure
typedef struct {
  char name[KNOTFS_NAME_LEN];
  uint32_t size;
  uint32_t block_count;
  uint32_t blocks[KNOTFS_DIRECT_BLKS];
} knode_t; /* file entry (the name is deliberately different from SimpleFS) */
```

Total of 72 bytes. 8 file entries = 576 bytes, which is exactly the space of `nodes[8]` in the SB header.

The core of each `knode_t` is the `blocks[8]` array, which is the "block mapping table" of the file. Suppose a file "hello.txt" is 14KB, it requires 4 data blocks (14KB / 4KB = 3.5, rounded up to 4). `blocks[0]` to `blocks[3]` record the physical block numbers of these four data blocks respectively. When reading a file, KnotFS calculates which block should be read based on the offset ÷4096, and then reads that block from Flash:

```c
// knotfs.c — block index calculation during read operations
case ST_RD_LOOKUP:
    nd = find_node(cur.name);
    /* ... */
    {
      uint32_t end = cur.r_off + cur.r_sz;
      if (end > nd->size)
        end = nd->size;
      sblk = cur.r_off / KNOTFS_BLOCK_SIZE;
      eblk = (end + KNOTFS_BLOCK_SIZE - 1) / KNOTFS_BLOCK_SIZE;
      if (eblk > nd->block_count)
        eblk = nd->block_count;
    }
    scratch[SCR_RD_SBLK] = sblk;
    scratch[SCR_RD_EBLK] = eblk;
    subst = sblk;
    prog = 0;
    cur.st = ST_RD_DATA;
    return;
```

Note that `size` and `block_count` are independent fields. A file might be 100 bytes, but occupy a full 4KB block (because the allocation unit is blocks). It is also possible that a file has 0 bytes (just created and not written). At this time, `block_count = 0` and `blocks[]` are all 0.

## free_map: 16 bits handle the allocation of all blocks

KnotFS's block allocation bitmap is a simple `uint32_t`:

```c
// Fields in knot_sb_t
uint32_t free_map; /* bitmask: 16 blocks -> fits in 1 uint32 */
```

Each bit represents the allocation status of a block:
- bit 0 → block 0 (SB0), always "used"
- bit 1 → block 1 (SB1), always "used"
- bit 2 → block 2 (data block)
-...
- bit 15 → block 15 (data block)

set bit = used, clear bit = free.

The function to operate free_map is extremely simple:

```c
// knotfs.c — Bitmap operations
static void mark_free(uint32_t b) { sb.free_map &= ~(1U << b); }
static void mark_used(uint32_t b) { sb.free_map |= (1U << b); }
static bool is_free(uint32_t b) { return !(sb.free_map & (1U << b)); }
```

When formatting, block 0 and block 1 are marked as used:

```c
// knotfs.c — mark SB blocks in format
memset(&sb, 0, sizeof(sb));
sb.magic = KNOTFS_MAGIC;
sb.version = KNOTFS_VERSION;
sb.sequence = 0;
sb.log_offset = SB_HEADER_SZ;
for (uint32_t i = 0; i < KNOTFS_DATA_START; i++)
  mark_used(i);
```

Looping `i < KNOTFS_DATA_START` is `i < 2`, so block 0 and block 1 are marked as used. The other 14 data blocks are initially free.

## Library Metaphor: General Catalog and Bookshelf

There is a rule for the collection management of a library: two copies of the general catalog of collections are kept, one is placed in the catalog cabinet at the front desk, and the other is placed in the safe at the back to prevent fire. This is completely consistent with the double SB design of KnotFS.

Imagine that you have to manage a library in a 64-grid (=64KB) library space. In cells 0 and 1 (the two cells facing the door), instead of placing bookshelves, you place two identical "catalogue cabinets". Put a collection distribution map in each cabinet: which grids have bookshelves (set bit of free_map), how many times each bookshelf has been read (wear[]), and how many rows of bookshelves there are in total (nodes[]).

The remaining 14 grids are yours to use. You can place bookshelves (data blocks) on it, and each bookshelf can store up to 4096 books (the size of a block). A borrowing registration card (knode_t) can register up to 8 bookshelves (blocks[8]), so the maximum storage capacity of your borrowing area is 32,000 books.

When recataloging (compact), you clear out the old catalog cabinet and put the latest collection distribution map in the new cabinet. This new cabinet has a higher serial number than the old cabinet. When a visitor comes, he glances at the two cabinets and knows which one is new.

If there is a power outage (power loss) during the recataloging process, at least one cabinet will still be intact. After the call, you find the collection map from the intact cabinet and continue managing your library.

## Are 14 data blocks enough?

For teaching, that's enough. 14 blocks × 4KB = 56KB. The largest file in the test case is 8KB (`t3_large_file`), occupying 2 blocks. After that there are still 12 blocks free.

But it's not enough for production. An embedded system with real needs may require tens or even hundreds of MB of storage. This is why the production-level solution introduces indirect blocks and a larger block number, supporting 128 blocks (512KB), to exceed the limit of the number of direct blocks through indirect blocks.

---

> ⚠️ **Teaching Simplification Tip**: KnotFS's `free_map` is a `uint32_t`, covering exactly 16 blocks. The production-level solution `free_bitmap` needs to cover 128 blocks, so a 4×32-bit array is used. The file table of KnotFS is directly placed in the SB using `nodes[8]`, while the production-level solution will have independent File Table blocks (FT0 in block 2, FT1 in block 3), and each FT block has independent Log append space to reduce SB wear.
