# 4.3 Metadata Pairs: Atomic Commit with Two Mirrored Pages

## Why are two blocks enough?

Now you are faced with a question: How to implement a "small log" that can be submitted atomically on a NOR Flash that can only be erased in its entirety?

The classic definition of a log is a ring buffer where you keep appending records and go back to the beginning when you reach the end. But on Flash, "erase at end" means you have to erase a whole block. If the erase operation loses power in the middle, the block becomes a half-erased garbage state. So you need at least two blocks: while one is actively being written to, the other is either empty (just erased) or holds historical data.

**This is the fundamental reason for Metadata Pair: two pieces of Flash, one active and one standby. ** Not three blocks, not four blocks, two blocks is the minimum configuration to maintain "atomicity + no data loss".

```
Basic structure of Metadata Pair
=========================================

         pair[0] pair[1]
    ┌──────────────┐ ┌──────────────┐
    │ revision: 3 │ │ revision: 2 │
    │──────────────│ │──────────────│
    │ entry A' │ ← latest │ entry A │ ← old data
    │──────────────│ │──────────────│
    │ entry B' │ │ entry B │
    │──────────────│ │──────────────│
    │ entry C │ │ entry C │
    │──────────────│ │──────────────│
    │ checksum │ │ checksum │
    └──────────────┘ └──────────────┘
         ↑ Active ↑ Inactive
    revision larger revision smaller
```

Each metadata pair consists of two block addresses: `pair[0]` and `pair[1]`. By comparing the revision counts in the two blocks (using sequence number arithmetic to prevent problems caused by integer overflows), LittleFS knows which one is the "newest". **revision is essentially the number of compactions this metadata pair has experienced, and revision+1 is applied each time it is compacted. **

In LittleFS, the structure of metadata pair is `lfs_mdir_t`:

```c
// lfs.h:377-386 — metadata directory runtime status
typedef struct lfs_mdir {
    lfs_block_t pair[2];    // The addresses of the two blocks
    uint32_t rev;           // Current revision (value in RAM)
    lfs_off_t off;          // Current read/write offset
    uint32_t etag;          // end tag: the last valid tag
    uint16_t count;         // Split count (number of sub-blocks after directory split)
    bool erased;            // Whether the spare block has been erased
    bool split;             // Whether it has been split (there is a tail pointing to the next metadata pair)
    lfs_block_t tail[2];    // Tail address after splitting
} lfs_mdir_t;
```

On the disk, the format of each metadata block is extremely simple:

```
Metadata Block on-disk format
=========================================

Offset 0: revision (4 bytes, little-endian)
         ┌─────────────────────────────┐
         │ entry 1: tag + data │
         │ entry 2: tag + data │
         │ entry 3: tag + data │
         │ ... │
         │ entry N: tag + data │
         │ padding │
         │ CRC (4 bytes, little-endian)│ ← last 32-bit word
         └─────────────────────────────┘

Note: Entries grow from the beginning of the block to the end.
      CRC is always at the end of the block
      The area in the block not covered by entry is 0xFF (erased state)
```

Each entry consists of a tag (4 bytes) and subsequent data. The tag encodes the type, ID and data size. When LittleFS reads the end of the data, it checks the CRC. If the CRC matches, the contents of the entire block are credible.

## Three steps of atomic commit

The "atomic commit" of the Metadata pair is mathematically guaranteed as follows: **When the power is turned off at any time, at least one of the two blocks contains complete and CRC-checked data. **

This guarantee is achieved through the careful orchestration of three operating modes:

**Mode 1: Append, when the block is not full**

This is the ideal situation. There is still space in the active block, so you can add a new entry directly after the existing entry. The consequence of a power outage during the append process is that the CRC cannot cover the unfinished entry, so the old CRC is still valid. When mounting, LittleFS reads the old CRC, ignores the incomplete tail, and returns to the last complete state.

```
Power loss safety during append operations
=========================================

commit A:
┌───────────────┬─────────────┐ ┌──────────────┬───────────────┐
│ rev=1 │ rev=0 │ │ rev=1 │ rev=0 │
│──────────────│ │ │──────────────│ │
│ │ │ ==> │ A │ │
│ │ │ │──────────────│ │
│ │ │ │ CRC(ok) │ │
└───────────────┴──────────────┘ └──────────────┴───────────────┘

commit B and A':
┌───────────────┬─────────────┐ ┌──────────────┬───────────────┐
│ rev=1 │ rev=0 │ │ rev=1 │ rev=0 │
│──────────────│ │ │──────────────│ │
│ A │ │ │ A │ │
│──────────────│ │ │──────────────│ │
│ CRC(ok) │ │ │ B │ │
│ │ │ ==> │──────────────│ │
│ │ │ │ A' │ │
│ │ │ │──────────────│ │
│ │ │ │ CRC(ok) │ │
└───────────────┴──────────────┘ └──────────────┴───────────────┘

If power is lost during writing to B or A':
→ The new CRC does not exist → The old CRC is still valid → Return to the state of only A
→ Safe!
```

**Mode 2: Compaction, the block is full but there are no expired entries**

When the active block is full, LittleFS needs to copy the still valid entries to the spare block (which becomes a clean blank area after erasing). The old active blocks are not erased immediately, but are kept as spares and will be erased during the next compaction. This process is called compaction.

```
Power loss safety in Compaction
=========================================

commit B', need to compact:
┌───────────────┬─────────────┐ ┌──────────────┬───────────────┐
│ rev=1 │ rev=0 │ │ rev=1 │ rev=2 │
│───────────────│ │ │──────────────│──────────────│
│ A │ │ │ A │ A' │
│───────────────│ │ │──────────────│──────────────│
│ CRC(ok) │ │ │ CRC(ok) │ B' │
│───────────────│ │ │──────────────│──────────────│
│ B │ │ ==> │ B │ CRC(ok) │
│──────────────│ │ │──────────────│ │
│ A' │ │ │ A' │ │
│──────────────│ │ │──────────────│ │
│ CRC(ok) │ │ │ CRC(ok) │ │
└───────────────┴──────────────┘ └──────────────┴───────────────┘

If power is lost during compaction:
→ The new CRC of pair[1] has not been written yet → The old CRC of pair[0] is still valid
→ Return to the state before compaction
→ Safe!
```

At the code level, `lfs_dir_compact` (lfs.c:1952) accurately implements this process:

```c
// lfs.c:1952-2064 — The core process of lfs_dir_compact (simplified version)
static int lfs_dir_compact(lfs_t *lfs,
        lfs_mdir_t *dir, const struct lfs_mattr *attrs, int attrcount,
        lfs_mdir_t *source, uint16_t begin, uint16_t end) {

    dir->rev += 1;  // Increment revision

    while (true) {
        // 1. Initialize the commit state, the target is pair[1] (spare block)
        struct lfs_commit commit = {
            .block = dir->pair[1],
            .off = 0,
            .crc = 0xffffffff,
        };

        // 2. Erase spare blocks
        int err = lfs_bd_erase(lfs, dir->pair[1]);
        if (err) {
            if (err == LFS_ERR_CORRUPT) goto relocate;
            return err;
        }

        // 3. Write a new revision
        err = lfs_dir_commitprog(lfs, &commit,
                &dir->rev, sizeof(dir->rev));

        // 4. Traverse the old data and copy the entries that are still valid
        err = lfs_dir_traverse(lfs, source, 0, 0xffffffff,
                attrs, attrcount,
                LFS_MKTAG(0x400, 0x3ff, 0),
                LFS_MKTAG(LFS_TYPE_NAME, 0, 0),
                begin, end, -begin,
                lfs_dir_commit_commit, &commit_data);

        // 5. If there is a tail, write the tail pointer
        if (!lfs_pair_isnull(dir->tail)) {
            err = lfs_dir_commitattr(lfs, &commit,
                    LFS_MKTAG(LFS_TYPE_TAIL + dir->split, 0x3ff, 8),
                    dir->tail);
        }

        // 6. Write the delta of global state
        // ...

        // 7. Write the CRC (this is the key to atomicity!)
        err = lfs_dir_commitcrc(lfs, &commit);
        if (err) {
            if (err == LFS_ERR_CORRUPT) goto relocate;
            return err;
        }

        // 8. CRC written successfully → flip pair, old active block downgraded to standby block
        dir->erased = false;
        lfs_pair_swap(dir->pair);  // pair[0] ↔ pair[1]
        dir->off = commit.off;
        dir->etag = commit.ptag;
        return 0;

    relocate:
        // Bad block processing: try to replace pair[1] with a new block
        lfs_cache_drop(lfs, &lfs->pcache);
        lfs_block_t bad = dir->pair[1];
        int err = lfs_alloc(lfs, &dir->pair[1]);
        if (err) return err;
        // Mark bad blocks as "used" to prevent subsequent allocations
        // Enter the next cycle and try again
    }
}
```

**Mode 3: Split, the block is full and cannot be compacted**

If the block is full, but after traversal it is found that there are no expired entries that can be cleaned (all entries are active), this means that the amount of metadata in this directory needs to exceed the capacity of one block. At this time, LittleFS's approach is to split the metadata pair into two and connect them using a linked list.

```
Split: A metadata pair is divided into two
=========================================

commit C and D, need to split:
┌───────────────┬─────────────┐ ┌──────────────┬───────────────┐
│ rev=1 │ rev=2 │ │ rev=3 │ rev=2 │
│─────────────────────────────│ │──────────────│───────────────│
│ A │ A' │ │ A' │ A' │
│─────────────────────────────│ │──────────────│───────────────│
│ CRC(ok) │ B' │ │ B' │ B' │
│─────────────────────────────│ │──────────────│───────────────│
│ B │ CRC(ok) │ ==> │ tail ───┐ │
│───────────────│ │ │──────────────│──────────────│
│ A' │ │ │ CRC(ok) │ │
│──────────────│ │ │──────────────│ │
│ CRC(ok) │ │ │ │ │
└───────────────┴──────────────┘ └────────┬─────┴───────────────┘
                                             │
                               ┌─────────────┘
                               v
                      ┌──────────────┬──────────────┐
                      │ rev=1 │ rev=0 │
                      │──────────────│ │
                      │ C │ │
                      │──────────────│ │
                      │ D │ │
                      │──────────────│ │
                      │ CRC(ok) │ │
                      └──────────────┴───────────────┘
```

Note the two-step atomicity of the split process:1. **Prepare a new metadata pair** first, allocate two new blocks, write half of the entries, and write CRC.
2. **Insert the tail pointer** into the original metadata pair to point to the newly allocated pair. This step itself is an atomic directory commit (append mode).

If the power is off after step 1 and before step 2: the old directory state is retained, and the new metadata pair is not referenced by the parent directory. It is not inserted into the directory tree by orphan recovery, but becomes an unreachable residue and is later reclaimed by free space management.

**This is the "linked list of bounded logs". Each metadata pair is bounded (can accommodate up to about half a block of valid data), but can be infinitely expanded through the linked list. ** This ensures that the directory can contain any number of files, while the time complexity of each operation is still O(1).

## 50% split threshold - why not split at 100%?

There is a confusing point here: LittleFS's **compact trigger condition** is not 50%. The real triggering condition for compact is that the **block is full** (there is no space to accommodate the next commit) or **block_cycles expires** and forced relocation. 50% is the split decision threshold during compaction.

When compaction occurs, LittleFS checks the proportion of valid data (static entries) in the current metadata pair:
- If valid data ≤ 50% → compact in place, no splitting
- If valid data > 50% → split into two metadata pairs and concatenate using tail pointer

Why 50%? Mathematically:

Assume that each entry is 100 bytes and a block is 4KB (4096 bytes):

- When valid data accounts for 25%, each compact cost ≈ 1.3n
- When valid data accounts for 50%, each compact cost ≈ 2n
- When valid data accounts for 75%, each compact cost ≈ 4n
- When valid data accounts for 90%, cost ≈ 10n

The cost curve is exponential. In DESIGN.md, the author of LittleFS used amortized analysis to prove: **Split at 50% can limit the amortized cost of compact to within 2x, ensuring O(1) operation complexity. **

So what LittleFS does is: don't care about it at ordinary times, only compact when the block is full. If more than half of the valid entries are found during compaction, it will be split. "50%" is a judgment condition, not a trigger condition.

## Comparison with SB Log of KnotFS

If you've read Chapter 3 (The Design of KnotFS), you might find an interesting contrast here:

```
Metadata Pair vs KnotFS’s SB dual-slot design
=======================================================

Features LittleFS Metadata Pair KnotFS SB dual slot
──────────────────────────────────────────────────
Number of blocks 2 (pair[0] + pair[1]) SB: 2 blocks (SB0/SB1)
                                              The file table is embedded in the SB Header
Atomic commit append+compact+split append+compact (write to spare slot)
Active identification Compare revision count Compare sequence number
Compact triggers the block to be full or the block_cycles Log area reaches 50% capacity.
Split threshold Split when valid data exceeds 50% No split (fixed 8 file slots)
Split mechanism Yes (tail pointer linked list) No (file table fixed at 8 slots)
CRC protection: one CRC for each commit and one CRC for each log record
──────────────────────────────────────────────────
```

The core ideas of the two designs are similar, both are "two blocks alternation + sequence number arbitration + log append". But the difference in details reflects the different design goals of the two:

- **KnotFS is "aware of the upper limit":** There are up to 8 files and up to 8 block files, so the size of the superblock (including the file table) is fixed. Compact just writes the complete state in the memory to the spare SB slot, without splitting.
- **LittleFS is "unknown about the upper limit": ** The number of files, directory depth, and file size are not limited (except for the 2GB upper limit on file size). So it requires a tail linked list to support unbounded expansion of metadata pairs.

## revision counting and sequence number arithmeticMetadata pairs rely on revision counts to determine which block is "latest." But revision is a uint32_t, which will eventually overflow. If the revision flips from 0xFFFFFFFF to 0x00000000, a simple size comparison will go wrong.

LittleFS uses Sequence Number Arithmetic to solve this problem. The core idea is: What we compare is "how many times we need to add from A to B". This "distance" is not affected by overflow in two's complement.

It’s more intuitive to understand with code:

```c
// Determine whether rev_a is newer than rev_b
// Instead of simply a > b, check the clockwise distance
bool is_newer(uint32_t rev_a, uint32_t rev_b) {
    return (int32_t)(rev_a - rev_b) > 0;
}
```

Why is this okay? Because the addition and subtraction of uint32_t is itself an operation modulo 2³² in the computer. `(int32_t)(a - b) > 0` is equivalent to "the distance from b to a clockwise is less than 2³¹", which is exactly the condition we need for "a is newer than b".

**The prerequisite is that you will not perform more than 2³¹ compactions in a row without checking the revision. Within the physical life of Flash (100,000 erase times × two blocks = 200,000 times), this condition will always be met. **

## lfs_dir_commit: The full path of a commit

Let’s look at the complete call chain of directory submission from the top level:

```c
// lfs.c:2601 — Top-level logic of lfs_dir_commit
static int lfs_dir_commit(lfs_t *lfs, lfs_mdir_t *dir,
        const struct lfs_mattr *attrs, int attrcount) {

    // Step 1: Try to append
    int orphans = lfs_dir_orphaningcommit(lfs, dir, attrs, attrcount);

    // Step 2: If orphans are generated, clean up the orphans
    if (orphans) {
        int err = lfs_fs_deorphan(lfs, false);
        if (err) return err;
    }

    return 0;
}
```

`lfs_dir_orphaningcommit` internally calls `lfs_dir_relocatingcommit`, which calls `lfs_dir_splittingcompact`:

```
lfs_dir_commit
  └─ lfs_dir_orphaningcommit ← Handle orphan logic
       └─ lfs_dir_relocatingcommit ← If you need to relocate the block
            └─ lfs_dir_splittingcompact ← Processing compaction/split
                 ├─ Try to append (if there is space in the current block)
                 ├─ Try compact (if the current block is full)
                 └─ Try split (if it still exceeds 50% after compacting)
```

This call chain demonstrates the comprehensiveness of the metadata pair design: **No matter what the current state is, there is always a path that allows the commit to succeed, or to trigger more advanced processing due to insufficient space. **

## Final verification of power-down guarantee

Let's do a thought experiment. You unplug a metadata pair while it is in any state. Possible situations:

**Case 1: The entry is being added, but the addition is not completed. **
→ The old CRC is still valid → Read the old CRC when mounting → Ignore the incomplete tail → Return to the state before appending.

**Case 2: Compacting, old data has been copied to pair[1], but CRC has not been written. **
→ pair[1] does not have a valid CRC → the old CRC of pair[0] is still valid → returns to the pre-compact state.

**Case 3: Compacting, CRC has been written, but the pair has not been swapped yet. **
→ pair[1] has a new valid CRC → pair[0] has an old valid CRC → compare revisions → find the revision update of pair[1] → use pair[1] as the data source → compact completed!

**Case 4: Split is in progress, the new pair is prepared, but the tail pointer is not written in the original pair. **
→ Two pairs exist independently → The new pair is not linked to the parent directory → The old state is retained and the new pair is recycled later.

**In all possible states, the file system either returns to the previous consistent state or advances to the next consistent state. There is no intermediate state of "partial writing". **

This is the specific implementation of LittleFS's **Strong Guarantee** at the metadata pair level.KnotFS's double SB slots (SB0/SB1) draw on the idea of ​​double block alternation of Metadata Pair. SB Log appends to active slots, Compact covers inactive slots, and sequence parity determines who is the current valid copy. But the key difference is: LittleFS's Metadata Pair stores directory entries (as many as you want), which can be dynamically split into tail chains; KnotFS's SB stores file tables (fixed 8 slots), and Compact is an overall rewrite, which is simpler, but also more "Flash-consuming". This is the complexity that the teaching version deliberately cuts off: when you only need to manage 8 files, there is no need for a metadata pair generic framework.
