# 3.8 Power-Loss Safety: Rebuilding Order in the Dark

## Your hand is hanging in the air, and the light suddenly goes out.

Imagine a scene: you are copying an important document with a brush. The ink is full and the rice paper is smooth. You have reached the seventh character on the third line, which is the last character of the word "zhou". The moment the pen tip touched the paper, the whole room fell into darkness. The candle went out.

You can't see anything. You don't know whether the word "zhou" has been finished. You don’t know if the pen tip has scratched the rice paper. You don't know whether the ink on the brush is a drop or a half drop.

**You just know: In that moment in the dark, some things may be complete and some things may not be complete. **

This is the situation when the Flash file system faces a power outage.

For disks, power outage is usually a secondary disaster. After the computer is restarted, the file system does a `fsck` check, scans the inode linked list, and repairs some inconsistent reference counts, and it can usually be restored. Because the disk is written in place, it is either finished or not written. The unwritten data is old (has not been overwritten), and the file system can always find a state.

For Flash, power loss is more dangerous because Flash write operations are not atomic. **A 4KB erase takes 200 milliseconds and a 4KB program takes 58 milliseconds. ** In any microsecond without power, the status of this block may be "work in progress".

---

## The semi-finished state of Flash erasure: how many ways can a block die?

Let’s look at erasure first. It takes about 200 milliseconds to erase a sector of NOR Flash. During these 200 milliseconds, the high-voltage generator inside the Flash is running, and the electrons in the floating gate are returning to the substrate through the oxide layer.

```
Internal timeline of erase operations (NOR Flash 4KB sectors)
=======================

t=0ms: Erase command (0x20) + address received
          Inside Flash: Start the high-voltage pump, and the voltage rises from 0V to ~20V
          On SPI: BUSY=1

t=50ms: High voltage is stable at ~20V
          Electrons in the floating gate begin tunneling back to the substrate
          Each unit is slowly changing from "0" back to "1"
          
t=100ms: About 50% of the cells have been erased (indicative, does not represent a linear erasure curve)
          
t=150ms: ← Power off! !
         ┌────────────────────────────
         │The status of this sector at this time:
         │ Some cells have been erased (identifiable as "1") → 0xFF
         │ Some cells are not erased (still "0") → 0x00 or other values
         │ Some units are in the fuzzy range of threshold voltage → The reading result is uncertain!
         │ Overall: Not all 0xFF, not all 0x00
         │ It’s a mess
         │ And: when the threshold voltage is at the edge of the read window,
         │ Temperature/voltage changes may cause different readings
         └─────────────────────────────

t=200ms: Normal completion
          All cell threshold voltage drops to erase state
          Read back all 0xFF
```

**When the power is turned off at the 150th millisecond, the content of this 4KB sector is invalid, unpredictable, and may even be different every time it is read. **

Let’s look at programming again. Programming one byte of NOR Flash takes about 14 microseconds. Full page programming of a 4KB sector takes 58 milliseconds:

```
Internal timeline of programming operations
=======================

t=0ms: Receive programming command (0x02) + address + data
          Flash internal: start programming high voltage
          On SPI: BUSY=1

t=10ms: first ~700 bytes programmed
          
t=29ms: ← Power off! !
         ┌────────────────────────────
         │The status of this sector at this time:
         │ offset 0~2047: programmed (indicated by linear progress)
         │ offset 2048~4095: not programmed → may still be old data, or partially disturbed
         │ Overall: The first half is new data, the second half is old data/garbled code
         │ Similar to "A file is cut in half"
         └─────────────────────────────

t=58ms: Normal completion
          All 4096 bytes have been programmed
```

**The Flash block after power-off can be in at least four states: complete erase, partial erase, partial programming, and complete programming. **

And, the scariest thing is, you don't know what state it is. ** After power cycle, the data you read back may be anything. The CRC check may or may not pass. You cannot trust a CRC passing result, because the garbled data in the "partially erased" state may happen to match the CRC (the probability is 1/2³² ≈ 2.3×10⁻¹⁰, which is extremely small but not zero).

## Four weapons: How to arm a power-down safe file system

The file system has four classic weapons to fight against power outages. KnotFS uses them all.

**Weapon 1: Copy-on-Write (copy-on-write), old blocks remain intact before being erased by GC**

```
Copy-on-Write power-down protection
=======================

The process of modifying the file "config.txt" (CoW mode):

Step 0: Old data is on block 5.
  ┌──────────────────────────┐
  │ Block 5: [header│data: v1.0] │ ← Old, complete data
  └──────────────────────────┘

Step 1: find_free_block() → allocate block 18 (new, erased block)
  ┌──────────────────────────┐
  │ Block 18: [blank all 0xFF] │ ← Newly erased block
  └──────────────────────────┘

Step 2: Read old data into memory → modify → write to block 18
  ┌──────────────────────────┐
  │ Block 18:[header│data: v2.0] │ ← New data
  └──────────────────────────┘
  ← If there is a power outage here:
     Block 5 (old data): Complete!
     Block 18 (new data): may be partially written
     → After filesystem mount, select block 5 as valid version
     → Block 18 is garbage → Marked as invalid, waiting for GC

Step 3: Update the file table: config.txt from pointing to block 5 → pointing to block 18
  ┌──────────────────┐
  │ File table: config.txt │ ← Update pointer
  │ → Block 18 │ If power fails here: see "Double Slot Compact"
  └──────────────────┘

Step 4: Mark block 5 as garbage (free_bitmap[5] = 0)
  ← Block 5 awaits garbage collection (GC) erasure
```

The core philosophy of CoW is: **The old version is always intact until the result of the modification is "switched" into effect. ** When there is a power outage, you only need to abandon the incomplete new version and fall back to the complete old version.

It's like when you write a paper: you never revise directly on the original manuscript, you save a copy `paper_v2.docx` and revise on the copy. The computer has a blue screen after changing it? It doesn't matter, `paper_v1.docx` is still there.

**Weapon 2: Two-slot Compact, only one slot has been modified**

```
Dual Slot Compact
=======================

    Block 0 (current active SB) Block 1 (standby SB slot)
  ┌──────────────────┐ ┌──────────────────┐
  │ SB Header │ │(currently an old version) │
  │ nodes[8] file table │ │ │
  │ SB Log [rec1..N] │ │ │
  └──────────────────┘ └──────────────────┘
            │
            │ Compact trigger
            ↓
  ┌──────────────────┐ ┌──────────────────┐
  │(reserved, unchanged) │ │1. Erase block 1 │
  │ │ │2. Write new SB Header │
  │ │ │ + nodes[8] │
  │ │ │ + Cleared log area │
  │ │ │3. seq++ │
  └──────────────────┘ └──────────────────┘
            │ │
            │ │ Writing completed, CRC passed
            ↓ ↓
        Change to "Old Version" Change to "Current Active SB"

If the Compact loses power midway:
  → New SB on block 1 is incomplete (CRC failed or seq not big enough)
  → Read two SBs when mounting, choose the one that passes the CRC and has a larger seq
  → The old SB of block 0 is still intact → Restored to the pre-Compact state
  → The semi-finished product on block 1 is recognized as invalid and will be overwritten by subsequent Compact
```

The key to Compact is: **compact only erases and writes "the slot that is not currently in use". ** Active slots are not erased during compact; but daily metadata/Log paths may write to them. Compact always erases and writes to the spare slot, switching the "active" pointer after writing. If the power is interrupted during the writing process to the spare slot, the writing is not completed or the CRC is incorrect, the original active SB will remain unscathed. After restarting, read two SBs and choose the one with a passed CRC and a larger sequence, which is equivalent to automatically returning to the state before Compact.**Weapon 3: Log Replay, start over from the last complete record**

> Note: The following Log Replay and orphan cleaning are design deductions. The current KnotFS teaching implementation leaves the Log in memory/not truly persisted, and does not have independent GC or orphan cleaning; actual persistence relies on compact rewriting the SB header.

```
Log Replay
======================

When remounting, KnotFS performs the following process:

Step 1: Read SB0 and SB1, select the one with passed CRC and larger sequence_number (valid SB)
  ┌─ SB0: seq=142, CRC=OK, valid=true
  │ SB1: seq=96, CRC=OK, valid=true
  └─ → Use SB0

Step 2: Scan the Log area forward from the SB Header
  ┌─────────────────────────────┐
  │ Record N: seq=142 (mount) │ ← The last complete record
  │ Record N-1: seq=141 (write) │ ← Valid
  │ Record N-2: seq=140 (write) │ ← Valid
  │ Record N-3: seq=139 (.......) │ ← CRC error! Power outages can happen here
  │ ... │
  └─────────────────────────────┘

Step 3: Find the last record that passed CRC verification → seq=142
  Scan forward for all valid records → replay their cumulative impact on the file system state
  Get the latest logical status of the file system:
    - which files exist
    - What is the starting block of each file
    - The status of the idle bitmap
    - Wear count

Step 4: Consistency fix (if needed)
  Scan data area:
    - Only scan the data area, excluding SB0/SB1 and log blocks
    - Mark them as invalid/dirty first; return to the free pool after erasure is complete
    - The current teaching implementation does not have an independent GC
```

The essence of log playback is: **Find the last complete "safety line" in the log, take credit from the state after that, and discard any previous semi-finished operations. **

**Weapon 4: Consistency Repair, clear debris**

```
Consistency fixes
======================

Scenario: Power loss occurs when new data blocks have been written but Compact has not yet completed
  At this time: the new data block is on Flash, free_map shows it as used,
        But the file table (nodes[]) still points to the old data block

Repair steps:
  1. Select the latest valid SB when mounting → read the file table (nodes[]) and free_map
  
  2. Play back all valid records from SB Log → Rebuild the running status of free_map
  
  3. Traverse all data blocks:
     a. free_map mark the block as used → check if there is a file entry referencing it
        With reference → normal, reserved
        No reference → Orphan block (data block is written but Compact is not completed)
     b. First mark the orphan block as invalid/dirty; after the erasure is completed, return to the free pool.
  
  4. These residual blocks must be erased before they can be reallocated; NOR cannot be directly overwritten.

  "Orphan cleaning" of physical blocks (design diagram):
  Only the data area is scanned, SB and log blocks are verified separately according to their respective structures.
    For each block:
      If there is data in the block (not all 0xFF):
        Check if there is an FT entry pointing to it
        If there is no → orphan block → mark as garbage (free_bitmap corresponding bit = 0)
        Waiting for GC wipe
```

Consistency repair is the last line of defense for power outage safety. When neither Compact nor log replay can be restored perfectly, it at least ensures that the file system will not be "half-dead". It will sweep all inconsistent fragments into the garbage heap, leaving a self-consistent state.

## Vulnerable window analysis: When is the most dangerous time for power outage?

Let us analyze the "vulnerable windows" of each operation of KnotFS one by one, that is, what are the consequences of power failure during the operation.

```
Vulnerable window analysis of KnotFS operations
=======================

1. Write files (complete CoW process)
  ┌────────────────────────────────────┐
  │ Operation steps │ Consequences of power failure │
  ├─────────────────────────────────────┤
  │ 1. find_free_block() → allocate block 18 │ block 18 free_bitmap=1 │
  │ If power is lost: Block 18 is marked occupied │ But block 18 is empty │
  │ → Orphan cleaning during mount: Block 18 is empty → │ Released back to the free pool during mount │
  │ Release back to free pool (fixed after checking) │ │
  ├─────────────────────────────────────┤
  │ 2. Erase block 18 (if not erased yet) │ Block 18 in half-erased state │
  │ If there is a power outage: Block 18 may be garbled │ The CRC will definitely not pass │
  │ → When mounting: mark as invalid, re-erase │ Re-erase when mounting │
  ├─────────────────────────────────────┤
  │ 3. Program block 18 (write new data) │ Block 18 in half-programmed state │
  │ If power outage: part new data + part garbage │ Block 5 (old data) complete │
  │ → FT still points to block 5 (old data) │ → Fallback to old data │
  ├─────────────────────────────────────┤
  │ 4. SB Log adds records │ SB Log has half a record │
  │ If power fails: SB Log tail is damaged │ Dual copy: old SB is intact │
  │ → Select another valid SB when mounting │ → Fall back to the old state │
  ├─────────────────────────────────────┤
  │ 5. Compact to the spare SB slot │ The new SB has not been written yet │
  │ If power is lost: │ Old SB is still intact │
  │ → Select the SB that passes the CRC when mounting │ → Automatic rollback │
  ├─────────────────────────────────────┤
  │ 6. Mark old block 5 as garbage │ Block 5 is not marked as garbage │
  │ (free_map[5]=0→SB Log appends records) │ Both block 5 and block 18 are valid │
  │ If power failure: SB Log record is not committed │ → Both have data │
  │ → Play back SB Log during mount │ The file table points to the new block 18 │
  │ Find orphan blocks: Block 5 is not referenced by the file table │ Block 5 is a "redundant backup" │
  │ → Mark as free │ → Next GC collection │
  └────────────────────────────────────┘

Conclusion: In the design deduction, complete CoW + dual-slot Compact + Log Replay + orphan cleaning can form multi-layer protection; the current teaching implementation has not yet been fully realized.
     If power is lost at any time during file writing operations, the worst consequences are:
     - Lost the latest update (data rolls back to the last completed state)
     - Generate an orphan block (recycled by the next GC)
     There will be no: file corruption, file system crash, data loss.
```

These four weapons together constitute the file system's "power-down immunity system."

## Power-down test: Certification of the brave

A brownout safety analysis on paper is one thing. Real-world power-down testing is another story.

In engineering practice, the method of power-off testing is: **Insert random power-off points on the critical path of file operations, repeat thousands of times, and verify that each time it can be successfully restored. **

```
Pseudocode for power-off test
=======================

for test_round in 1..10000:
    // 1. Prepare initial state
    format()
    write("config.txt", data_1KB)
    
    // 2. Select a power outage point
    power_loss_point = random_from([
        "during_erase",
        "during_program", 
        "during_sb_log_write",
        "during_compact",
        "during_free_map_update",
        "during_gc_compact"
    ])
    
    // 3. Insert a breakpoint in the code at the power-off point
    inject_power_loss_at(power_loss_point)
    
    // 4. Start a file write operation
    async_write("config.txt", data_modified)  // Will trigger a series of state machine transitions
    
    // 5. Cut off power at the point of power failure (software simulation = forced abort of operation)
    simulate_power_loss()
    
    // 6. "Power on again" → mount file system
    mount()
    
    // 7. Verify file system consistency
    assert(file_system_is_consistent())
    assert(all_metadata_crc_valid())
    
    // 8. Check the data
    //    config.txt is either the old data_1KB (modifications lost)
    //    Either new data_modified (modified successfully)
    //    Never allowed: half-old, half-new, garbled, files that do not exist
    content = read("config.txt")
    assert(content == data_1KB || content == data_modified)
```

## “Library” Metaphor: Blackout Protection

Japan is a country prone to earthquakes. Japanese library designers have a complete set of power outage defense strategies when planning libraries:

```
Power outage protection → Power outage safety
=======================

Flexible structure (allows the bookshelf to sway but not collapse):
  → Copy-on-Write (allows operation failure without losing old data)
  
Redundant support (multiple rows of bookshelves support each other, and one row will not fall down when it falls):
  → Dual-slot Compact (SB is written to the spare slot, and the old slot is intact)
  
Post-power outage inspection (quickly assess damage and reinforce hazardous areas after a power outage):
  → Log playback + consistency repair (scan and rebuild consistency during mount)
  
Backup power supply (isolate core directory cabinet from main circuit):
  →Double copy SB (bad one and another one)
```

**Managing a library in an earthquake zone, you cannot guarantee that the library will survive an earthquake unscathed. You can only guarantee that after the earthquake, the library can still operate and the books inside are safe. **

The same is true for the power-down safety of Flash file systems. You cannot guarantee that every operation will not be interrupted by a power outage. Power outages are random and may occur at any time. All you can guarantee is that after a power outage, the file system can be restored to a self-consistent state and user data will not be lost. **

## Why Flash power outage is more terrifying than disk

Final review: Why is the engineering challenge of Flash power failure much greater than that of disks?

```
Flash vs disk power-down comparison
=======================

                         Disk HDD NOR Flash
───────────────────────────────────────────────────
The most hungry operations: Sector Write (~5ms) Sector Erase (~200ms)
                         Cover in situ, erase first and then write
The state when powering off is either finished writing or not writing, possibly half-erased (garbled characters).
                         Old data is still in place Old data may have been corrupted
Repair mechanism fsck (scan inode) 4 heavy weapons (CoW+Compact+Log+Consistency)
Difficulty of data recovery Simple Complex
Severity of risk of loss Usually only the last few sectors are lost Metadata may be corrupt → the entire volume is unusable
Recoverability High High (through engineering means)
```

Flash power outage is more difficult to deal with, but it is not impossible to deal with. KnotFS's four-layer defense proves an argument: **As long as sufficient "prediction of power-off points + design of rollback paths" is done in the project, the Flash file system can achieve the same or even higher power-off reliability as the disk file system. **

Because in-place overwriting of the disk means: if your old data is half covered by new data when writing, you can't go back. Flash's off-site update (Copy-on-Write) naturally gives you an "old version" as long as you don't erase it at the correct time.
