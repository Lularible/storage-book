# 5.3 Fooling the File System with RAM: The Flash Array and Asynchronous Delay Simulation

## The file system thinks it is operating Flash

Let's play a mind game.

You are a piece of C code. You think you are operating NOR Flash. In a function called `fdev_write`, you "write" a 4KB data block into the 7th block of Flash. After you finish this, you have to wait for 2 "hardware ticks" to know whether the write operation was successful.

But in fact, you are just doing `memcpy` into an array of `uint8_t`.

```c
// knotfs.c — The entire Flash is an array
static uint8_t flash[KNOTFS_BLOCK_COUNT * KNOTFS_BLOCK_SIZE];
```

This line of code is the foundation of the entire KnotFS physical layer. 16 × 4096 = 65536 bytes static array. All "Flash operations", including reading, writing, and erasing, finally fall on this memory.

This is the core of the KnotFS teaching philosophy: **replacing physical media with a controllable simulation layer, allowing learners to observe the internal behavior of the file system on any computer. ** You don't need a development board, a JTAG line, or a Flash chip. All you need is GCC and a terminal.

---

## fdev: Software emulation of Flash devices

`fdev` (flash device) is a global state structure, and only one operation can be in flight at a time:

```c
// knotfs.c — Flash emulator status
static struct {
  fop_t op;
  uint32_t blk_idx;
  uint32_t blk_off;
  void *buf;
  uint32_t size;
  int ticks_left;
  int result;
} fdev;
```

The `op` field has four values:

```c
// knotfs.c — Operation types
typedef enum { FOP_NONE, FOP_RD, FOP_WR, FOP_ER } fop_t;
```

When `op == FOP_NONE`, it means "the flash memory is free and can accept the next operation". This is a key signal of asynchronous architecture: the file system cannot submit new operations while the operation is in progress.

But there's a key simplification here: **KnotFS's fdev can only accept one operation at a time. ** There is no operation queue, no DMA linked list, and no interrupt priority. Each call to `fdev_read`/`fdev_write`/`fdev_erase` will directly overwrite the contents of the `fdev` structure:

```c
// knotfs.c — three initiating functions: directly overwriting fdev
static void fdev_read(uint32_t blk, void *dst, uint32_t sz) {
  fdev.op = FOP_RD;
  fdev.blk_idx = blk;
  fdev.blk_off = 0;
  fdev.buf = dst;
  fdev.size = sz;
  fdev.ticks_left = FDEV_TICK_RD;
}

static void fdev_write(uint32_t blk, const void *src, uint32_t off,
                       uint32_t sz) {
  fdev.op = FOP_WR;
  fdev.blk_idx = blk;
  fdev.blk_off = off;
  fdev.buf = (void *)src;
  fdev.size = sz;
  fdev.ticks_left = FDEV_TICK_WR;
}

static void fdev_erase(uint32_t blk) {
  fdev.op = FOP_ER;
  fdev.blk_idx = blk;
  fdev.ticks_left = FDEV_TICK_ER;
}
```

Note the latency constants: read = 1 tick, write = 2 ticks, erase = 3 ticks.

---

## Why 1, 2, 3?

This is not an arbitrary choice. On real NOR Flash:
- Reading one block (4KB): ~0.5-2ms (depends on SPI clock frequency and interface mode)
- Writing one page (256 bytes): about 50-100 microseconds, about 10 milliseconds to write 4KB (16 pages)
- Erase one block (4KB): about 50-150 ms

Erase is about 5-15 times slower than writing, and writing is about 5-20 times slower than reading. This is a gap of two orders of magnitude.

KnotFS intentionally preserves this asymmetry: erase is slowest (3 ticks), writes are medium (2 ticks), and reads are fastest (1 tick). Although the specific ratio has been greatly scaled (otherwise you would have to wait hundreds of ticks for erasing to complete), the relative relationship of "erasing is slower than writing, and writing is slower than reading" is retained. This allows readers to intuitively feel at runtime: formatting (requiring 16 blocks to be erased) is indeed much slower than mounting (requiring only 2 blocks to be read).

Observe the output of `./knotfs_test`:

```
[format]     tick 15...
    tick 30...
    tick 45...
    tick 60...
    tick 69... done
OK
  [mount]     tick 4... done
OK
```

format requires erasing 16 blocks (16 × 3 = 48 ticks) + writing 2 SBs (2 × 2 = 4 ticks) + compacting and other state machine scheduling overheads. The actual measurement time is about 69 ticks. Mount only needs to read 2 SB blocks for checksum selection (2 × 1 = 2 ticks) + CRC calculation and SB selection logic overhead, which is about 4 ticks in actual measurement.

This gap allows you to intuitively feel: **Erase is the slowest operation on Flash. ** Formatting is "slow" (69 ticks) because it is erasing all blocks; mounting is "fast" (4 ticks) because it only requires reading.The absolute time of each tick is controlled by the `TICK_NS` constant in `knotfs.c` (currently 80ms). According to this calculation: erasing a block ≈ 240ms, writing a block ≈ 160ms, and reading a block ≈ 80ms. Formatting 16 blocks takes about 69 × 80ms ≈ 5.5s, which is basically the same magnitude as a real NOR Flash automotive chip. Adjusting `TICK_NS` can make the demo run faster or slower.

## fdev_tick: The heart of asynchronous

The core of the entire asynchronous simulation is `fdev_tick()`. It is called every time the event loop is entered:

```c
// knotfs.c — Decrement the counter every tick and perform the operation when it reaches zero
static void fdev_tick(void) {
  if (fdev.op == FOP_NONE)
    return;
  {
    struct timespec ts = {0, TICK_NS};
    nanosleep(&ts, NULL);
  }
  if (--fdev.ticks_left > 0)
    return;
  uint32_t base = fdev.blk_idx * KNOTFS_BLOCK_SIZE + fdev.blk_off;
  fdev.result = 0;
  switch (fdev.op) {
  case FOP_RD:
    memcpy(fdev.buf, &flash[base], fdev.size);
    break;
  case FOP_WR:
    memcpy(&flash[base], fdev.buf, fdev.size);
    break;
  case FOP_ER:
    memset(&flash[base], 0xFF, KNOTFS_BLOCK_SIZE);
    break;
  default:
    break;
  }
  fdev.op = FOP_NONE;
}
```

This function looks ridiculously simple, it is just a memcpy/memset with a countdown. But it accomplishes two core teaching purposes:

**1. Timing decoupling. ** Calling `fdev_erase(7)` will not immediately change block 7 to 0xFF. It just sets `fdev.op = FOP_ER` and `fdev.ticks_left = 3`. The real erasure occurs after 3 `knotfs_run()` calls. This simulates the behavior of real hardware: after the CPU sends the erase command to the Flash controller, the Flash controller takes its own time to complete it, and the CPU can do other things.

**2. Status is visible. ** Because the operation is not instantaneous, the state machine must "wait". While waiting, `fdev_idle()` returns false and the caller (the file system) cannot submit new operations. This forces upper-level code to break long processes into multiple states, which is the motivation behind the design of asynchronous state machines in production-grade versions.

The implementation of `fdev_idle()` only requires one line:

```c
// knotfs.c
static bool fdev_idle(void) { return fdev.op == FOP_NONE; }
```

In the event loop, this condition is checked repeatedly:

```c
// knotfs.c — Waiting for Flash to become idle in the event loop
if (!fdev_idle())
  return true;
```

If Flash is busy, the event loop directly `return true`, waiting for the next tick before coming in. This is the essence of cooperative multitasking: let the task itself say "I'm not finished yet, you can ask me again next time" instead of using preemptive thread switching to "suspend" a task.

## Current bottleneck: only one operation can be performed at a time

KnotFS's fdev has an obvious limitation: only one operation can be in progress at the same time. This means that you cannot read the data in block 3 while waiting for block 7 to be erased. The entire file system is serialized.

This is intentional. In production-level scenarios, the DiskAsync task can submit multiple operations at once through a DMA linked list. However, since the teaching purpose is to allow readers to see the state transitions of each step clearly, rather than to demonstrate the advanced usage of the DMA controller, KnotFS chose the simplest single-operation model.

If you're thinking "this is slow", you're right. But don’t forget what this “slow” is relative to. Without KnotFS, you have to either read the ext4 source code of the Linux kernel (about 50,000 lines), or read the integrated code of FreeRTOS+FAT (mixing file system logic and operating system calls together), or go directly to the production-level solution (10,000 lines of AUTOSAR code). Among these, KnotFS's "slowness", which allows you to single-step debug the entire write process line by line, is the fastest learning path.

## A real bug: stack variable trap of compact_buf

There is a bug worth mentioning during the development of KnotFS, which perfectly demonstrates the most common pitfall in asynchronous programming: ** Passing the address of a local variable to an asynchronous operation. **

The earliest version of `compact_write` is probably like this:

```c
/* Buggy version (don’t do this) */
static void compact_write(void) {
  knot_sb_t sb_copy;
  memcpy(&sb_copy, &sb, sizeof(knot_sb_t));
  sb_copy.sequence = sb.sequence + 1;
  sb_copy.log_offset = SB_HEADER_SZ;
  sb_copy.log_count = 0;
  sb_copy.crc32 = sb_checksum(&sb_copy);

  fdev_write(inactive_sb_slot(), &sb_copy, 0, sizeof(sb_copy));
}
```

What's wrong with this version? `sb_copy` is a stack local variable. `fdev_write` recorded it in `fdev.buf`:

```c
static void fdev_write(uint32_t blk, const void *src, uint32_t off,
                       uint32_t sz) {
  fdev.op = FOP_WR;
  /* ... */
  fdev.buf = (void *)src;
  /* ... */
}
```

Then `compact_write` returns, and the stack frame where `sb_copy` is located is destroyed. After 2 ticks, `fdev_tick()` executes `memcpy(&flash[base], fdev.buf, fdev.size)`, but the stack memory pointed to by `fdev.buf` may have been overwritten by subsequent function calls.It's like handing a letter to the postman, but as soon as you turn around and close the door, a gust of wind blows the mailbox over your door. When the postman came back to pick up the mail, he found a pile of white paper that had been blown around by the wind.

Fix: Use a **static variable** to save the compact data:

```c
// knotfs.c — statically allocated compact buffer
static knot_sb_t compact_buf; /* persistent buffer for async compact writes */
```

Then `compact_write` becomes:

```c
// knotfs.c — fixed version
static void compact_write(void) {
  memcpy(&compact_buf, &sb, sizeof(knot_sb_t));
  compact_buf.sequence = sb.sequence + 1;
  compact_buf.log_offset = SB_HEADER_SZ;
  compact_buf.log_count = 0;
  compact_buf.crc32 = sb_checksum(&compact_buf);

  uint32_t tgt = inactive_sb_slot();
  fdev_write(tgt, &compact_buf, 0, sizeof(knot_sb_t));
}
```

This time, the life cycle of `compact_buf` is the life cycle of the entire program, and it will not be recycled until the program exits.

**This bug is the epitome of asynchronous programming. ** In synchronous programming, "call a function, and the data is no longer needed after the function returns" is the norm. In asynchronous programming, "the call initiates the operation and the operation is completed at some time in the future" means that your data must live until the moment the operation completes. `static` variables, heap memory allocated by malloc, and global buffers are all tools to solve the problem of "data life cycle spanning function calls".

There are several such static buffers in KnotFS:
```c
static uint8_t  tmp[KNOTFS_BLOCK_SIZE];   // knotfs.c — temporary buffer of data blocks
static knot_sb_t compact_buf;             // knotfs.c — compact write buffer
static knot_log_t log_buf[LOG_BUF_CAPACITY]; // knotfs.c — Log accumulation buffer
```

Each has the same reason: they need to remain valid across ticks and cannot be destroyed when a function returns.

---

> ⚠️ **Teaching Simplification Tip**: The delay of real Flash is millisecond level (erasure is about 100ms), and requires DMA+interrupt driver: after the CPU initiates the operation, the Flash controller autonomously completes the data transmission through the DMA bus, and notifies the CPU through an interrupt after completion. KnotFS simulates this with a simple counter `ticks_left`. Additionally, a real Flash controller can keep multiple commands in the queue at the same time (command pipelining), whereas KnotFS's fdev is strictly serial. The production-level solution will use the AUTOSAR FLS MCAL driver, which supports asynchronous job submission, interrupt callbacks, and cache consistency maintenance (`arch_clean_cache_range`/`arch_invalidate_cache_range`/`__DSB` barriers).
