## After KnotFS, how far is it?

You've finished writing KnotFS. 1165 lines of code, the entire skeleton of a complete file system: format, mount, write, read, append, delete, compact, power-loss recovery. All 18 checkpoints passed.

If this was the end, you could already close the book.

But you know in your heart: the operating environment of KnotFS is an ideal sandbox. There is no hidden danger of the data transferred by DMA becoming obsolete in the Cache, there is no anxiety about the watchdog countdown during 100ms Flash erasure, and there is no race condition of GC status between different threads during multi-tasking concurrency. These are intentional teaching simplifications of KnotFS, rather than limitations, just like the smooth plane and vacuum environment in physics textbooks.

There is a distance between KnotFS and a file system that can run stably on real hardware that cannot be fully expanded in textbooks. This distance is a problem that you must solve yourself on a specific platform, using a specific tool chain, and facing specific usage scenarios, rather than some mysterious high-level knowledge.

These questions are not taught in textbooks.

Specifically, from the teaching version to the deployable version, at least these gaps need to be faced:

| Teaching version available | Not available yet |
|-----------|----------|
| RAM simulation Flash | Real hardware abstraction and driver docking |
| Tick counter simulation delay | Asynchronous I/O and DMA interrupt driver |
| Single-threaded event loop | Multi-task isolation and priority scheduling |

This is a memo on what extra considerations are needed to survive in the real physical world, not a feature list. Behind each is infrastructure, not new algorithms: Cache coherence, watchdogs, DMA, interrupt priority, Flash partition planning.

## The last few kilometers that textbooks don’t teach

**The textbook does not teach Cache consistency debugging.** The design team’s textbook will talk about Cache mapping methods and replacement strategies. However, after DMA transfers data, the CPU still reads the old cache value. This bug cannot be stably reproduced and cannot be located with breakpoints. The only way to do this is to check whether the Cache operation is complete line by line during code review. All embedded engineers fear it.

**Textbooks do not teach what a 100ms erase time means for a multitasking system.** Operating system textbooks will talk about scheduling algorithms and priority inversion. But while your file system is waiting for a flash erase, the watchdog is counting down, and the terminal task still has keep-alives to reply to. 100ms is not a "slow operation", it is enough for the MCU to context switch hundreds of times. Your design must ensure that no other task is starved during these 100ms.

**The textbook does not teach the testing methodology for power failure safety.** Database textbooks will talk about ACID transactions and WAL log recovery. But when the system is running on a car that can stall at any time, you can't test for power loss at "any moment", you can only inject reset at a limited number of critical transition points. This is a limited verification, not a completeness proof, using limited test points to cover unlimited power-down moments.**Textbooks do not teach that convergence of wear leveling requires correct data, not a new algorithm.** This Wikhipuedia entry is no larger than three screens. But getting it right may require multiple rounds of iterations. What you need to ensure is that the update of the count covers all paths, that persistence is timely enough, and that appending logs does not block users, rather than improving the algorithm itself (the algorithm is correct).

The common characteristics of these challenges are: **They are infrastructure problems, not core logic problems.** The core logic is taught in textbooks. Infrastructure is a problem you solve yourself on a specific platform. The relationship between the two is complementary, not hierarchical.

## When is there no need for a file system at all?

If all you have is a hammer, everything looks like a nail. After reading this, you are holding the hammer of the file system in your hand. You may have an illusion: Since the file system is so good, why not give all the data to it?

Quite the opposite. The file system is a costly tool, and every one of its capabilities: name, directory, log, GC, wear leveling, is designed to deal with "uncertainty". If the data model itself is deterministic, these capabilities become pure overhead.

```
Uncertainties resolved by the file system:
  What's the name of the file?        → name list
  How big is the file?            → block mapping
  Will the file be overwritten?      → CoW/Log
  Will the data change frequently?    → Wear leveling
  Will the power be cut off at any time?        → Dual copy + log

If only you knew the answers to these questions from the beginning...
```

Assume that all you really want to manage are a few pieces of data: factory calibration parameters, serial numbers, and a fixed set of angle tables. They have a fixed number, fixed size, and fixed location, and are only written a few times a year or even only once when they leave the factory. At this time, a complete file system is like building a library for a sticky note.

A more direct approach is **fixed address direct writing**: define the data as a structure, write directly to the fixed address segment of Flash (directly erase before writing), and add CRC check. It is suitable for reconstructable, low-value data.

```
File system vs fixed address direct write
=============================

          File system fixed address direct write
Number of files: arbitrary (with a maximum value) fixed
File size: arbitrary (with a maximum value) fixed
name any string compile time constant
Power-off safety CoW+dual copy is not guaranteed (single copy+CRC can only detect errors)
Wear leveling Dynamic allocation None (writes are very low frequency, wear is negligible)
Code amount ~1165 lines of core, dozens of lines
RAM state machine + buffering is almost zero
```

There is only one judgment criterion: **Whether the shape of the data is certain.** If the number, size, name, and update frequency of files are unpredictable, a file system is the right answer; if they are written in compile-time constants from day one, then fixed-address direct writing is not only a simplification, but also the right engineering choice.

The value of KnotFS does not lie in "using it", but in letting you understand what a file system has undertaken and what it has paid for. When you truly understand these costs, you will know when to pick up the hammer and when to put the hammer down.

## The essence of storage: fighting entropy increase

Now, let's lift ourselves up from the engineering details and see what these five chapters are really about.

Chapter 1, Section 1, we tell about a Stone Age man who tied a knot in a hemp rope. He used the position of the knot to express "east", the size of the knot to express "cow", and the number of knots to express "quantity". He needs to agree on the symbol system (encoding rules), needs the rope to not rot (durability), and needs to know which node to start interpreting from (retrieval).

Twenty thousand years later, you sit in front of your computer and write a line `write_file("config.cfg", data, 1024)` in C language. Your computer completes the encoding of information (byte → threshold voltage of Flash cell), storage (F-N tunneling of floating gate electrons), and indexing (superblock + file entry) in less than a second. There is not the slightest difference in soul between the things you do and the things he does:

- Your superblock magic number is his "knot start mark"
- `blocks[]` in your file entry is his "knots in different positions express different information"
- Your CRC32 checksum is his "end check knot"
- Your log-structured metadata is his clever way of adding new knots to the rope without untying the old ones.
- Your Copy-on-Write is his working habit of first tying a temporary knot to confirm the position and then untying the old knot.
- Your wear leveling is to tie knots evenly on all sections of the rope, so that one section will not be worn out early.

**The essence of storage is mankind’s continuous efforts to combat entropy increase.** Increase in entropy is the only certain direction of the universe. Data naturally tends to be chaotic in the physical world, with charges leaking from floating gates, writes being interrupted mid-stream, oxide layers degrading through repeated tunneling, and bits flipping under bombardment by cosmic rays. Any physical storage medium is a competitor in the race against entropy, and the file system is the coach.

From the clay tablets of Mesopotamia to the papyrus of ancient Egypt, from the papermaking technology of the Han Dynasty in China to IBM's Winchester hard drive, from Toshiba's NAND Flash to Intel's Micron 3D XPoint, every evolution of storage media is a new version of solving the same three problems: **How ​​to encode information into physical media, how to resist the natural deterioration of the media, and how to quickly find the one you need in the vast data.**

## You are the Nth person passing the baton

Have you ever realized that the position you are sitting in right now is the same position that countless people have been sitting in over the past 20,000 years?

The chipu interpreter devised a convention of knot symbols in Cusco, the capital of the Inca Empire. He didn’t know that tens of thousands of years later there would be a Cortex-R5, a C language struct, and a CRC32 algorithm. But what he does, define the expression form of the data so that future readers can correctly understand the information without knowing who the sender is, is the same thing as defining the file entry structure.

Sumerian scribes carved cuneiform inscriptions on wet clay tablets to record the king's taxes. He carved the same record on two different clay tablets, one for the temple and one for the palace. **This is your double backup of SB0 and SB1.** He knows as well as you do: you can’t keep just one copy of information. Natural disasters, in his world are floods, in your world they are power outages, which will break all the eggs.

Cai Lun of the Eastern Han Dynasty improved papermaking technology, allowing the density of information storage to jump from "a roll of bamboo slips can only write a few hundred words" to "a piece of paper can write thousands of words." He doesn't know what `__attribute__((packed))` means, but what he does, **efficiently encode as much information as possible in a limited physical space**, is the same thing as compressing the fields of your superblock.

**You are making a file system, not writing code. You are continuing an engineering relay that has been running for 20,000 years.**

The Copy-on-Write logic you write can trace its origins back to the shadow paging of database systems in the 1980s, to the Log-Structured File System papers of Rosenblum and Ousterhout in the 1990s, and to the copy-on-write transaction model of ZFS in the 2000s. You are just the latest link in a long chain.

The old block release/deletion logic you wrote is for that one day in the future, a driver stops the car on the side of the road, turns off the engine, removes the key, and gets out of the car. When he starts it again the next morning, he does not know whether yesterday's driving log was damaged due to an abnormal power outage. He doesn't know your code exists, he doesn't even know what a file system is. But your logic protected his data. It can be compiled into a car-grade chip, run on another chip tomorrow, and read, understood, and improved by another engineer the day after tomorrow. The relay continues.

**"The future will look at the present just as the present looks at the past."** In 353 AD, when Wang Xizhi wrote this sentence at Lanting in Shanyin, Kuaiji, he was lamenting the shortness of life and the impermanence of things. But the traditional relay used to describe engineering is more apt than any specially designed motto.

The knotted Andean man looked at us as we would look at an engineer thousands of years from now. He doesn’t know what the C language is, he doesn’t know what a file system is, he doesn’t know what an operating system is. But the first big knot he wrapped on the top of the rope, the knot that said "the message starts here," was the ancient precursor to the magic constants you write in your header files today. Future engineers may look at the code you write now and find it clumsy, childish, and inelegant, just like you do now when you look at knotted ropes to take notes. They may use storage media that we cannot imagine to store data. But they will definitely understand the code you wrote today. Your code is their proof of "what I think."

**You are not the end. You are the deliverer.**

## You close the book and open the editor

The book ends here. From knotty rope to Flash, from the quantum mechanics of floating-gate transistors to the 1165 lines of code of KnotFS, we have walked a complete path, from mankind's first "storage system" to today's NOR Flash file system running on embedded chips.

This road has no end. Tomorrow's storage media may be materials that we can't even name today. But no matter how the medium changes, the three core issues remain unchanged: turning information into a physical state (encoding), resisting the degradation of the physical state (durability), and finding it quickly when needed (retrieval).

The engineering tradition to solve these three problems started with the first man in the Andes 20,000 years ago, and continues through Sumer, ancient Egypt, Cai Lun, Gutenberg, IBM, Intel, and you today.

**Someone will take the stick from you tomorrow.** What you have to do now is to make sure your code is clear enough, your documentation is complete enough, and your design decisions are well-founded so that the person who takes over the baton doesn't have to guess "what are the engineers in 2026 thinking?"

When you close this book, open the editor, create a new file named `my_fs.c`, and start typing the first line `#include <stdint.h>`...

You are no longer a new student.

You are the latest holder of an engineering baton that has lasted for 20,000 years.

**Go ahead and tie the knot in your hand.**
