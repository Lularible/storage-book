# 1.5 File Systems: A Peace Treaty with Unreliable Media

## If you operate Flash directly

Before getting into the file system, let's do a thought experiment. The following is what you need to do when directly operating a piece of NOR Flash, assuming there is no file system. You have a 512KB Flash, 128 blocks of 4KB each.

You want to save a file, such as "config.txt", the content is a JSON configuration, about 1200 bytes.

Step one: Find a block that can be written to. Flash cannot be directly overwritten and must be erased before writing. So you need to know which block is erased (all "1"s). You need a data structure to track the status of each of the 128 blocks, which ones are empty (erased), which ones have data, and which ones are bad. You have to maintain this yourself:

```
128-block state tracking (minimized solution)
Block 0: [erased] Block 1: [with data] Block 2: [bad block] Block 3: [erased] …
```

Step 2: Write data on the selected block. But you need to decide: where to write the data? What is the offset within the block? You also need to ask yourself: How do I remember the mapping relationship "config.txt is at block 3, offset 128 bytes, length 1200 bytes"? You have to design a data structure yourself to store these mappings. This is the original form of metadata.

Step 3: If config.txt needs to be updated, for example, a configuration item is changed. You can't rewrite directly at the original location (Flash does not support in-place rewriting). You must write the new version to another block, then mark the old block as "to be erased" and find an opportunity to erase it.

Step 4: Erase is not free. Erase takes 5-10 milliseconds, and, as mentioned before, losing power mid-erase is a disaster. You need to make sure that the old data has not been destroyed (at least there is still a recoverable copy) before erasing it. You need a **power-down security policy**. Make it happen yourself.

Step 5: After a period of normal operation, certain blocks are erased too many times and you start to need **wear leveling**. You can't have block 7 being erased repeatedly (because it happens to always be selected as the target when config.txt is updated), while block 42 is never used (because it has read-only logo data on it that never gets moved). You need an algorithm that keeps track of the historical number of erases for each block and selects the least worn block to write to.

Step 6: A certain block unexpectedly has a physical failure that cannot be erased and becomes a bad block. You need to identify it, remove it from the free block pool, and make sure there is no active data on it, and if there is, you need to be able to recover from other replicas.

Step 7: You realize halfway through that, no, your configuration is no longer 1200 bytes, it has become 1400 bytes (a new function switch has been added). But the block is only 4KB, and config.txt now plus other file data just penetrates the block boundary, you need to store across blocks. You need to design a way to piece together a logical file that spans two physical blocks and seamlessly reorganize it when the upper layer reads it.

If you have really done all the above, written wear-leveling code, managed bad block mapping, implemented power-off safety metadata updates, and supported cross-block data storage, then congratulations.

**You have written a file system. **

It's just that it's difficult to use. And only you will use it.

## What does the file system do for you?

Let’s step back from the hopeless thought experiment above. What the file system is doing for you can be summarized in one sentence:

**Convert "the complexity of managing physical media" into "the convenience of operating logical objects". **

You don't need to know that config.txt is at offset 128 in block 3. You only need to call a function called `write()` and tell it the name of the file and what its content is. At the bottom level, the file system translates "files" into physical block addresses, erasure operations, and wear-leveling schedules, and you don't need to care about any of the details.

```
What users see:
  write_file("config.txt", json_data, data_len);
  → Return OK

What the file system is doing:
  ┌────────────────────────────────────────────────┐
  │ 1. Check the validity of the parameters (the file name is not empty, the data pointer is not empty) │
  │ 2. Check whether "config.txt" already exists in the file table │
  │ 3. If it exists: Update required → Trigger CoW copy-on-write │
  │ 4. find_free_block() → Select the block with the least wear from free_map │
  │ 5. Update SB Log → Record "Start writing config.txt" │
  │ 6. Erase target block → Wait for erasure to complete (asynchronous) │
  │ 7. Program data page by page → Wait for programming to complete (asynchronous) │
  │ 8. Update file table entries → record file name, block number, length │
  │ 9. Update SB Log → Record "config.txt writing completed" │
  │ 10. Compact SB (merge file table and log into spare slot) │
  │ 11. Recycle old blocks to free_map (old version data is no longer needed) │
  │ 12. Return OK to the user │
  └────────────────────────────────────────────────┘
```

Behind a `write` call you see is at least twelve steps of operation, spanning the erasure and programming of multiple physical blocks, including two log writes and possible garbage collection. These operations are completely transparent to you, the person calling `write`.

This is the first and most critical reason for the existence of file systems: abstraction. ** Encapsulate physical complexity behind a clear interface, allowing users to see "files" instead of "blocks" and "names" instead of "addresses".

## Three core abstractions of the file system

The design of file systems can be analyzed from countless angles, but regardless of all specific implementations, from FAT, ext4, NTFS, ZFS, APFS, to modern log structured designs, all file systems provide three core abstractions. These three abstractions are the minimum necessary requirements for a file system to become a "file system".

**Abstract 1: File, a named sequence of bytes**

This is the most basic one. A file is a named, ordered sequence of bytes. Note how abstract this definition is; it doesn't care about how the bytes are actually arranged on the physical medium. A 1200-byte file may be physically divided into three non-contiguous Flash pages, separated by erasure gaps and logical block boundaries. But when you call `read(fd, buf, 1200)`, what you get is a continuous byte stream, and the file system completes the transparent splicing of physical fragments when reading.

```
"File" - logical abstraction vs physical reality

Logical layer (what you see):
  config.txt → [byte0][byte1][byte2]...[byte1199]
  a continuous, ordered stream of bytes

Physical layer (what it actually looks like on Flash):
  Block 3, page 0, offset 0-255 → [byte0.. byte255]
  Block 3, page 1, offset 0-255 → [byte256..byte511]
  Block 3, page 2, offset 0-255 → [byte512..byte767]
  Block 3, page 3, offset 0-255 → [byte768..byte1023]
  Block 7, page 0, offset 0-175 → [byte1024..byte1199] ← Changed the physical block!

File = byte sequence + name + size attribute
File ≠ a fixed physical location
```

The core problem solved by the abstraction of files is **location independence**. The location of data can be dynamically changed without affecting upper-level users. You moved config.txt from block 3 to block 7 today (relayout caused by garbage collection and wear leveling). The person calling `read("config.txt")` will never notice this change.

**Abstract 2: Hierarchical organization of directories and files**

If you only have five files in Flash, you can name them one by one and remember the names. But what if there are a thousand files? What about ten thousand? The human cognitive system cannot directly process "a flat list of a thousand names". We need hierarchies, classifications, and a spatial structure to organize information.

Directory is this kind of spatial structure. There are "2024" and "2025" under "Gallery", and "Tokyo" and "Paris" under "2025". This is a tree structure. You can allocate hundreds or thousands of files into semantically meaningful subspaces, drastically reducing the cognitive load on each lookup.

But the underlying physical implementation of the directory may be very simple or extremely complex:

```
The underlying implementation lineage of the directory

The simplest implementation: a "path" field in the file table
                File name = "/photos/2025/tokyo/img001.jpg"
                 → String comparison path prefix when searching
                FAT and early embedded implementations support directories in this way.

Medium implementation: specialized directory entries, each directory is a special file
                Directory file content = [entry 1: name + inode number] [entry 2: name + inode number] …
                Implementation of ext2/ext3/ext4

Advanced implementation: B-tree / B+tree indexed directory
                Index key = hash of file name
                HFS+ (Apple), NTFS, btrfs, ZFS
                Even millions of file-level directories can be searched in O(log n)
```

Regardless of whether string prefix matching or B-tree indexing is used, the directory presents a consistent interface to the upper layer: a "folder" can contain "files" or "subfolders". The differences in the underlying physical structure are perfectly hidden by the abstraction.

**Abstraction 3: Permissions and attributes, who knows the existence of this file? **

The Flash chip has no idea what a "user" is. Find a NOR Flash chip and ask it: chip, who wrote the data on your block, and who can read it? The chip doesn't answer you because it has no concept of "who". Flash only recognizes electrical signals, addresses, commands, and data. No users, no permissions.

But file systems, designed for multi-user operating systems, introduce the concepts of "owner", "group", and "read/write/execute permissions". In Unix and Linux systems, each file has a uid (user ID) and a gid (group ID), as well as a 9-bit permission mask.

These things don't exist on Flash. They only exist in the file system's metadata structure, stored in certain bytes on the Flash block, interpreted by the file system code, and compared with permissions when `open()` is called:

```
Permission check process (simplified)

open("/etc/shadow", O_RDONLY)
  → File system: Find the inode of /etc/shadow
  → uid = 0 in inode (root)
  → Permission bit in inode = 0600 (owner can read and write, others have no permission)
  → euid of the current process = 1000 (ordinary user)
  → euid != uid → not owner
  → "other" bit contains read permission? → No
  → Return -EACCES(Permission Denied)
```

The whole process does not have any "hardware support" and is completely a logical judgment of the file system code running on the CPU. Flash is only responsible for faithfully storing and returning those dozens of bytes of metadata. It neither knows nor performs permission checks. The file system builds a layer of semantics out of thin air on top of the original "dumb" storage of physical media, that is, who owns the data and who has the right to access the data.

## File System = Translator

Putting these three abstractions together, the role of the file system becomes very clear:

**The file system is the "translator" between the user's high-level semantics (files, directories, permissions) and the physical media's low-level semantics (erasure, programming, verification). **

The user said: "Open `/data/config.json`."

File system translates to:
1. Read Superblock → find the location of the file table
2. Search the file table → find the entry corresponding to `config.json`
3. Get the block number and offset from the entry
4. Send the read command to the Disk driver → "Read block 5, offset 0, length 2048"
5. Disk driver sends Flash command → address calculation, read timing, ECC verification
6. Return data to the user

Each step of translation is crossing a layer of abstraction. Between the user and Flash, there are at least four levels of translation:

```
File system abstraction stack

Application layer: open/write/close ← Semantics of user interaction
             │
File system layer: inode management, directory search, file allocation ← logical to physical mapping
             │
Block layer: block/page addressing, wear leveling, bad block management ← Physical resource management
             │
Device driver layer: Flash command sequence (read/write/erase/status) ← Hardware primitives
             │
Physical layer: Floating gate transistor threshold voltage ← Electronic states of silicon atoms
```

Each level only talks to its neighbors above and below it. The user never knows what the driver layer is doing, and the driver layer never knows what file the user is reading. **Hierarchical isolation is the only way to manage complexity, and the file system is the central hub of this isolation strategy. **

## Back to that 50-year-old interface

The `open/read/write/close` interface defined by the POSIX standard has lived for more than fifty years. It was born in UNIX in the 1970s. When Ken Thompson and Dennis Ritchie wrote UNIX V1 at Bell Labs, they could not have foreseen that fifty years later there would be embedded systems, mobile phones, and file systems running on NOR Flash.

But the interface they designed is still in use today. Why?

Not because they are prophets. It's because they define the semantics of the interface to the right level of abstraction, which is general enough to adapt to any physical medium and specific enough to be efficiently implemented on various platforms.

```
POSIX core file I/O interface

int fd = open(const char *path, int flags, mode_t mode);
// "Give me a file" - doesn't care where the file is, what medium it is on, or how it's stored

ssize_t n = read(int fd, void *buf, size_t count);
// "Read n bytes" - doesn't care how many pages or blocks need to be turned over

ssize_t n = write(int fd, const void *buf, size_t count);
// "Write n bytes" - doesn't care whether it needs to be erased or how many blocks need to be allocated

int ret = close(int fd);
// "I'm done" - don't care about caching, logging, compression, and cleaning

off_t pos = lseek(int fd, off_t offset, int whence);
// "Jump to the Nth byte" - does not care about the addressing algorithm
```

These five functions define all operations of file I/O. Use them for disk files, use them for network sockets, and use them for pipes. In the Unix philosophy, "everything is a file", `open/read/write/close` not only operates data on tracks and sectors, but also operates data on TCP connections, data in inter-process communication pipes, and even data in hardware device registers. Same interface, same semantics, no matter what the "physical reality" behind it is.

For embedded systems, the standard POSIX interface is sometimes too heavyweight. A complete VFS (virtual file system) layer + inode cache + directory entry cache + dentry may require more memory than the RAM of the entire system. This is why embedded file systems often define their own, more lightweight API:

```
Embedded File System API (Asynchronous File System API Example)

sint32 fs_mount(void);
// Replace the complex boot sequence of "superblock load + free block scan"

sint32 write_file(const char *name, const uint8 *buf, uint32 len);
// Asynchronous entry for file writing - parameters are passed directly to file name + data + length
// No file descriptors, no offsets, no complex flags
// In embedded scenarios, one file is often operated at a time and closed after writing.

sint32 read_file(const char *name, uint8 *buf, uint32 buf_size, uint32 *out_len);
// Asynchronous reading - the user allocates the buffer and the driver fills it

sint32 delete_file(const char *name);
// Delete files - the bottom layer triggers SB/FT log update + old block recycling

bool fs_is_idle(void);
// Key query for embedded RTOS: Are there any ongoing I/O operations?
// The synchronization API is waiting for this signal
```

At first glance, there is a big difference between `write_file(name, buf, len)` and `write(fd, buf, len)`. The former uses a file name string instead of a file descriptor, and completes open + write + close in one call. But their semantic essence is the same: the user does not say "Give me the block number → erase → program", the user only says "save this".

POSIX is the "standard answer" accumulated over fifty years. Embedded APIs are simplified versions of "best practices" subject to resource constraints. But the core principle remains unchanged: the file system is the translator, and the user must speak the user's own language, not the language of the medium. **

## Embedded file system: when resources are insufficientLet’s look back at this problem from the eyes of an embedded engineer. Your platform is running FreeRTOS, does not have Linux VFS, does not have a huge page cache, does not have hundreds of KB of RAM for inode caching. You only have 64KB of RAM and a few kernel objects (tasks, semaphores, queues) to build your file system with.

More importantly, your storage medium is not a disk.

A disk is a rotating plate with tracks and sectors on it. The minimum writable unit of each sector that the magnetic head can accurately position is 512 bytes. The disk controller handles bad sector remapping, and the operating system sees a perfect block device abstraction.

This is not the case with Flash. The minimum writing unit of Flash is page (Page, 256 bytes or 512 bytes), but the minimum erasing unit is block (Block, 4KB or larger). You can't just erase a page, you have to erase the entire block. Flash requires wear leveling (because each memory cell has a limited erase cycle life). Flash will silently generate bad blocks. The writing and erasing time of Flash is much longer than the reading time, and is uncertain (depending on the algorithm inside the chip).

```
Disk vs Flash: Physical Characteristics Comparison

                        HDD (mechanical hard disk) NAND Flash
Minimum read and write unit 512B sector 256B~16KB page
Minimum erase unit N/A (can be directly overwritten) 4KB~several MB block
Does it need to be erased before writing? No. Required.
Write latency ~5ms (seek + rotation) ~200μs (page program)
Erase delay N/A ~2-10ms (block erase)
The erase life of each unit is nearly unlimited (magnetic media) 1K~100K times
In-place overwriting supported not supported
Bad blocks are rare (physical damage) relatively common (oxide layer defects)
Data retention time Magnetization stable, decades Charge leakage, ~10 years
```

This is why you can't just move a file system designed for disk (ext4, FAT32) onto a raw Flash and expect it to work. The assumptions of traditional disk file systems, such as in-place overwriting, no erasure concept, and infinite write life, are not true on Flash.

Embedded file systems must solve an additional problem that disk file systems do not need to consider: **Flash Translation Layer (Flash Translation Layer, FTL). **

FTL contains:
- **Address Mapping**: Translate the logical block number of the file system to the physical block number of Flash (frequent changes in physical location caused by erase before writing)
- **Wear Leveling**: Ensures that the number of erases is evenly distributed across all physical blocks
- **Garbage Collection**: Erase data units that have been marked as "invalid" and reclaim space
- **Bad Block Management**: Identify physically defective blocks and remove them from the available block pool to ensure data does not fall on them
- **Power failure recovery**: The log mechanism ensures that metadata can be restored to a consistent state after a power outage at any time

For platforms with complete operating systems (Android, iOS), FTL is usually implemented in the firmware layer of the Flash controller (NAND controller inside eMMC/UFS). What the file system sees is a perfectly simulated "block device", regardless of the fact that the underlying layer is Flash. But on an embedded bare metal or RTOS platform, such as your Cortex-R5 running FreeRTOS, the file system and FTL are a family that goes hand in hand. Your `fs_block.c` is managing wear leveling and bad blocks, and your `fs_sblog.c` is implementing log structure metadata updates. The boundaries between ** file systems and FTL are often blurred or even non-existent in the embedded field. **

## Concerto: Rules of communication between file systems and Flash

With the above foundation, we can now summarize the "code of interaction" between file systems and unreliable physical media. These codes are not an official standard, they are practice guidelines that embedded storage engineers have learned through blood and tears for decades.

**Rule 1: Never copy-on-write. **

In-place overwriting is the most dangerous operation in the file system. If the overwriting operation is interrupted midway, neither the old data nor the new data will be available.

CoW's approach is: **Always write the new version to the new location, leaving the old version intact. ** Only when the new version is completely written, verified, and metadata updated, will the location of the old version be marked as "recyclable". During the entire process, there is at least one complete and available copy of the data, either old (the new version has not been written) or new (the version switch has been completed).

```
Copy-on-Write example

Before writing:
  Block 3: [Version 1: config.txt = {"port": 8000}] ← Old version, fully available
  Block 7: [erased] ← free space

Writing process (CoW):
  1. New data is written to block 7 → [Version 2: config.txt = {"port": 8080}]
  2. Verify that block 7 is written correctly (optional: CRC32 comparison)
  3. Update file table: config.txt → block 7 (no longer block 3)
  4. Mark block 3 as "to be erased and recycled"

If power was lost before step 3:
  → File table still points to block 3 → Version 1 is intact
  → After restarting, the system will see the old version ✓

If power is lost after step 3:
  → File table points to block 7 → Version 2 is in effect
  → Version 1 waits for recycling at block 3 ✓ (recycling is a deferrable safe operation)
```

**Rule 2: Metadata updates must be atomic. **The consistency of the file system depends on the correctness of the metadata, that is, the Superblock and the file table. If metadata is corrupted, files may be lost, blocks may be leaked, and the entire file system may become unmountable.

The standard means of implementing atomic updates of metadata is logging.

```
Metadata log structure (SB Log + embedded file table)

Block 0 (SB0):
  ┌───────────────────────────────────┐
  │ SB Header: magic, seq, free_map… │
  │ nodes[8]: file table (embedded in SB Header) │
  │ SB Log: │
  │ [Rec1: file_create "a.txt"] │ ← Append writing, never overwrite in place
  │[Rec2: file_write "a.txt" 1024]│
  │ [Rec3: file_delete "a.txt"] │
  │ [Rec4: file_create "b.txt"] │
  │ … │
  │ When Log reaches 50% block capacity → Compact │
  └────────────────────────────────────┘

Compact (log compression):
  Merge all records in the Log + file table nodes in the memory into the latest status
  → Write to the spare SB slot (block 0↔block 1 alternately)
  → The new SB contains the latest file table + cleared log area
  → The old SB slot is marked for erasure
```

The atomicity of the log comes from its append-only mode. You never overwrite the original record with a new value, you append a new record to the end of the log. If the power is interrupted during the append process, there will be at most one incomplete and unverified "half" record at the end. When restarting, scan the log, check the CRC of each record, retain the CRC pair, and discard the incorrect CRC (it is waste in the middle of a power outage). Metadata can always be restored to the last consistent version.

**Rule 3: Verify everything you can. **

To build a reliable system on unreliable physical media, you must assume that "any data can go wrong," including the data you just wrote.

CRC32 or similar check codes are standard in embedded file systems (to prevent unintentional errors, CRC32 is more than enough; to prevent malicious tampering or pursue ultimate integrity, it needs to be upgraded to cryptographic hashing):

- Superblock Header has CRC
- SB Log Each record has a CRC

Every time you read a key data structure on Flash, you have to do a verification. Read the Superblock → check the CRC → trust the CRC if it is correct → try another copy (SB1) if the CRC is wrong. Verify each step, and then use the verified data to decide on the next step. This is not "over-caution", it is the only correct way to work under the premise that the physical medium is unreliable.

**Rule 4: Design for power outages, do not remedy them afterwards. **

"Be sure to recover after a power outage" should be a **design constraint**, not a **disaster recovery strategy**. When you write code, you should assume that every line of Flash operations may be interrupted by a power outage.

Specifically implemented into the embedded file system, this principle is reflected in:
- Put the erase operation after the new data is written (do not erase the old block first and then write the new data. In case of a power outage in the middle, the new data has not been written yet and the old data is gone)
- Metadata update sequence: first write the Data Block → then update the file table entries in the memory → finally Compact the entire SB to the spare slot (SB Log is only an operation record, and Compact is required for the "validation" of the file table status)
- The Compact operation must be transactional: if the power is cut off during the compact process, it will either return to the old SB state before the compact, or the new SB state after the compact has been completed. There is no "semi-compact" intermediate state.

This principle is called **Commit order** in KnotFS. SB Log is a record of operation intentions. It tells you "what happened". However, the actual status of the file system, whether the file exists and which block it occupies, is determined by the file table (nodes[8]) in the SB Header. Compact "implements" the operation intention in the SB Log into the file table, and then writes it into the spare SB slot. Once Compact is completed and the new SB verification passes, the old SB slot is marked as recyclable. If the Compact is powered off midway, the old SB is still intact and available. After restarting, the old SB is read and restored to the state of the last successful Compact.

## Anatomy of a Minimal File System

Let's put all these abstract concepts into practice with a concrete example. Suppose you have a minimum viable file system, which only provides four operations of "mounting, writing, reading, and deleting". It runs on FreeRTOS. The storage medium is 128 blocks × 4KB NOR Flash.

Its internal structure is like this:

```
Memory + Flash layout of tiny file system

Flash layout (64KB teaching version):
┌──────────┬──────────┬────────────────────────────────┐
│ SB0 │ SB1 │ Data Block │
│ (Block 0) │ (Block 1) │ (Block 2-15) │
│ Superblk │ Superblk │ File content storage area │
│ +nodes[] │ +nodes[] │ │
│ +SBLog │ +SBLog │ │
└──────────┴──────────┴───────────────────────────────────────────────────────────────────────────────

Core data structures in memory:
┌────────────────────────────┐
│ g_free_map │ ← "Collection General Catalog": 16-bit bitmap, marking whether each block is free
│ g_wear[16] │ ← Number of erases per block (wear leveling)
│ g_sb_log_pending │ ← Whether compact is needed
│ g_current_req │ ← The asynchronous request currently being processed
└─────────────────────────────┘
```

When the user calls `write_file("hello.txt", "Hello World", 11)`, the state machine process the system goes through:

```
State machine process (simplified)

STATE_IDLE → Request received, parameter verification
     ↓
STATE_LOAD_SB → Read Superblock, check CRC, get file table (nodes[])
     ↓
STATE_SEARCH_FILE → Search for "hello.txt" in the file table
     ↓
STATE_FIND_FREE_BLOCK → Select the free block with minimal wear from free_map
     ↓
STATE_START_SB_LOG → SB Log appends "Start writing hello.txt" record
     ↓
STATE_ERASE_TARGET → Erase selected target block (asynchronous wait)
     ↓
STATE_WRITE_DATA → Program user data page by page (asynchronously wait for each page to complete)
     ↓
STATE_UPDATE_META → Update file table entry in memory
     ↓
STATE_COMPLETE_SB_LOG → SB Log appends "hello.txt writing completed"
     ↓
STATE_COMPACT → Compact to the standby SB slot (persistent file table + log)
     ↓
STATE_MARK_OLD → Old version data blocks are marked for erasure and recycling
     ↓
STATE_COMPLETE → wake up the waiting synchronous API caller and return to IDLE
```

This is not a "function call", this is a state machine loop running in a FreeRTOS task. Each step may span multiple RTOS ticks (waiting for the completion signal of the Flash asynchronous operation). The status of the current request is saved in `g_current_req->state`. Each time the task is awakened, it continues from the last interrupted status.

This looks complicated. But if you think of each state as an independent, indivisible "atomic operation", at this granularity, the interaction between the system and the physical medium becomes controllable, the inconsistency caused by the interruption is limited to a single state, and the recovery process can restart accurately from a known safe point.

## Library: What readers see and what librarians manage are two different worlds

Let's wrap up this section with the full metaphor of "library."

You are a librarian. You signed a contract to turn a wasteland (512KB NOR Flash address space) into a library (a usable file system) that can be borrowed normally, and ensure that the people who borrow books (users) cannot see a bare iron shelf, a roll of tape, and a box of labels.

**Physical layer of the library: You hit each side of the bookshelf. **

Each block of Flash is your bookshelf grid. There are 128 bookshelves, some of which have been cleared (erased, waiting for books to be arranged), some of which are lined with books (programmed, storing data), and some are broken (bad blocks, never to be used again). You need to accurately mark the status of each bookshelf on the collection master catalog (free_bitmap).

**The structural layer of the library: how you organize it. **

SB0 and SB1 are the east and west wings of your library, two identical entrances. The general catalog of collections (free_map, nodes[] file table in SB Header) is posted on the wall of each entrance hall, and the borrowing record book (SB Log) is hung in the corridor. Readers can enter if either entrance is intact, and the other is a backup. The data block is your actual library, where the files are stored.

Every time a new book needs to be put into storage (a new file is written), you don't just throw the old books into the aisle and bring the new books in. Copy-on-Write tells you: keep the old bookshelf, build a new bookshelf, put the new books in, change the call number on the registration card, and then the old bookshelf can be used for other purposes. You always have a complete storage area available: either a new bookshelf or an old one.

**The operational layer of the library: your record books and recataloging. **

The SB Log is the borrowing record book you post on the wall of the entrance corridor, "Starting cataloging bookshelf No. 3 today → Bookshelf No. 3 has been put on the shelves → Bookshelf No. 3 is officially opened." All status changes are written above. In the event of a power outage (power outage), you can know the exact status of the library by looking at the record book: which bookshelf has been organized, which is still being sorted, and which books may be in chaos.

Compacting is what you do when you find that the record book is posted on half the wall: combine all the "last valid states" into a concise record, copy it to another location on the wall, and then free up the old space for later use. The process of re-writing is **transactional**, either the old record book is still valid (you cut off the power in the middle of transcribing, and you still see the old record book after restarting), or the new record book has taken effect (the copy is completed, the verification is passed, and the pointer switches to the new position). There is no "half new, half old" record book because rewriting is atomic by design.

**Persistence layer of the library: the collection catalog is never lost. **

Superblock records the core information of the library (the library's collection version number, seq number, the total number of bookshelves, and the current number of free bookshelves), all of which are double redundant storage. SB0 is in block 0 and SB1 is in block 1. If a power surge burns out SB0, you can use SB1 to restore it and be completely unaffected. You even periodically "refresh" one of the copies with a larger seq number. If a power outage occurs during this refresh process, the seq number ensures that only the "latest and verified" copy will be trusted.

**And what about readers? What readers see and what librarians manage are two different worlds. **When readers walk into your library, what they see is: a neat row of bookshelves, a call number, and a book. The reading area has desks and lamps. They don't know that behind the bookshelf are densely arranged Flash blocks, that behind the call number is a lengthy erasure programming verification process, and that each layer of the bookshelf is a logical abstraction under log records and metadata mapping. They don't need to know. They just need to "borrow the book" (call `write`) and the book is in place (return OK).

The entire craft of the file system is so that readers never need to walk into the device room.
